# ADR-0015 架构原则：小组件与标准接口（UNIX 哲学）

- 状态：已接受（2026-10-28）

## 背景

旧产品的维护成本主要来自三处：巨型单文件；自研的消息同步，三端各写一套；只为 Hermes 写的约 2.2 万行
适配层。一个组件知道得越多，换掉它或改动它的代价就越大。

Wonton 要做到“万物皆插件、Agent 可替换”，需要一条贯穿全局的原则来判断：新能力该放进哪个组件、组件之间
怎样连接。主人提出按 UNIX 哲学来做。

## 决策

1. **一个组件只做一件事。**
   - 核心的职责见 [AGENTS.md](../../AGENTS.md) 的“产品边界”。
   - Tuwunel 管消息，magpie 管模型，插件各管自己的能力（相册、文件、音乐等）。
   - Agent 插件负责思考和干活；ACP 桥只负责把 Matrix 房间和 ACP 会话接起来（ADR-0007）。
2. **组件之间只经标准接口连接**，就像 UNIX 里的管道：
   - Matrix 收发消息，MCP 调用工具，ACP 驱动 Agent，OIDC 登录，Compose 打包插件，iroh 承载远程访问；
   - 组件不直接读写彼此的数据，也不调用彼此的内部接口。
3. **同一类组件遵守同一份合同，每一块都能单独替换。**
   - 所有 Agent 插件经同样的权限（`matrix.bot`、`models`、`storage.*` 等）拿到同样的能力，核心不为某个
     Agent 特殊处理。Hermes 只是第一个使用这份合同的 Agent 插件。
   - 换 Agent 不用改核心，换模型网关不用改 Agent，换客户端（比如用 Element X）不用改服务器。
4. **边界上优先用协议，其次才用库。** 跨组件的边界用进程间的协议，方便独立替换和升级；不在核心或桥里
   内嵌某一家的“大一统”适配库。确实需要第三方库补足能力时，把它包成一个说标准协议的小程序，作为可以
   替换的零件放进对应的插件。
5. **组合优于扩张。** 新能力优先做成新的小组件（插件或适配器）组合进来，而不是往已有组件里加功能。
6. **每个组件都要可观察。** 错误按原因分类（ADR-0011、AGENTS.md 的“失败即停”），日志能追溯到具体的
   组件和版本，比如核心的启动日志打出构建它的提交号。

## 理由

- 组件小，改动和测试的范围就小；接口标准，组件就能独立演进、独立替换。
- 标准接口背后已经有现成的生态：Matrix 客户端、MCP 工具、支持 ACP 的 Agent 都能直接用，符合“不造轮子”。

## 代价与风险

- 进程和接口变多，排查问题要跨组件看日志，所以第 6 条必须做到。
- 标准协议往往只覆盖公共能力，比如 ACP v1 没有“插话”。缺口靠协议允许的可选扩展或小适配器补足，
  不在接口里写某一家的特例。
- 每个接口都要有契约测试，保证替换组件时合同不变（ADR-0013）。
