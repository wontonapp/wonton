# ADR-0053 插件之间按能力依赖：只写直接依赖，装时一起装，卸时拦下

- 状态：已接受（2026-11-07）

## 背景

一个插件要用另一个插件的服务时（Seerr 要 Jellyfin，Prowlarr 给下载器喂种子，Agent 用模型网关），清单里没有地方写，
主人只能自己知道先装哪个、哪个不能卸。核心里已经有两种特例：`provides.models`（模型网关，使用方申请 `models`
权限，ADR-0008）和 `provides.egress_proxy`（代理插件，ADR-0039）。

各家 NAS 和自托管平台的做法：按能力依赖的（Home Assistant 的 services、Cloudron 的 addons、Umbrel 的 implements、
Debian 的虚拟包）能换提供者；按插件名依赖的（飞牛的 `install_dep_apps`、Synology 的 `install_dep_packages`）把使用方
绑死在一个插件上，Synology 还因为几个套件共享一份 Python 出过一次升级后依赖方起不来的事。

## 决策

### 能力

能力是一个名字加一份接口约定。名字有两种：

- **核心定义的**：小写字母加下划线（`models`、`search`），由核心维护一张能力表，插件规范列出全表。表里每一项写明接口
  （一个已有的标准协议，如 OpenAI 兼容 API、SearXNG 的 JSON 接口，写明路径和必须支持的部分）。接口有不兼容的变化时
  换一个新名字（`search2`），能力不带版本号。
- **第三方定义的**：`x-<作者>.<名字>`（如 `x-acme.ledger`）。核心只按名字配对提供方和使用方，不管接口对不对得上。
  商店和确认页把它标成“第三方定义的能力”（来源提示，同“未审核”）。

清单写了不带 `x-` 前缀、又不在表里的能力，装的时候拒绝并说明“这份核心不认识能力 X，升级核心后再装”，不当成没写。

`models` 和 `egress_proxy` 进能力表，保留各自的专用字段（模型网关的服务商命令、代理插件的出口设置）。使用方一侧，
`models` 权限改成 `wants: [models]`；`egress_proxy` 没有使用方声明，出网插件都经它（ADR-0039 不变）。

### 清单

```yaml
x-wonton:
  provides:
    search: {service: searxng, port: 8080}
  requires: [search]      # 没有就装不上
  wants: [models]         # 有就用，没有照装
```

- 只写直接依赖，不递归。提供能力的插件自己不能 `requires` 别的能力（可以 `wants`），依赖最多一层，核心不解依赖图。
- 提供方可以像模型网关一样声明签发和吊销凭据的命令（`credentials`，同 ADR-0008 的凭据助手约定），核心给每个使用方
  签一个只属于它的凭据，注入 `WONTON_<名字>_KEY`；不声明时，提供方只认经核心转发来的请求。
- 只给一个插件用的服务（数据库、缓存）照旧写进那个插件自己的 compose，不做成能力。
- `plugin check` 和官方索引的检查：核心定义的能力名在表里，`provides` 的服务和端口在 compose 里；官方索引里每个被
  `requires` 的能力至少有一个插件提供，否则这个使用方的条目不收录。

### 访问

使用方在自己的插件网络里访问 `<名字>.wonton.internal`（第三方的是 `x-acme.ledger.wonton.internal`），核心认出来源、
转发给这个使用方选用的提供方，注入 `WONTON_<名字>_URL`（名字转大写，非字母数字换成 `_`）。转发时带上
`X-Wonton-Plugin: <使用方 ID>`，提供方据此区分是谁。

### 几个提供方

同一能力可以装几个提供方。和手机的“默认应用”一样：

- 设置里每种能力选一个全局默认的提供方。装上第一个提供方时它就是默认；默认的被卸掉时，剩下的里面选最早装的，
  并在设置里提示主人看一眼。
- 使用方插件的详情页里可以单独给它指定另一个提供方，不跟默认走。

### 装

- 商店详情和安装预览列出缺的 `requires` 能力和索引里提供它的插件。主人选一个、确认一次，核心先装提供方、等它就绪，
  再装使用方；确认页把两边申请的权限一起列出来。提供方装失败时使用方不装，错误说清是哪一个。
- Bot 经 MCP 装插件时同样走确认卡片（ADR-0016），卡片上列出要一起装的插件。
- 缺 `requires` 而索引里没有提供方：装不上，预览写明需要哪个能力、商店里没有提供它的插件。
- 缺 `wants`：照装，详情页一条轻提示，类别由核心给。

### 卸、停和升级

- 卸载提供方时，有使用方 `requires` 它、又没有别的提供方能接上，就拦下，错误列出这些插件，不给一键连卸。有别的提供方时，
  这些使用方改用默认的那个，确认页写明。只被 `wants` 的照卸，确认页写明哪些插件会用不上它。
- 卸载使用方后，有提供方再没有别的插件在用，问主人要不要一起卸，不自动卸。
- 停止提供方不拦，确认页写明谁会受影响。
- 升级提供方时，新版本不再提供某个有人 `requires` 的能力、又没有别的提供方，拦下这次升级，说清是谁在用。
- 启动 `requires` 了某能力的插件时，它选用的提供方停着就先启动提供方。

### 运行时

- 使用方选用的提供方没在运行（停了、异常、记录读不懂）时，`requires` 它的插件标为异常，原因类别是“依赖的插件没有在
  运行”，带上提供方的名字；提供方恢复后核心重新核对，使用方回到运行中。只 `wants` 它的插件状态不变，详情页一条轻提示。
- 核心转发能力请求时，提供方不在运行返回 503，类别同上；没声明这个能力的插件访问它返回 403 `permission_denied`。
- 核心启动时先恢复提供方，再恢复使用方。
- 好友共享（ADR-0051）不另做规定：开放给好友的插件照旧经主人的核心访问它的提供方。

## 理由

- 按能力依赖，提供方能换（换一个媒体服务器、一个模型网关）而使用方不改，这是 ADR-0015 的“经标准接口连接，每个组件都能
  单独替换”。按插件名依赖等于把两个插件焊在一起。
- 经核心转发而不是把两个插件放进同一个网络：插件之间照旧互相隔离，核心按来源认出是谁、留审计，几个提供方时按主人的
  选择转发，在提供方不在时给出分清原因的错误。`models.wonton.internal`、`mcp.wonton.internal`、
  `notify.wonton.internal` 已经是这种做法。
- 第三方能力名带前缀：社区插件之间也能互相依赖而不用等核心发版；前缀让它和核心定义的名字不撞，也让界面能标清来源。
- 一层依赖、不带版本是飞牛和 Umbrel 的简化：家用场景里依赖链很短，解依赖图和版本冲突的复杂度换不来什么。
- 数据库不做成能力：共享数据库把几个插件的升级、备份、权限绑在一起，TrueNAS 也是每个应用自带。

## 代价与风险

- 核心定义的能力加一项要改核心、发版。第三方能力不用，但核心不保证两边的接口对得上，对不上时是使用方自己报错。
- 只支持 HTTP 类的接口；以后要非 HTTP 的（SMTP、数据库协议）得另想转发方式。
- 不给一键连卸：被依赖的提供方要主人先一个个卸掉使用方，多点几下，换来不会误删数据。

## 没选的做法

- **按插件名依赖**（飞牛、Synology）：见理由。
- **带版本约束**（Synology、Debian）：插件的接口靠能力名区分，版本约束只会多出装不上的组合。
- **使用方和提供方共用一个 Docker 网络**：省掉转发，但插件之间不再隔离，核心也看不到谁在用谁。
- **递归依赖**：提供方再依赖别的能力时要解依赖图、处理环，没有这样的需要。
- **同一能力只允许一个提供方**：主人想同时留两个（比如一个本地模型、一个云端模型）做不到。
