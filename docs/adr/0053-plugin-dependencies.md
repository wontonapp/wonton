# ADR-0053 插件之间按能力依赖：只写直接依赖，装时一起装，卸时拦下

- 状态：已接受（2026-11-07）。“高权限能力”一节 2026-11-07 补充；“使用方怎么用变量”“共享凭据”“连接变了就重建使用方”三节和 `tcp` 能力
  2026-11-12 补充（主人定：*arr 共享凭据，`mqtt` 进能力表并由核心按使用方做四层中继，连接变了自动重建使用方、高权限的先确认）；
  `personal_data` 能力 2026-11-12 补充（ADR-0098）

## 背景

一个插件要用另一个插件的服务时（Seerr 要 Jellyfin，Prowlarr 给下载器喂种子，Agent 用模型网关），清单里没有地方写，
主人只能自己知道先装哪个、哪个不能卸。核心里已经有两种特例：`provides.models`（模型网关，使用方申请 `models`
权限，ADR-0008）和 `provides.egress_proxy`（代理插件，ADR-0039）。

各家 NAS 和自托管平台的做法：按能力依赖的（Home Assistant 的 services、Cloudron 的 addons、Umbrel 的 implements、
Debian 的虚拟包）能换提供者；按插件名依赖的（飞牛的 `install_dep_apps`、Synology 的 `install_dep_packages`）把使用方
绑死在一个插件上，Synology 还因为几个套件共享一份 Python 出过一次升级后依赖方起不来的事。

## 决策

### 能力

能力是一个名字加一份接口约定。名字有两种：

- **核心定义的**：小写字母加下划线（`models`、`search`），由核心维护一张能力表，插件规范列出全表。表里每一项写明接口
  （一个已有的标准协议，如 OpenAI 兼容 API、SearXNG 的 JSON 接口，写明路径和必须支持的部分）。接口有不兼容的变化时
  换一个新名字（`search2`），能力不带版本号。
- **第三方定义的**：`x-<作者>.<名字>`（如 `x-acme.ledger`）。核心只按名字配对提供方和使用方，不管接口对不对得上。
  商店和确认页把它标成“第三方定义的能力”（来源提示，同“未审核”）。

清单写了不带 `x-` 前缀、又不在表里的能力，装的时候拒绝并说明“这份核心不认识能力 X，升级核心后再装”，不当成没写。

`models` 和 `egress_proxy` 进能力表，保留各自的专用字段（模型网关的服务商命令、代理插件的出口设置）。使用方一侧，
`models` 权限改成 `wants: [models]`；`egress_proxy` 没有使用方声明，出网插件都经它（ADR-0039 不变）。

能力表每一项除了接口，还写明三件：凭据方式（不用、按使用方、共享，见“共享凭据”）、传输（`http` 走网关，`tcp` 走
[ADR-0092](0092-capability-tcp-relay.md) 的四层中继，`tcp` 的带端口）、是不是高权限。这次进表的：

| 能力 | 接口 | 凭据 | 传输 |
| --- | --- | --- | --- |
| `mqtt` | MQTT 3.1.1 和 5.0；用户名 `WONTON_APP_ID`，密码 `WONTON_MQTT_KEY` | 按使用方，必须声明 | `tcp`，1883 |
| `sonarr` | Sonarr 的 HTTP API v3（`/api/v3/`），`X-Api-Key` 鉴权 | 共享 | `http` |
| `radarr` | Radarr 的 HTTP API v3（`/api/v3/`），`X-Api-Key` 鉴权 | 共享 | `http` |
| `lidarr` | Lidarr 的 HTTP API v1（`/api/v1/`），`X-Api-Key` 鉴权 | 共享 | `http` |
| `personal_data` | 位置和健康数据的存取契约，见 [ADR-0098](0098-location-and-health.md) 第 5 节；类型在 `wonton-protocol` | 按使用方，必须声明 | `http` |

都不是高权限。官方插件里写成 `x-wonton.mqtt`、`x-wonton.sonarr` 这类第三方名字的，改用表里的名字。

### 清单

```yaml
x-wonton:
  provides:
    search: {service: searxng, port: 8080}
  requires: [search]      # 没有就装不上
  wants: [x-acme.ledger]  # 有就用，没有照装
```

`requires`、`wants` 和通用 `provides.<能力名>` 的规范版本下限是 `0.11`。这个下限不追溯到专用的
`provides.models`、`provides.egress_proxy`，它们保留各自原有的版本下限。

- 只写直接依赖，不递归。提供能力的插件自己不能 `requires` 别的能力（可以 `wants`），依赖最多一层，核心不解依赖图。
  例外是同一个能力：提供方可以 `requires` 或 `wants` 自己提供的那个能力，核心给它选提供方时排除它自己（`agent_acp`，见 ADR-0061 第 9 节）。
- 提供方可以像模型网关一样声明签发和吊销凭据的命令（`credentials`，同 ADR-0008 的凭据助手约定），核心给每个使用方
  签一个只属于它的凭据，注入 `WONTON_<名字>_KEY`；不声明时，提供方只认经核心转发来的请求。
  签发和吊销走同一条命令执行路径：在声明的服务容器里执行 argv、不经 shell，`{name}` 替换为使用方插件 ID，
  最多等 30 秒；签发时随机凭据加换行经标准输入送入，吊销时不送凭据。退出码为 0 才算成功；失败保留原始错误、
  退出原因或标准错误输出，不把命令执行失败写成已连接。
- 只给一个插件用的服务（数据库、缓存）照旧写进那个插件自己的 compose，不做成能力。
- `plugin check` 和官方索引的检查：核心定义的能力名在表里，`provides` 的服务和端口在 compose 里；官方索引里每个被
  `requires` 的能力至少有一个插件提供，否则这个使用方的条目不收录。

### 访问

使用方在自己的插件网络里访问 `<名字>.wonton.internal`（第三方的是 `x-acme.ledger.wonton.internal`），核心认出来源、
转发给这个使用方选用的提供方，注入 `WONTON_<名字>_URL`（名字转大写，非字母数字换成 `_`）。转发时带上
`X-Wonton-Plugin: <使用方 ID>`，提供方据此区分是谁。
提供方的服务实际使用宿主网络时，复用 WebUI/MCP 的 Unix 中继，经该服务和端口唯一的套接字转到宿主回环地址；
不把使用方接进提供方网络，也不要求提供方额外发布端口。

### 几个提供方

同一能力可以装几个提供方。和手机的“默认应用”一样：

- 设置里每种能力选一个全局默认的提供方。装上第一个提供方时它就是默认；默认的被卸掉时，剩下的里面选最早装的，
  并在设置里提示主人看一眼。
- 使用方插件的详情页里可以单独给它指定另一个提供方，不跟默认走。

### 连接与凭据记录

- 插件记录目录下的 `capabilities/connections.json` 保存全局默认、使用方单独选择、提供方安装顺序，以及每对
  “使用方—提供方—能力”的确认、凭据和失败原因。目录权限 `0700`、文件权限 `0600`，临时文件写完同步后再改名；
  持久化成功才更新内存。读不懂记录就报存储错误或能力不可用，不当作空记录、更不自动恢复授权。
- 凭据在调用签发命令前落盘；重启、提供方恢复或重建时用同一个值重新签发，不因重启换 key。签发失败的连接不能转发，
  卸载使用方或提供方时删除相关连接和选择记录，按凭据命令约定吊销；重装不继承旧确认。
- 可选连接首次签发失败或提供方未就绪，不阻止安装；确认和待签发的凭据保留，未成功连接时 URL/KEY 为空。
  提供方恢复后重用同一凭据；需要重建使用方才能注入新变量时，记录重建未完成的状态，失败原因保留到恢复成功。

### 装

- 商店详情和安装预览列出缺的 `requires` 能力和索引里提供它的插件。`CapabilityProvider` 只带
  `id/title/source/high_privilege`；主人选中后，App 按它的 `source` 调现有预览接口，取得提供方自己的完整
  `InstallPreview`，在同一个确认页里单独列一节权限、可选项、密钥、设备和局域网选择。不在候选列表里嵌套预览，
  也不一次取全部候选。
- `InstallTogether` 是 `{ id, request: InstallRequest }`：内层是提供方自己的完整决定，带它的来源、摘要、计划、
  权限、可选项、输入密钥、设备、局域网开关和范围。只允许一层，内层 `install_together` 或 `connect_plugins`
  非空时，整个请求报 `invalid_input`，不递归装依赖。`request` 是必填项，缺失时直接解码失败，不补空请求。
- `InstallPreview.plan` 是不透明字符串，`InstallRequest.plan` 原样带回。核心按使用方的插件包摘要、当时已装的
  提供方和全局默认、使用方—提供方—能力的连接集合计算；确认时重算不符就返回 HTTP 409 `changed`，App 重新预览，
  不自动授权变更后的连接。提供方各自的摘要和计划由内层请求核对；`plan` 的 serde 默认值只是通用解码兼容，
  不代表空计划可以跳过核对，也不保留旧请求写法。
  此计划绑定只适用于 `InstallRequest` 安装流程。升级预览虽复用 `InstallPreview`，`UpgradeRequest` 不携带
  `plan`，不提供这项升级连接状态绑定。
- 所有层的输入、授权、摘要和计划都校验通过后，才能开始安装任何插件。核心先装提供方、等它就绪，再装使用方。
  任一步失败按现有规则整体回滚本次安装，使用方不会半装；错误写清失败的是哪个插件，回滚未完成也如实报告。
  回滚也恢复本次安装改变过的既有使用方：按安装前的记录、变量和镜像重建，保留原有密钥与数据；恢复失败仍保留最初的
  安装错误，并附上未恢复的插件和清理错误，不把部分回滚描述为成功。
- Bot 经 MCP 装插件时使用同一个请求形状，走同一套预览、校验和执行；确认卡片列出要一起装的插件及它们的权限与输入项。
- 缺 `requires` 而索引里没有提供方：装不上，预览写明需要哪个能力、商店里没有提供它的插件。
- 缺 `wants`：照装，详情页一条轻提示，类别由核心给。

### 高权限能力

有的能力让使用方能借提供方做很多事，比如能跑命令、改文件的 Agent（`agent_acp`）。使用方连上它，就拿到了提供方的大部分本事，
所以“谁连上了谁”要主人点头，不能跟着依赖关系自动发生。

- **哪些算高权限**：核心定义的能力在能力表里逐项标明，规范的能力表照抄。第三方能力（`x-` 前缀）核心不知道接口是什么，
  看提供方：提供方申请了高权限（ADR-0036 的任一级），或者它是 Agent 插件，这个能力就按高权限处理。
- **三个时刻要确认**，确认页醒目写明“X 能经 Y 使用 <能力>”，和 ADR-0036 的高权限同一种醒目程度：
  1. **装**：装使用方（含一起装提供方）时，安装确认页就是这次确认。
  2. **换提供方**：在使用方详情页换、在设置里改默认（列出跟默认走的使用方）、卸掉默认的提供方导致改用别的（卸载确认页
     写明），都是确认。
  3. **新使用方第一次连上**：提供方后装时，已装、`wants` 这个能力的插件不自动接上。提供方的安装确认页列出它们，主人
     勾选的才接上，没勾的详情页留一条轻提示，以后可以在那里接上。
- **Bot 发起的**（经 MCP 装插件、换提供方）一律走确认卡片（ADR-0016），由主人在 App 里点，规则同 ADR-0033 的高权限。
- **核心按记录转发**：每对“使用方—提供方—能力”确认过才记下，没有记录的请求返回 403 `permission_denied`，和没声明这个
  能力的插件一样。同一对确认过一次，之后重启、升级都不再问（升级多申请的权限照 ADR-0017 在升级确认页列出）；卸掉使用方
  或提供方时记录一起删，重装要重新确认。
- **核心只管连不连**：连上以后使用方能让提供方做什么（比如 Agent 的工具确认、权限放宽），由提供方自己管，核心不在中间
  拦单个请求。

### 使用方怎么用变量

把 `WONTON_<名字>_URL`、`_KEY`（`tcp` 能力还有 `_HOST`、`_PORT`）写进上游配置是插件自己的事，核心不碰上游的配置文件：

- 上游认环境变量的，compose 里直接引用，如 Zigbee2MQTT 的 `ZIGBEE2MQTT_CONFIG_MQTT_SERVER: ${WONTON_MQTT_URL}`。
- 不认的，插件带一个幂等的一次性“连接”服务（`restart: "no"`），每次启动经上游 API 把地址和 key 写进去，变量为空时把
  对应的配置删掉或停用。例：Prowlarr 往 Sonarr 里加自己，Bazarr 接 Sonarr。
- 不读别的插件的数据目录拿 key，不写死别的插件的容器名或服务名（Umbrel 这样做）。规范和开发套件模板给这两种写法的范例。

### 共享凭据

Sonarr、Radarr、Lidarr 只有一把全局 API key，没有建多把的接口，按使用方签发做不到。凭据方式标为“共享”的能力：

- 提供方不声明签发和吊销命令，清单写 `provides.<名字>.credentials: shared`（核心定义的能力以能力表为准，写了不一致的清单不合法；
  第三方能力由提供方这样声明）。
- 核心装提供方时生成一把 key（32 位小写十六进制，同 Servarr 自己生成的格式），存在连接记录里，以
  `WONTON_PROVIDES_<名字>_KEY` 注入提供方，由插件映射给上游（如 `SONARR__AUTH__APIKEY`）。每个连上的使用方拿到同一把，
  变量照旧是 `WONTON_<名字>_KEY`：使用方分不出也不用分是共享的还是只属于它的，换成按使用方签发的提供方时使用方不用改。
- 转发和放行不变：请求照旧经核心，没有连接记录的照旧 403。key 只是上游自己的那道门。
- **断开一个，全部换 key**：一个使用方断开（卸载、换提供方、主人断开）时，核心生成新 key，先按“连接变了就重建使用方”重建提供方，
  再重建其余连着的使用方。断开的那个手里的旧 key 立即作废：提供方还可能经局域网端口、宿主网络或公网入口被连到，那里只有 key 挡着。
  确认页写明“断开 X 后，Y 和 Z 会换新 key 并重启”。
- 新使用方连上不换 key，只重建这个使用方。

### 连接变了就重建使用方

使用方拿到的变量取决于连接：没连上时为空，连上时是地址和 key。变量是渲染时注入的，所以连接一变，核心重新渲染使用方，
按 `wonton.render` 摘要只重建渲染结果变了的服务（同 ADR-0077 改设置），卷和数据目录不动。会触发的情况：

| 情况 | 重建谁 |
| --- | --- |
| 提供方后装，`wants` 它的插件接上 | 接上的使用方 |
| 换提供方（详情页单独换、改全局默认、默认的被卸掉改用别的） | 换了的使用方：新提供方给的 key 不同 |
| 提供方卸掉，`wants` 它的插件断开 | 断开的使用方：变量变空 |
| 共享凭据换 key | 提供方和其余连着的使用方 |

- **升级提供方不重建使用方**：地址是核心的别名，不随提供方的版本变。
- **高权限能力先确认再重建**：哪些时刻要确认见“高权限能力”，主人点了确认才改连接记录、才重建；没确认就什么都不变。
  普通能力不问，直接重建，详情页不另外提示。
- Bot 发起的变化（经 MCP 装提供方、换提供方）同样在主人确认后才重建。
- 重建失败：使用方标为异常，类别是“连接变了以后没能重启”，带上原始错误；连接记录保留新的，详情页可以重试。共享凭据换 key 时，
  提供方重建失败就把 key 退回旧的、提供方按旧 key 再渲染一次，不往下重建使用方；退回也失败就把提供方标成异常。
- 几个使用方一个一个重建，按安装顺序，一个失败不影响下一个。

### 这次进表的能力：契约、提供方和使用方

| 能力 | 契约 | 提供方 | 真实使用方 |
| --- | --- | --- | --- |
| `mqtt` | MQTT 3.1.1 / 5.0，见 ADR-0092 | Mosquitto 插件 | Zigbee2MQTT；之后 Node-RED、ESPHome |
| `sonarr` | Sonarr API v3 + 共享 key | Sonarr 插件（映射 `SONARR__AUTH__APIKEY`） | Bazarr、Prowlarr、Seerr |
| `radarr` | Radarr API v3 + 共享 key | Radarr 插件（映射 `RADARR__AUTH__APIKEY`） | Bazarr、Prowlarr、Seerr |
| `lidarr` | Lidarr API v1 + 共享 key | Lidarr 插件（映射 `LIDARR__AUTH__APIKEY`） | Prowlarr |

契约测试照 [`model_gateway_contract`](../../crates/wonton-core/src/plugin/tests/model_gateway_contract/) 的样板，证明换提供方时使用方不用改：

- `mqtt` 的见 ADR-0092。
- 共享凭据：同一组使用方用例跑在两个假提供方上，一个按使用方签发凭据、一个是共享凭据。用例只用 `WONTON_<名字>_URL/_KEY`，
  断言两种提供方下使用方的 compose、变量名和请求写法完全一样，请求都能带 `X-Api-Key` 通过；再断言共享的那个在断开一个使用方后，
  其余使用方的 `_KEY` 换了新值、提供方的 `WONTON_PROVIDES_<名字>_KEY` 同步换了、断开的那个用旧 key 直连提供方被拒。
- 重建：假 Docker 下，提供方后装、换提供方、卸掉提供方、换 key 四种情况各断言重建了哪些服务，没引用变量的服务不重建；
  高权限能力没确认时一个容器都不动。

### 卸、停和升级

- 卸载提供方时，有使用方 `requires` 它、又没有别的提供方能接上，就拦下，错误列出这些插件，不给一键连卸。有别的提供方时，
  这些使用方改用默认的那个，确认页写明。只被 `wants` 的照卸，确认页写明哪些插件会用不上它。
  获准管理插件的家人不能借卸载确认新的高权限连接：必需使用方要接到未确认的高权限替代方时，在卸载前拒绝；
  可选使用方允许断开，但不自动授权新的高权限提供方。
- 卸载使用方后，有提供方再没有别的插件在用，问主人要不要一起卸，不自动卸。
  一起卸载的请求先按整批结束后仍存在的提供方检查必需依赖与连接确认；本批选中删除的插件不作为替代方，
  检查拒绝时不卸任何插件。替代连接需要重建使用方而重建失败时，保留其安装记录并标为异常，不继续显示运行中。
- 停止提供方不拦，确认页写明谁会受影响。
- 升级提供方时，新版本不再提供某个有人 `requires` 的能力、又没有别的提供方，拦下这次升级，说清是谁在用。
- 启动 `requires` 了某能力的插件时，它选用的提供方停着就先启动提供方。

### 运行时

- 使用方选用的提供方没在运行（停了、异常、记录读不懂）时，`requires` 它的插件标为异常，原因类别是“依赖的插件没有在
  运行”，带上提供方的名字；提供方恢复后核心重新核对，使用方回到运行中。只 `wants` 它的插件状态不变，详情页一条轻提示。
- 核心转发能力请求时，提供方不在运行返回 503，类别同上；没声明这个能力的插件访问它返回 403 `permission_denied`。
- 核心启动时先恢复提供方，再恢复使用方。
- 好友共享（ADR-0051）不另做规定：开放给好友的插件照旧经主人的核心访问它的提供方。

### 主人 API

以下路径都在 `/_wonton/api/` 下，修改操作沿用主人的鉴权和确认规则：

| 方法 | 路径 | 约定 |
| --- | --- | --- |
| GET | `capabilities` | 返回已装提供方、全局默认和受影响的使用方（`CapabilityProviderSettings`） |
| PUT | `capabilities/{capability}` | 以 `CapabilityDefaultChoice` 修改全局默认 |
| PUT | `plugins/{id}/capabilities` | 以 `ConsumerCapabilityChoice` 修改使用方的一项选择，可跟随默认 |
| GET | `plugins/{id}/uninstall/preview` | 返回 `UninstallPreview`，列出卸载后不再被使用的提供方；与卸载同样允许获准管理插件的家人 |
| DELETE | `plugins/{id}?purge=true` | `purge` 控制是否删除数据；可选 JSON 请求体 `UninstallRequest` 的 `providers` 列出主人确认一起卸载的提供方，不带请求体就只卸指定插件 |

## 理由

- 按能力依赖，提供方能换（换一个媒体服务器、一个模型网关）而使用方不改，这是 ADR-0015 的“经标准接口连接，每个组件都能
  单独替换”。按插件名依赖等于把两个插件焊在一起。
- 经核心转发而不是把两个插件放进同一个网络：插件之间照旧互相隔离，核心按来源认出是谁、留审计，几个提供方时按主人的
  选择转发，在提供方不在时给出分清原因的错误。`models.wonton.internal`、`mcp.wonton.internal`、
  `notify.wonton.internal` 已经是这种做法。
- 第三方能力名带前缀：社区插件之间也能互相依赖而不用等核心发版；前缀让它和核心定义的名字不撞，也让界面能标清来源。
- 一层依赖、不带版本是飞牛和 Umbrel 的简化：家用场景里依赖链很短，解依赖图和版本冲突的复杂度换不来什么。
- 数据库不做成能力：共享数据库把几个插件的升级、备份、权限绑在一起，TrueNAS 也是每个应用自带。
- 高权限能力按“连接”确认，不按“调用”：连上以后每个请求都确认，主人会被问烦，提供方自己（如 Agent 的工具确认）更清楚哪一步
  危险。按连接确认和手机的“允许某应用访问某数据”同一个粒度。第三方能力看提供方的权限，是因为核心读不懂它的接口，提供方有多
  大本事，连上它的使用方就可能借到多大本事。
- 共享凭据而不是核心替使用方加鉴权头：加头要核心知道每个上游的头名，Prowlarr 这类界面要求填 key 的应用还得填一个假的；
  共享凭据核心只管生成和注入，上游怎么用由插件映射，和 Home Assistant 给所有应用共用一个 Mosquitto 账号、Cloudron 由平台生成密钥同路。
- 连接变了自动重建（StartOS 依赖装上、卸掉、换地址时重启依赖方，升级不重启）：后装了 qBittorrent，Sonarr 自己就连上了，主人不用
  知道“要重启一下”。只重建变了的服务，复用渲染漂移，不另写一套依赖分析。
- 变量为空而不是填假地址（StartOS 的 “Absent means absent”）：没连上就是没连上，上游按没配置处理，不会拿一个连不通的地址报错。

## 代价与风险

- 核心定义的能力加一项要改核心、发版。第三方能力不用，但核心不保证两边的接口对得上，对不上时是使用方自己报错。
- 第三方能力只支持 HTTP；`tcp` 只给能力表里的能力（ADR-0092）。
- 共享凭据断开一个就要重启提供方和所有其余使用方，正在跑的任务（下载整理、字幕搜索）会断。
- 连接变了会自动重启使用方，正在进行的任务会断；主人不会被事先问到（高权限能力除外）。
- 不给一键连卸：被依赖的提供方要主人先一个个卸掉使用方，多点几下，换来不会误删数据。
- 高权限能力多出几次确认，主要在换提供方和提供方后装时；默认提供方被卸掉后跟默认走的使用方怎么接，也落在卸载确认页上。
  第三方能力按提供方判断会有误判：一个不危险的能力因为提供方有高权限而被醒目确认，多一次确认，不会少拦。

## 没选的做法

- **按插件名依赖**（飞牛、Synology）：见理由。
- **带版本约束**（Synology、Debian）：插件的接口靠能力名区分，版本约束只会多出装不上的组合。
- **使用方和提供方共用一个 Docker 网络**：省掉转发，但插件之间不再隔离，核心也看不到谁在用谁。
- **递归依赖**：提供方再依赖别的能力时要解依赖图、处理环，没有这样的需要。
- **同一能力只允许一个提供方**：主人想同时留两个（比如一个本地模型、一个云端模型）做不到。
- **高权限能力每次请求都确认**：见理由。
- **核心转发时替使用方加鉴权头**（*arr 的单把 key）：见理由。
- **共享凭据断开时不换 key**：少重启一次，但断开的插件手里留着一把还能用的 key，提供方开了局域网端口时它能绕过核心直连。
- **连接变了只在详情页提示，主人手动重启**：主人得知道“重启才能连上”这件事，和 StartOS 的自动处理比多一步，换不来什么。
- **读别的插件的数据目录拿 key、写死容器名**（Umbrel 的 Prowlarr）：把使用方绑在一个具体插件的内部布局上，换提供方就坏。
- **让插件作者给第三方能力自己标高不高**：作者说不危险，核心就放行，等于由使用方一侧决定提供方的风险。
