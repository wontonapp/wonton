# ADR-0059 多 Agent 团队作战：接入现成的编排器，每个做成一个插件

- 状态：已接受（2026-11-08）

## 背景

主人想在 App 里指挥一群 Agent 干活。并发 Agent 一多，瓶颈就到了人的验收和决定上，主人要的指标是：**每投入一分钟人的注意力，最终有多少工作通过验收**。

这篇的第一版打算自己写任务库、等人状态和工人池。主人（2026-11-07）改了方向：“接入各类这些的包括 comma 包括 dsh super agent，都分别作插件，
然后要和我们云吞适配的非常好”。先做 AO 和 Comma，SuperAgent 暂缓（见“暂缓的”）。现成的编排器已经有任务状态机、工人池、工作区隔离、问人和审批、CI 与 review 反馈：

| | Agent Orchestrator（AO） | Comma | DeepSeek SuperAgent 原型 |
|---|---|---|---|
| 许可证 | Apache-2.0 | AGPL-3.0 | MIT |
| 怎么跑 | 一个 Go 守护进程，只要 SQLite；实测无头跑通“派活—问人—审批—交付” | docker compose 9 个服务（Postgres、Redis、S3、ClickHouse、SMTP 等），要一台装 Connector 的机器跑 Agent | DeepSeek Harness（dsh）的一个扩展包，网页面板在本机端口；要一个专用的 GitHub 用户账号 |
| 对外接口 | REST + SSE，`user_input` 表单、审批都有 resolve 接口 | REST + SSE，要邮箱验证码登录的用户会话 | 从 GitHub、飞书“听”任务（Source），可以加 Source |
| 上游发布物 | 桌面安装包、Linux deb/AppImage、npm 启动器；没有容器镜像 | 没有镜像（compose 全部本地构建） | 只有源码；一次提交，研究原型 |

AO 的实测见调研报告（`research/orchestrator-probe.md`，2026-11-07）。

## 决策

### 1. 每个编排器是一个 Agent 插件，核心不为它做特殊处理

- 插件按 ADR-0035 的样子：`agent` 服务里跑编排器本身和它的工人，`bridge` 服务是标准的 ACP 桥，主控在云吞里就是这个插件的 Bot。
- 插件里多一层**适配器**：一端是编排器自己的接口，另一端对桥说 ACP。各插件只写这一层，下面第 2～6 节是三个插件共用的约定。
- 镜像用 Agent 底座（wonton-agent-base）：官方登录、模型网关、ACP 转发都是现成的。

### 2. 每个任务一个话题

- 编排器开了新任务，适配器发一条 ACP 扩展通知 `_wonton/task`（任务编号、标题、状态、对应的 ACP 会话 ID）。桥收到后在主对话里发一行
  “新任务「标题」”，以它为根开一个话题（ADR-0058），并对那个会话 `session/load`，之后这个任务的回复、工具调用都进这个话题。
- 主人在话题里说的话发给这个任务的会话（`session/prompt`），适配器转给编排器里负责它的工人（如 AO 的 `ao send`）。
- 状态变化（干活中、等你回答、等你审阅、受阻、失败、完成）也走 `_wonton/task`，桥更新工作板（ADR-0058）。
- 任务话题由编排器管并发和分工，ADR-0058 给人开的话题定的规矩不套在它们身上：不算进“最多 3 个活跃话题”，桥不注入“其他会话的动态”，
  不做改同一个文件时的排队。编排器的并发上限在插件设置里。

### 3. 问人和审批走确认卡片，卡片写明是哪个任务

- 编排器要批准（执行命令、改文件、开 PR）：适配器发 `session/request_permission`，桥照现在的做法转成核心的确认卡片（ADR-0024），
  卡片标题带任务名，如“「修登录页」想运行 git push”。编排器给的选项原样成为卡片按钮，推荐的排第一。
- 编排器问问题：有选项的（AO 的 `user_input` 表单、Comma 的 question block），每个问题一张卡片，选项就是按钮，再加一个“在话题里回答”；
  没选项的，在任务话题里发问题并提及主人。ACP 有了标准的表单请求后换成它。
- 只有要人行动的（等回答、等审阅、受阻、失败）推送；进度、CI 结果这类只进话题，不推送。

### 4. CI 和 review 的反馈回到对应的话题

- 盯 CI、review、合并冲突是编排器自己的活（AO 的 SCM 轮询、SuperAgent 的 GitHub Source），反馈由编排器交给负责的工人。
- 适配器把这些事件作为那个任务会话的消息发出，主人在话题里看得到“CI 红了，工人在修”“review 要改两处”，不用自己去 GitHub 翻。

### 5. 编排器自带的网页是插件的网页入口

- 编排器有看板或面板的，作为插件的 `webui`，经核心网关登录后打开（ADR-0033），聊天顶栏菜单和 Bot 资料页的“打开 <插件名>”也到这里（ADR-0060）。
- 编排器自己的接口多半不认证（AO 的 REST 在容器内 loopback、无鉴权；SuperAgent 的面板只听 127.0.0.1），只能在插件容器里访问，
  对外只经核心网关。

### 6. 工人用什么 Agent

- 第一步：工人跑在编排器的容器里，用编排器支持的 Agent CLI（Codex、Claude Code、Qwen 等），登录走 Agent 底座的官方登录或模型网关（ADR-0055）。
- 以后：用户已装的 Agent 插件当工人，经核心的 `agent_acp` 入口（ADR-0061 第 9 节）：编排器插件 `requires: [agent_acp]`、不提供它，
  连接代表在编排器里下目标的人，派活深度 1，并发和轮数有上限，卡片标题写“编排器任务 → 哪个 Bot → 想做什么”。

### 7. 安全

- 编排器和工人在插件容器里可以随意执行命令（AO、SuperAgent 都按“完全权限”跑工人），所以照 Agent 插件的规矩：不给 Docker socket，不给宿主 shell，
  只看得到自己的数据目录和工作区。
- GitHub 令牌是插件的密钥，由主人在安装时给，范围最小。
- **只认主人的指令**：自动从 issue 接活的编排器（SuperAgent、AO 的 tracker）默认关，或只认主人写的规则（谁发的、哪个仓库或标签）；
  陌生人的 issue、评论、网页只当数据。Bot 发的消息不算主人的指令。

### 8. 顺序和验收

1. **AO 先做**：实测最成熟、依赖最少。先做第 2、3 节在桥里的通用部分（`_wonton/task`、话题里 `session/load`、卡片带任务名），再做 AO 的适配器和插件。
2. AO 跑通后做 Comma，只写适配器。
3. **“适配得好”用实测说话**：每个插件合并前，在真实栈上从 App 里派一个活，走完“问人—批准—交付”（交付是 PR 或文件），录屏放进 PR。

## 镜像

三个编排器都没有上游官方镜像。按 AGENTS.md（主人 2026-11-07 放宽）：AO 装上游的 Linux 发布包或 npm 包，Comma 按上游 compose 从固定提交原样构建，
都不改源码、固定版本；Comma 是 AGPL，插件页写明源码地址。

## 暂缓的

**DeepSeek SuperAgent 原型**（主人 2026-11-07 定）：上游写明是研究原型、不是正式产品；仓库只有一次提交（2026-10-31），看不出有人维护；
还要主人另建一个专用的 GitHub 用户账号（不能用 GitHub App）。上游有了持续维护再看。

## 不写死宿主是 Linux

服务端以后可能也跑在 Mac 和 Windows 上。插件里不假设宿主的路径、systemd、宿主网络（`network_mode: host`），只用 Compose 和插件规范给的卷、网络、密钥。

## 考虑过的做法

- **自己写任务库、等人状态、工人池**（本篇第一版）：主人改成接现成的。第一版里从各家学来的设计（等人状态分类、默认只观察、按待审积压开工）
  由各编排器自己实现，不在云吞里再做一份。
- **编排器直接对 Matrix**（自己当 Matrix 客户端）：每家都要写一遍 Matrix、加密和卡片，确认卡片和话题的行为也会各不一样；走 ACP 桥只写一层适配器。
- **OpenAI Symphony**：只驱动 Codex，状态全在内存里，重启后全丢，输入只能经 issue 系统轮询。没选。
- **所有任务挤在主对话里**：几个任务的回复交错，看不出谁在问；每个任务一个话题，主对话只留一行。

## 代价与待验证项

- `_wonton/task` 是我们自己的 ACP 扩展，写进插件规范；别的编排器要按它实现适配器。
- AO 没有无 PR 的验收流（自动评审挂在 GitHub PR 上），云吞里不开 PR 的任务怎么验收要实测。
- Comma 要 9 个服务和邮箱验证码，家庭服务器上能不能跑得动、SMTP 怎么给，做插件前先实测。
- 每个编排器迭代都快，插件按版本固定，升级跟插件发版走。
