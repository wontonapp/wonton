# ADR-0094 聊天里附件和文字一起发：附件区预上传，全部传完才发第一条，一组事件带同一个分组标记

- 状态：已接受（2026-11-12）。多张图发成多条 `m.image`、文字挂在最后一条、上传中能点发送，由主人定
- 修订 [ADR-0020](0020-file-service.md)：设备上传的文件发进房间时，不再一个文件一条只有链接的消息

## 背景

照片选完立刻发，不带输入框里的字；文件逐个上传，每个传完各发一条只有 `wonton://file/<编号>` 的文字。主人发“三张图，哪张好看”，
房间里是三条图片加一条文字，Bot 当成四轮处理：Hermes 每个媒体事件单开一轮，忙时还会打断前一轮；ACP 桥根本不收图片。

两条路都是先传完再发事件，Bot 不会拿到还没传上去的文件；这一点改完以后也要守住。matrix-sdk 0.19.1 的发送队列一个房间串行：
传第一张、发第一条、再传第二张，所以多张图会在上传期间一条条冒出来，Bot 先拿到第一张。

## 决策

### 1. 附件区

- 照片多选，选好的照片和文件都先进输入框上方的附件区，每个附件一项，可以删掉。一个附件区最多 `ComposerViewModel::max_attachments` 个（10 个，
  Telegram 一组相册和 Element X 逐条发送的上限）。
- 进附件区就开始上传（学 Signal）：照片走 Matrix 的媒体上传，文件走自家的 tus（ADR-0020）。每项显示自己的进度，失败的标红，能重试或删掉。
- 输入框里的字和附件区的附件一起用一次发送发出。有文字或至少一个附件时能发；附件区里有失败的附件时不能发，先重试或删掉。
- 附件区和点了发送还没交出去的消息（第 3 节）都由客户端核心持有，存在这台服务器的作用域目录里，换房间、杀 App 再回来还在。
  壳只渲染 `ComposerViewModel`，照片的压缩和缩略图仍由壳做（和原来的 `ImageUpload` 一样）。
- 照片一律用标准的 `POST /_matrix/media/v3/upload` 上传，加密房间里先在本机加密（和 SDK 发图一样，每个文件一把随机密钥）。
  不用 `POST /_matrix/media/v1/create` 先占地址：接收方会拿到一个还没有内容的地址，最多等 20 秒后得到 `M_NOT_YET_UPLOADED`。

### 2. 一组映射成几条事件

| 附件区里有 | 发出去的事件，按顺序 | 主人的字放在 |
| --- | --- | --- |
| 只有字 | 一条 `m.text`，没有分组标记（和原来一样） | 正文 |
| 照片 | 每张一条 `m.image` | 最后一张的说明文字（`caption`） |
| 文件 | 一条 `m.text`：主人的字，空一行，每个文件一行链接 | 这条 `m.text` |
| 照片和文件 | 每张一条 `m.image`，最后一条是带全部链接的 `m.text` | 最后这条 `m.text`，照片都不带说明 |

规则只有一句：**主人的字在这一组的最后一条事件上**，回复关系（`m.in_reply_to`）也在这一条上。

- 说明文字用 Matrix v1.10 的媒体说明：`filename` 是文件名，`body` 是说明文字，两者不同时 `body` 就是说明。matrix-sdk 0.19.1 的
  `AttachmentConfig::caption` 就是这么填的。发的是纯文本，和发文字一样。
- 不用 MSC4274 图集（`dm.filament.gallery`）：提案还开着；SDK 要开 `unstable-msc4274`；Element Web 不显示；Hermes v0.22.7 整条丢掉，
  连文字也不给 Agent。各家都支持以后再换，换的时候只改核心里这一处映射。
- 文件消息的正文：

  ```text
  这是上个月的账单

  wonton://file/abcdefghijklmnopqrstuvwxy2
  wonton://file/bcdefghijklmnopqrstuvwxy23
  ```

  没有字时只有链接，一行一个，按附件区的顺序。不写文件名和大小：App 按编号画卡片，名字和大小从核心取（ADR-0020 的“链接”），
  写进正文会和卡片重复；Bot 经 `wonton__view_file` 或桥自己取。

### 3. 分组标记 `app.wonton.batch`

带附件的一次发送（哪怕只有一条事件）里，每条事件的内容都带同一个对象：

```json
"app.wonton.batch": {"v": 1, "id": "3f0c9a1e5b7d42c6a8e1f0b2c4d6e8a0", "index": 0, "count": 3}
```

- `v`：结构版本，现在是 `1`。不认识的版本当没有标记。
- `id`：这一组的标识，128 位随机数的 32 个小写十六进制字符；在同一发送者里唯一，接收方按（房间、发送者、`id`）认组。
- `index`：这条在组里的位置，从 0 开始，就是第 2 节表里的顺序。
- `count`：这一组一共几条事件，1 到 32；文件消息也算一条。
- 不合规则的（`index` 不小于 `count`、`count` 超范围、`id` 不是 32 个十六进制字符）当没有标记，按单独一条处理。
- 标记放在事件内容的顶层（matrix-sdk 的 `extra_content`），加密房间里随内容一起加密。别的客户端不认识这个键，照常一条条显示。
- 只有纯文字的消息不带标记：没有要收齐的东西。

标记的格式、校验和文件消息的正文由 `wonton-protocol` 的 `MessageGroup` 和 `files_message_body` 生成和解析，发送端和接收端（App、ACP 桥）
用同一份代码，有契约测试。

### 4. 发送：全部传完、授权完才发第一条

主人点发送后：

1. 输入框的字、回复对象和附件区的附件一起变成一条待发消息（`ComposerViewModel::outgoing`），附件区和草稿清空。
   它马上出现在时间线最后，每个附件带进度环，整体状态用 `SendState`：`Sending { progress }` 是全部附件合起来的比例。
2. 核心等这一条的附件全部传完。断网时附件暂停（`AttachmentState::Paused`），连上后接着传，消息仍是 `Sending`；
   有附件失败，整条变成 `SendState::Failed { recoverable: false }`（红色），能重试（只重传失败的附件）或取消（整条不发）。
   从待发消息里的单个失败附件点重新上传，也恢复这条消息的发送；其他失败附件仍须处理，全部就绪才继续，不需要再点一次整条重发。
   重复点击不重复启动上传，已经上传完成的附件不重传，后面的消息不越过这一条。
3. 有文件时，把每个文件授权给这个房间（`POST /_wonton/files/{id}/grants`）。授权失败同上，整条标红。
4. 这一组的事件按顺序一次全部交给 matrix-sdk 的发送队列（几毫秒内），待发消息随之换成 SDK 的本地回显。
   之后每条事件照 SDK 发送队列的规矩（ADR-0005）：可恢复的失败自动重发，不可恢复的停在队首等主人重发或取消。

- **Bot 不会收到文件还不在的消息**：事件里引用的照片都已经传上去，文件都已经传完并授权给了房间里的 Bot。
- 同一房间的待发消息按点发送的顺序交出：后点的（哪怕只有字）排在前面没交出的后面，前面那条失败时也等着，直到它发出或取消，
  和 SDK 发送队列一样。只有字、前面没有待发消息时直接交给发送队列。
- 杀 App 后重启：附件区和待发消息从磁盘读回，照片从头重传（Matrix 的上传不能续传），文件按 tus 续传，传完接着发。
- 照片传完到点发送之间房间开了加密的话，发送前用加密重新上传那张照片，不把明文媒体放进加密房间。
- 删掉附件、取消待发消息时，已经传上去的照片留在服务器上（Matrix 没有删媒体的客户端接口），文件按 ADR-0020 的规则 24 小时后清掉。
- 自己发的照片交给发送队列时，原图和缩略图按上传后的地址放进本机的媒体缓存，时间线不用再下载一遍。

### 5. 接收方怎么收齐一组

**ACP 桥（以及其他把一组当一轮的 Bot）：**

- 带合法标记的事件按（房间、发送者、`id`）收集，同一个 `index` 只收第一条（重复投递按事件 ID 去重）。`0..count` 都到了才开一轮，按 `index` 排序：
  照片和文件是这一轮的附件，最后一条的说明文字或正文是这一轮的文字。
- 不带标记的事件照旧一条一轮（别的客户端发的；要不要另加静默窗口是桥自己的事）。
- 收齐的一组始终是一个整体，不拆开。Agent 空闲时开一轮；正忙时和任何一条消息一样：Agent 支持 steer 就马上 steer 进正在跑的这一轮
  （照片在 steer 带得了时一起带上）；不支持就由桥和这一轮里陆续到的别的消息攒在一起，这一轮结束时作为一条交出。App 不显示排队、打断之类的状态，只有 Agent 的已读回执。
- 收不齐时：从这一组最后到的一条算起 120 秒还没到齐，就用已经到的开一轮，并在文字里写明“这一组 N 条只收到 K 条”，同时在房间里发一条
  `m.notice` 告诉主人。
  发送端交出去以后事件是连着发的，120 秒还没到齐说明有一条停在了发送端（失败了等主人处理，或者被主人取消了）。
  之后再到的同 `id` 的事件按单独一条处理，不再等；桥记住处理过的 `id` 一小时。
- 桥重启不丢收到一半的组：处理过的 `id` 存盘（保留一小时）。启动后往回读每个房间最近一小时的时间线，带标记、`id` 不在处理过的记录里的事件
  按上面的规则重新收集；之后同步来的同组事件接着收。120 秒按服务器时间从这一组最后到的一条算起，重启期间已经超过的，读回来就按收不齐处理。
  不另存一份收到一半的组：事件本来就在服务器的时间线上，另存一份还得和它对账。
- 下载照片或文件失败、类型不支持：按类别回主人，不开残缺的一轮。
- 给 ACP 的内容：文字是 text 块；照片在 Agent 声明了 `promptCapabilities.image` 时给 image 块，否则下载到工作区给 `resource_link`；
  `wonton://file` 链接下载到工作区给 `resource_link`。桥怎么下载 `wonton://file`（要的权限、和文件服务授权的关系）由聊天线另行设计，不在本 ADR。

**App：** 不等，到一条显示一条。`TimelineMessage::group` 给出标记，壳把同一发送者、同一组、挨着的几条画在一起，说明文字画在最后一张下面
（`ImageContent::caption`）。

**Hermes（v0.22.7）：** 单张照片加一句话是一个事件、一轮，读得到说明文字。多张照片仍可能拆成几轮再合并（每个媒体事件单开一轮、忙时打断），
作为底座问题记录，不改上游。

## 考虑过的做法

- **一条 MSC4274 图集**：见第 2 节，接收方普遍不支持。
- **文字单独发一条 `m.text`，放在照片后面**：Bot 要靠时间窗口配对，Hermes 会把它当成新的一轮；Matrix 的媒体说明正是为这件事定的。
- **说明文字挂在第一张上**（Element X 的逐条模式）：收齐一组之前就能读到文字的 Bot 会先开一轮；放最后一条时，读到文字时照片都已经到了。
- **用 SDK 发送队列自己的上传**：一个房间串行“传一张、发一条”，满足不了“全部传完才发第一条”；而且上传期间整个房间的队列被占着。
- **上传中不让点发送**（Vercel chatbot、LibreChat）：实现简单，大文件要干等，主人定了能点。
- **先占 mxc 地址再补内容**（`/media/v1/create`）：正好会让 Bot 拿到还没有内容的文件，不用。

## 代价与待验证项

- 预上传和待发消息要核心自己存盘、自己加密上传，不再全交给 SDK 发送队列；照片在交出去之前存着一份在 App 目录里，交出后删掉。
- 删掉的附件、取消的消息，已传的照片留在服务器上，主人看不到也删不掉，占家里服务器的磁盘。
- 交给发送队列以后，主人取消其中一条会让这一组永远收不齐，Bot 要等 120 秒才开一轮。
- Hermes 多图拆轮只按代码推断，没在真实房间里测过。
- 加密房间里自己加密上传的照片、本地媒体缓存放对地址，要用真实 Tuwunel 测（`crates/wonton-matrix/tests/tuwunel`）。
