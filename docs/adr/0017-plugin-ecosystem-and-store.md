# ADR-0017 插件生态：独立仓库、商店和来源

- 状态：已接受（2026-10-30）。“App 只按来源安装”“没有降级”和 `Local` 的标签已被 [ADR-0031](0031-plugin-sources.md) 取代；“谁能装”里 Bot 的部分和小程序 JS SDK 已被 [ADR-0033](0033-plugin-tabs.md) 取代；导入 CasaOS 已撤销（主人 2026-11-04 定）；挑语言的规则已被 [ADR-0043](0043-app-languages.md) 取代；“一个插件一个 Git 仓库”已被 [ADR-0079](0079-agent-plugins-monorepo.md) 修改：插件包也可以是仓库里的一个子目录

## 背景

M1 第 4 项是插件商店：官方目录至少有 Immich、Navidrome、Paperless-ngx、Ollama、Syncthing、Samba，
安装前确认权限，插件网页在 App 里打开。主人 2026-10-30 定的方向：

- 插件系统是为了解耦。插件代码不放主仓库，每个插件一个独立仓库，相当于外部开发者写的，做插件不需要改主仓库。
- 发现机制参考 magpie 的 Extend / Plugins / Discover：按 GitHub 仓库的 topic 发现社区插件，和审核过的官方列表分开，显示为
  “未审核”。
- 设计要现代、美观，接口能满足自定义需求：插件列表像应用商店，插件声明自己的图标，列表和详情页都显示。

此前的安装接口只收上传的插件包；Bot 能装的插件目录是只有开发镜像才带的本地目录（`WONTON_CATALOG`，ADR-0016）；预装的
magpie 的插件包在主仓库里；App 里没有插件列表，“模型设置”的网页只有调试构建能打开。

magpie 的做法（`internal/plugin` 的 `github.go`、`market.go`、`dist.go`，MIT，只读参考）：search API 按 topic 找仓库，
按星数排序，排除 archived 和 fork；结果缓存 10 分钟并落盘；GitHub 不通时给上次的结果并说明原因，从不把取失败当成“没有”；
审核过的市场列表另放一个仓库，最多 6 小时取一次，上次成功取到的存在磁盘上；图标来自插件自己的声明；“国内镜像”开关只用
逐字节相同的副本（jsDelivr），不用会改写内容的代理。

## 决策

### 插件仓库和版本

- 一个插件一个 Git 仓库，仓库根目录就是插件包（已被 ADR-0079 修改：也可以是仓库里的一个子目录，来源带子目录，tag 为 `<子目录>/v<版本>`）：`docker-compose.yml` 加它引用的文件（插件规范的“插件包”）。仓库里的其他
  文件（README、没有被 `notices` 引用的 LICENSE、Dockerfile、源码、测试脚本）核心不取。
- 发布就是打 tag `v<版本>`，`<版本>` 是这个提交里清单的 `version`（语义化版本）。核心取包时核对两者一致，不一致拒绝。带
  预发布后缀的版本（`v1.2.0-beta.1`）可以按 tag 明确安装，不进商店，也不作为升级提示。
- 插件自己的镜像由作者构建并推到镜像仓库，compose 按摘要引用；核心不构建镜像（`build` 不在 Compose 子集里）。

### 商店信息

商店展示的信息写在清单（`x-wonton`）里，随插件包一起按提交固定：图标、截图、作者、主页、许可证、标签（插件自己声明，不固定）、
标签、详细介绍、更新说明，文字至少有中文和英文。字段、格式和上限见插件规范的“商店信息”。清单加一个 `spec` 字段写它按
哪一版规范写成；核心遇到比自己新的版本，明确提示先升级核心，不再只报“未知字段”。

截图不算插件包的一部分：不参与插件包摘要，安装时不取，核心镜像也不内置。商店的详情页要显示时，核心按同一个提交去取。
截图只在挑插件时有用，放进插件包会让每次安装和内置的那份都大好几倍。

### 图标和截图

- 图标是插件包里的 PNG 或 SVG，正方形，满幅，不留透明边，不自己画圆角：App 统一裁成圆角方形，重要内容放在中间 80% 里。
  官方索引要求必须有；社区插件没有时 App 画一个占位图标。
- 不再支持 HTTPS 地址的图标：图标随提交固定，App 不向第三方发请求，国内的主机取不到外网图片也不受影响。
- 核心统一处理后才交给 App：PNG 解码后缩放，SVG 用 resvg 渲染（不加载外部资源，不渲染文字），图标输出 192×192 和
  512×512 的 PNG；截图缩到长边不超过 1280 的 JPEG。输出重新编码，不带原文件的元数据。App 只收到核心编码的位图，收不到
  SVG，也不在 WebView 里显示插件给的图片。
- 处理不可信输入有上限：文件大小（见插件规范）、解码后不超过 4096×4096 像素。解码和渲染放在单独的进程里，限内存和
  时间，超出的按处理不了：渲染器费时费内存的写法挡不完，预检只用来给作者清楚的报错。
- 图片的地址由核心给出，按原文件的 sha256（或它所在的提交和路径）和输出规格生成：同一个地址的内容不变，App 可以一直
  缓存。核心只给它列出的插件的图片，不替任意地址取图。

### 来源与取包

- 安装来源写成 `github:<owner>/<repo>@<tag>`。省略 `@<tag>` 时取最新的正式版本；开发时也可以写 40 位的提交号。
- 解析：经 `https://github.com/<owner>/<repo>.git` 的 git 协议 v2 `ls-refs` 把 tag 解析成提交（注解 tag 取它指向的提交）。
  之后一律按提交取，tag 后来被移动或删除也不影响这一次。
- 取包：先取这个提交的 `docker-compose.yml`，再按清单逐个取它引用的文件，大小上限同上传的插件包。取到后和上传的包走同一套
  解析和校验。
- 每次请求（含正文）限 30 秒，连接阶段限 5 秒，由 HTTP 客户端在解析到的地址间分配；保留连接复用。固定提交的文件遇到超时最多重取
  一次，丢弃未读完的内容后从头取，不重取 tag、`HEAD`、任意索引地址，也不重试 HTTP 拒绝、大小或摘要错误。总共最多两次、每次仍限 30 秒。
  原因：国内直连实测既有首个 IPv4 建连停住、也有连上后首字节或正文停住，不能只延长总时限或强制 IPv4。超时仍用 `source_unavailable`，详情注明超时。
- 插件包摘要：插件包每个文件的 sha256 按路径排序列成清单（格式同 `sha256sum` 的输出），清单本身的 sha256 就是摘要，写成
  `sha256:<十六进制>`。它和文件从哪里取、怎么打包无关。预览给出摘要，安装请求带回同一个摘要，对不上就拒绝：主人确认的就是
  装上的，和 ADR-0016 的确认卡片一样。
- 安装记录写下来源、tag、提交、信任级别和插件包。

### 镜像的固定

- 官方索引里的插件，所有服务的 `image` 都按摘要写（`名字:标签@sha256:…`，多架构镜像写清单列表的摘要），收录时检查。
- 社区插件和上传的插件包可以只写标签。预览如实提示“镜像没有按摘要固定”。标签之后可能被作者移动：重建容器用本地已有的镜像，不重新拉；升级失败回滚时用旧容器
  当时的镜像。这样，下一次升级之前，跑的始终是主人确认时的那个镜像，除非主人自己删了本地镜像。

### 官方索引

- 一个公开仓库 `wontonapp/wonton-store` 里的 `index.json`。每个插件一项：来源、版本、提交、插件包每个文件的 sha256，加上
  compose 原文。商店列表和 Bot 的搜索直接用索引里的清单，不用逐个去取。格式见插件规范的“官方索引”。
- 收录就是向这个仓库提 PR，审核后合并。条目由 `wonton-core plugin index-entry github:<owner>/<repo>@<tag>` 生成，不手写。
  审核看这些：`wonton-core plugin check --official` 通过（图标、标签、许可证、作者、随包的许可声明齐全，镜像全按摘要固定，长期运行的服务
  都有健康检查）；申请的权限和插件做的事相符；镜像来自上游官方或作者可复现的构建。
- 一个插件只收录一个版本，即最新审核过的；升级就是改这一项。
- 在线更新：6 小时一次，App 刷新时立即更新，一分钟内不重复。索引只从 GitHub 取：先 `raw.githubusercontent.com`，不通时
  `api.github.com`，都走 TLS。取不到时用磁盘上次成功的那份，并如实说明列表是什么时候的、为什么没更新。核心不内置索引：内置的只会过期误导。
- 开发镜像和冒烟测试用本地的索引目录代替官方索引（`WONTON_STORE_INDEX`，格式同官方索引），取代 ADR-0016 的
  `WONTON_CATALOG`。主人可以关掉社区插件（`WONTON_STORE_COMMUNITY=off`），商店里就只有官方插件。
- M1 不给索引签名，信任靠 GitHub 账号和 TLS。插件包的文件按索引里的 sha256 核对，所以可以从任何地方取。以后加上索引签名
  （minisign），索引本身也能经镜像和国内的静态托管分发，即 ADR-0012 说的“签名静态文件”。

### 社区插件

- 社区插件指 GitHub 上打了 topic `wonton-plugin`、有 `v<语义化版本>` tag 的公开仓库。发现照 magpie 的做法：search API 查
  `topic:wonton-plugin archived:false fork:false`，按星数排序，翻页，最多 1000 个。官方索引里的仓库，以及插件 ID 和官方插件
  相同的仓库，都不列出：同 ID 的未审核插件容易被当成官方的。
- 官方索引里的仓库不读：它们的版本和清单索引里都有，列商店不为它们多发请求。其余每个仓库取最新的正式版本 tag（`ls-refs`）和那个提交的 `docker-compose.yml`，解析出商店信息；没有 tag 或清单解析不了的不列出，
  日志里记下原因。按 `仓库@pushed_at` 缓存，仓库没有新推送就不重读。
- 缓存 10 分钟，新打 tag 的仓库几分钟内就能出现。结果落盘，核心重启后 10 分钟内直接用。GitHub 不通时给上次的结果并说明原因，
  一分钟后再试。有仓库没读到时如实标出列表不完整。
- 限速：不带令牌时，search API 每个出口 IP 每分钟 10 次，其他 API 每小时 60 次。发现每 10 分钟最多一轮搜索（通常一页）；读
  tag 走 git 协议，读文件走 `raw.githubusercontent.com`，都不计入 API 额度，只有 raw 不通时才退到 contents API。核心不保存
  GitHub 令牌。

### 升级

- 发现新版本：官方插件看官方索引里的版本；社区插件看仓库最新的正式版本 tag。每 6 小时检查一次，主人打开商店或已安装列表时
  也检查，受同样的缓存约束。主人手动刷新商店和打开升级预览时不等缓存过期，连官方索引一起重新取，一分钟内不重复；这次没取到
  就如实报没取到，不拿上次的索引说“没有新版本”。上传的插件包没有来源，不检查。
- 按 tag 从 GitHub 装的社区插件，官方索引后来收录了同一个仓库的同一个提交：检查新版本时认成官方，不用主人重装。提交一样，
  装着的就是审核过的那份。提交对不上的保持社区，主人升级到官方索引里的版本才换过来。
- 提示：已安装列表里给出能升级到的版本、更新说明（清单的 `release_notes`），以及权限有没有变。App 显示角标。M1 不另发消息，
  以后在“Wonton”私聊里发（ADR-0016）。
- 一键更新（2026-11-09 定）：商店列表和详情页的“获取”“更新”点了就开始，不跳页；只有要主人拿主意的才弹出确认页。核心取
  预览、判断要不要请主人拿主意，规则在核心写成测试：装不了、缺资料、要用设备、有核心不支持的权限；安装时有带风险等级的
  权限或标了重点的提醒（内存、架构、自动登录这类说明不拦）；更新时新增了权限，或者这个插件有 Bot 开了“始终允许”
  （ADR-0024 规定这种不能静默升级）。核心判完把要确认的放进 `PluginsViewModel.confirmation`，壳照着打开确认页。
- 商店页右上角的更新图标带着可更新数，点了弹一次确认（列出这些应用），然后逐个升级：不用拿主意的直接开始，要拿主意的排进
  确认页，一次一条。侧边栏“应用商店”的角标是同一个数。
- 升级要主人拿主意时，和安装用同一个确认页：列出新版本的全部权限，新增的标出来，高权限照样醒目；新版本多申请了权限，就要
  重新确认全部权限。
- 执行：保留数据、密钥、Bot 账号和设备（不换加密身份）、模型凭据和 OIDC 客户端，只换容器。新版本健康检查不过就回滚，按旧
  记录和旧容器当时的镜像重建旧版本的容器。没有降级，回滚只发生在这次升级失败时。（“没有降级”已被 ADR-0031 取代。）
- 数据迁移由应用自己负责。迁移做到一半才失败时，旧版本可能读不了新数据；插件作者要在更新说明里写明这类风险。升级前备份的
  钩子是插件规范的待定问题。
- tag 被改写（同一个版本号指向了别的提交）不当作升级，已安装列表里如实提示。
- M1 不做自动升级。以后可以给“官方插件、权限没变”的升级打开自动（ADR-0012）。
- 系统插件（magpie，见插件规范的“预装插件”）随核心镜像发版：镜像里的版本比装着的新时，核心启动后按同样的步骤升级它，装核心
  就是对它的确认，和预装一样。
- 默认插件（Hermes）只在第一次从核心镜像里的默认插件目录装。之后和别的官方插件一样，由官方索引提示升级、主人确认，核心不随
  镜像升级它；主人卸掉了不装回来。

### 信任和权限

- 插件分四种来源（已被 ADR-0031 取代），商店、预览和已安装列表里都标出来：官方（官方索引里审核过的版本，按摘要核对；App 上写“已审核”，写“官方”放在上游标志旁边，像对方出品）、社区（未审核）、本地
  （主人上传的插件包）、系统（随核心预装）。
- 社区插件的预览里加一行醒目的提示：云吞没有审核过这个插件，代码和镜像由它的作者提供。权限规则和官方插件一样，不额外放宽，
  也不收紧。
- 谁能装：主人在 App 里能装官方、社区和本地插件；Bot 能装什么见 ADR-0033 的“确认”。系统插件（`kind: system`）只能随核心预装，哪种来源都装不了。
- 管理接口（已安装列表、商店、详情、预览、安装、升级、卸载、图片）接受主人经隧道的已配对设备和主人令牌。设备身份随
  隧道上的每个请求自动带上，App 的 WebView 里打开的插件网页发的请求也带着它，所以经隧道的请求还要不是网页发起的：
  `Sec-Fetch-Site` 不是 `same-origin` 或 `none` 的、`Origin` 不是核心地址的，一律拒绝，读也拒绝（插件网页不能拿商店
  刷新消耗限速，也不能探测装了哪些插件）。客户端核心的请求不带这两个头。接口都不带 CORS 头，跨站的修改另外还被拦下
  （ADR-0011）。浏览器只对 https 和 `localhost` 发 `Sec-Fetch-Site`；自定义域名走 http 时，跨站的 no-cors GET（`<img>`、
  `<script>`）两个头都不带，和客户端核心分不开。这种环境下插件网页读不到响应，但能触发商店刷新，也能凭加载成败探测装了
  哪些插件；修改不受影响，因为 POST、DELETE 浏览器总会带 `Origin`。

### 国内的主机

- 离线可用：核心镜像带着官方索引和官方插件包，连不上 GitHub 时商店照常列出官方插件，也照常安装。镜像仍要从镜像仓库拉，
  它们按摘要固定，Docker 的镜像加速和代理照常起作用。
- 官方插件包的文件按 sha256 核对。GitHub 不通时，依次从 jsDelivr（`cdn.jsdelivr.net/gh/<owner>/<repo>@<提交>/<路径>`）和主人
  配置的镜像取。
- 社区插件必须连得上 GitHub：它们没有可信的摘要，只认和 GitHub 之间的 TLS 连接。主人可以配 HTTP(S) 代理（ADR-0023，
  核心和出网插件用同一个地址）：TLS 端到端，代理改不了内容。不用那些改写地址的“GitHub 加速”服务，它们能返回任意内容。
- 超时和错误类别按“来源与取包”和“接口”处理；连不上时主人可以配置出网代理，不改变宿主 DNS、Docker 网络或地址族偏好。

### 开发期

- 私有仓库搜不到，核心也取不到（核心不存 GitHub 令牌）。开发时从本地目录安装：开发工具把目录打成 tar 上传，用的是原有的
  安装接口。要装某个私有仓库的某个 tag，开发工具在开发者的机器上用开发者自己的 git 凭据导出插件包再上传。这样装上的都算
  本地来源，不检查升级。
- 仓库公开、打上 topic 和 tag 以后，就能从 `github:` 来源安装，也会出现在社区列表里。
- 开发套件是公开的模板仓库 `wontonapp/wonton-plugin-template`，不需要主仓库：
  - 校验：发布的核心镜像带 `wonton-core plugin check <目录>`，和安装时同一套解析和校验，再加上商店信息的检查，并输出插件包
    摘要；`--official` 按官方索引的要求检查。
  - 开发环境：用发布的核心镜像在本机起一套核心、身份提供方和 Matrix 服务器，和正式安装是同一份 compose。数据放在插件目录
    下，端口和项目名可以改，不装进系统，不要 root。
  - 几个人共用一台 Docker 主机：核心的资源名和标签都带上实例名（`WONTON_INSTANCE`），几套核心各管各的插件，同一个插件
    也能在几套核心里同时装。正式安装不设实例名。
  - 发布：本地脚本检查、打 tag、推送；插件带自己的镜像时，在本地构建多架构镜像推上去，再把摘要写回 compose。发布要不要改用 CI 见 #126。

### 预装插件

- magpie 和 Hermes 也移出主仓库，各用一个插件仓库，和别的插件一样发版。
- 主仓库只留锁文件，写明每个预装插件的来源、版本、提交和插件包摘要，系统插件和默认插件两个目录都由它管。构建核心镜像时，
  用刚编译出的 `wonton-core` 按锁文件取包、核对摘要，放进镜像（`WONTON_SYSTEM_PLUGINS`、`WONTON_DEFAULT_PLUGINS`）。
  这样首次启动离线也能装，它们的镜像仍要拉。

## 接口：App 和核心（M1）

类型在 `crates/wonton-protocol` 的 `plugin` 模块：核心的管理接口收发这些类型，客户端核心把它们放进 `PluginsViewModel`
交给壳。字段的含义写在类型的文档注释里。

**管理接口**：都在 `<核心地址>/_wonton/api/` 下，接受主人经隧道的已配对设备（不能是网页发起的，见“信任和权限”）和主人
令牌（`Authorization: Bearer`）。错误同其他管理接口：`{"error": {"kind": …, "message": …}}`，另带 `X-Wonton-Error` 头。

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| GET | `plugins` | — | `InstalledPlugins` |
| GET | `plugins/{id}` | — | `PluginDetail`（装着的版本） |
| GET | `store` | 可选 `?refresh=true`：不等缓存过期，直接去来源取 | `StoreListing` |
| GET | `store/plugin?source=<来源>` | — | `PluginDetail`（来源最新的版本） |
| POST | `plugins/preview` | `InstallSource`（JSON），或者插件包 | `InstallPreview` |
| POST | `plugins` | `InstallRequest`（JSON），或者插件包加 `?grant=` | 201 `InstalledPlugin` |
| POST | `plugins/{id}/upgrade/preview` | 空（升到提示的版本），或者插件包 | `InstallPreview` |
| POST | `plugins/{id}/upgrade` | `UpgradeRequest`（JSON），或者插件包加 `?grant=` | `InstalledPlugin` |
| GET | `plugins/{id}/settings` | — | `PluginSettingsView`（ADR-0077） |
| POST | `plugins/{id}/settings/preview` | `PluginSettingsUpdate` | `PluginSettingsView`（只校验） |
| PUT | `plugins/{id}/settings` | `PluginSettingsUpdate` | `PluginSettingsView`（保存并重建） |
| DELETE | `plugins/{id}?purge=true` | — | 卸载报告 |
| GET | `PluginImage.path` 给出的地址 | — | `image/png` 或 `image/jpeg`，可以一直缓存 |
| GET | `storage` | — | `StorageUsage`（存数据的那块盘） |

- 插件包同原有的接口：compose 文本，或者插件包目录的 tar（`Content-Type: application/x-tar`）。JSON 请求的
  `Content-Type` 是 `application/json`。App 上传压缩包见 ADR-0031。
- 文字按请求的 `Accept-Language` 挑语言。~~先找完全一样的语言标签，再找主语言相同的，都没有时用英文，再没有就用任意一种。~~挑法已被 [ADR-0043](0043-app-languages.md) 取代：按可能子标签补全文字系统后协商。
- 新的错误类别：`source_unavailable`（503，家里的服务器连不上插件的来源，如 GitHub）、`not_found`（404，来源里没有这个
  仓库或版本）、`changed`（409，插件包在预览之后变了，摘要对不上，要重新预览）、`images_unavailable`（503，核心起不了
  处理图片的进程；图片本身处理不了是 `invalid_input`）。原有的类别照旧（`invalid_input`、`permission_denied`、
  `unsupported`、`conflict`、`not_installed` 等）。设置另有 `settings_schema_invalid`（包的 Schema 不合格）和
  `settings_invalid`（值过不了 Schema），见 [ADR-0077](0077-plugin-settings.md)。
- 安装、升级和卸载在核心里单独执行：请求断开了也照样做完，结果体现在已安装列表里。

**客户端核心**（`ClientCore`）：

- 状态：`subscribe_plugins()` 推 `PluginsViewModel`：已安装的插件、商店、最近一次取列表的问题，以及安装、升级、卸载的
  进展（`tasks`）、可更新的应用（`updatable`）、侧边栏的内容（`sidebar`），以及一键装、一键升的进展
  （`pending`）和要主人拿主意的确认（`confirmation`）。
- 操作：`SetLanguages`（壳把系统的语言偏好告诉核心，核心据此带 `Accept-Language`）、`RefreshPlugins`、
  `RefreshStore { force }`、`InstallPlugin { preview, secrets, settings }`、`UpgradePlugin { preview, secrets, settings }`、`UninstallPlugin`、
  `DismissPluginTask`，以及一键装、一键升：`InstallNow { source }`、`UpgradeNow { plugin_id }`、`UpgradeAll`、
  `DismissStoreConfirmation`。安装和升级把确认页渲染的那份预览原样交回，核心按它授予列出的全部权限：确认页上看到的
  就是授予的，壳不用自己拼权限列表。
- 直接返回结果的调用：`store_plugin(source)`、`installed_plugin(id)`（详情页）、`plugin_detail(route)`（详情页：
  插件还在时给 `PluginDetail`，已经卸掉时给 `Close` 让壳关掉这一页）、`plugin_detail_after_task(route)`（详情页上的
  任务做完后重取；卸载确定做成了直接给 `Close`，失败或等不到结果时由重取认出“没装”再关）、`preview_install(source)`、
  `preview_upgrade(id)`（确认页）、`plugin_settings(id)`、`preview_plugin_settings(id, update)`、`set_plugin_settings(id, update)`（ADR-0077）、`load_plugin_image(image)`（经隧道取图片并缓存，返回 PNG 或 JPEG 的字节，同
  `load_media`）、`search_store(query)`（在取到的商店列表里按名字、说明、标签和 ID 找）。
- 失败的原因（`PluginFailure`）按核心的错误类别区分，壳据此提示下一步：连不上家里的服务器、本设备不被认、家里的服务器
  连不上来源、来源里没有、插件包变了、核心不支持（权限、架构、规范版本）、冲突（已经装了或正在装）、插件包不合法、
  家里的服务器上出错、选不出局域网地址（ADR-0019）、两端版本对不上。
- 核心可能比 App 新：枚举遇到不认识的取值时落到 `Other` 或 `Unknown`，多出来的字段被忽略，整份列表照样能显示。

## 理由

- 一个插件一个仓库、仓库根目录就是插件包：插件作者只用模板仓库，主仓库不随插件改动；发现时只读一个固定路径的文件。
- 内容寻址（按 sha256 取文件、按提交取包、按摘要拉镜像）：文件从哪里取可以换（GitHub、jsDelivr、以后的国内
  镜像），装上的东西不变。国内和离线的问题于是只剩“去哪里取”。
- 官方和社区分开：和 magpie 一样，审核过的列表单独一份，没审核的照实标出来。
- 图标由核心统一转成位图：App 两端只处理 PNG，看上去一致；SVG 只在核心里渲染一次，不执行脚本，也不取外部资源。

## 代价与风险

- 官方索引不签名：GitHub 账号被盗或 TLS 被劫持时，索引可能被换掉；靠插件包摘要和主人的权限确认兜底，签名以后补上。
- 依赖 GitHub：社区插件的发现和安装都离不开它；连不上 GitHub 的国内主机上，只有已装的插件和预装插件稳定可用；官方列表只能显示磁盘上次取到的。
- 核心多了 SVG 渲染和图片解码，处理的是不可信输入：靠大小和像素上限，再放进限了内存和时间的子进程里（子进程由一个常驻助手起，见 [ADR-0075](0075-image-helper-process.md)）；resvg 不执行
  脚本、不取外部资源。子进程只限资源，不是沙箱：它和核心是同一个用户，解码器的内存安全漏洞仍会波及核心的数据。
- 上游的 tag 可以改写，仓库可以删除：已安装的插件按提交记录，镜像在本地，不受影响；但仓库删掉以后就重装不了。

## 没选的方案

- 一个仓库放多个插件：发现按仓库计，一个仓库一个插件最简单。以后需要时可以加 `github:<owner>/<repo>/<路径>@<tag>`。
- 下载 GitHub 生成的源码归档：会带上整个仓库（源码、测试），大小不可控；归档的字节也不保证不变，GitHub 2023 年 1 月升级
  git 后归档的校验和变了，依赖它的很多构建因此失败（后来回退）。按文件取，只取插件包要的。
- 官方索引只放指针、不放 compose：商店列表和 Bot 的搜索就要逐个去取每个插件的 compose。
- 社区插件也必须按摘要固定镜像：最安全，但多数现成的 compose 都只写标签。安装时记下摘要，已经能保证
  跑的就是确认的。
- 图标用 URL 或 data URI（magpie 的做法）：magpie 的插件是 npm 包，包里的文件不好单独取；我们的插件包本来就能带文件。
- 开发环境用 Docker-in-Docker：完全隔离，但要特权容器，镜像要在每个环境里重新拉（国内慢），磁盘占用翻倍。
