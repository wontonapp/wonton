# ADR-0025 核心一键升级：升级器容器、状态文件和回滚

- 状态：已接受（2026-11-03）

## 背景

ADR-0012 定了“核心拉起一次性的升级器容器，失败回滚”，没定这几件事：升级器用什么镜像、改哪些东西、核心断开期间状态记在哪、
中途断电或者卡住怎么办、怎么知道渠道上有新版本。核心容器不能替换自己：`compose up` 一停掉它，做到一半的事就没人接着做了。

## 决策

### 已定

主人 2026-11-03 逐条定的取舍。下面的做法都按这些来，数字以这里为准。

原则：安全和稳妥做到必要就行，别让升级变麻烦。确认页只放主人真正需要知道的（版本号、不能退回时的醒目提示），其余放进详情，不要层层确认。

1. 后台自动下载新版本，只留一个预下载的版本；磁盘剩不到 5 GB 就不自动下载。主人手动下载和升级按镜像大小加余量判断。
2. 启动时查一次新版本，之后每 6 小时一次，打开升级页时也查。
3. 允许跳版本：渠道只指向最新版，再旧也直接升到最新。每个版本都要能从任意旧版本升上来；真有过不去的版本，让新镜像的 `init` 拒绝并写明先升到哪个版本。
4. M1 不做自动升级，每次都由主人点。
5. 升级前每次都备份核心数据；Tuwunel 聊天库只在这一版声明会迁移它时才备份。
6. 从停核心到新核心起来，总时限 30 分钟，超时就回滚或显示“不确定”。下载单独计时，最多 60 分钟；还在下载、什么都没动的时候可以取消。最坏情况下 App 显示约 78 分钟“升级中”，之后才改成“不确定”。
7. 新核心过了健康检查后再观察 3 分钟，这期间崩了就自动回滚。
8. `install.sh` 和一键升级用同一份 compose（镜像里带的那份）。系统容器不继承宿主 Docker 客户端的代理，出网按 ADR-0023。
9. 给出手动退回的命令。退回后照样跟渠道，App 会再提示有新版本。
10. 会迁移数据、退不回去的版本：确认页醒目提示，先备份受影响的数据，迁移开始后出问题就报“不确定”，不自动回滚。
11. 新装的主机默认走 stable 渠道。

### 升级器

核心用 Docker API 建一个容器 `wonton-updater`，执行 `wonton-core updater`：

- **镜像就是正在运行的核心的镜像**（按镜像 ID 引用）。回滚的逻辑来自已知能用的旧版本，新版本再坏也不影响回滚；本机已有这个镜像，
  不用在升级时多拉一个。
- **`docker compose` 放进核心镜像**：只放一个 `docker-compose` 文件（官方 `docker` 镜像里的 v5.6.1，Apache-2.0，压缩后约
  11 MB），直接运行，不要 docker 命令行。其余操作（拉镜像、跑 `init`、查容器）走 Docker API。这样升级不依赖宿主的 compose 版本。
- **挂载**：Docker socket、安装目录（读写，`.env` 和 compose 文件在这里）、`<数据目录>/core`（备份和状态文件）。容器内外路径
  相同。`--network none`：只和 socket 说话，拉镜像是 Docker 守护进程的事。
- **环境**：执行 `docker-compose` 时不带任何 `WONTON_*` 环境变量。compose 里环境变量优先于 `.env`，带着旧的 `WONTON_CORE_IMAGE` 就换不了镜像。
- **重启策略 `unless-stopped`**：宿主重启、升级器崩溃后 Docker 把它拉起来，它按状态文件接着做，重试有上限（见“卡住和反复崩溃”）。
  做完把自己的策略改成 `no` 再退出。留下的容器供查日志，下次升级时删掉。
- 设了实例名（`WONTON_INSTANCE`，ADR-0011）的核心和开发环境不能一键升级。

### 步骤

下面的 `up` 都指 `docker-compose -f <安装目录>/compose.yaml up -d --wait --wait-timeout 600 --remove-orphans`。

| 阶段 | 做什么 | 失败或超时 |
| --- | --- | --- |
| `pulling` | 确认新镜像在本机；让它列出它要用的其他镜像（`wonton-core compose-images`），经 Docker API 拉好 | `failed`，写明拉不到哪个镜像：什么都没动。这个阶段能取消，结果是 `canceled` |
| `backing_up` | 查磁盘，停 `core`，备份（见“备份”） | 启动回原样，`failed` |
| `switching` | 把 `.env` 的 `WONTON_CORE_IMAGE` 改成新的，在新镜像里执行 `init` | 回滚 |
| `starting` | 处理核心管理的其他组件（见下），`up`；再查 `core` 服务的容器确实跑在目标镜像上 | 回滚 |
| `observing` | 过了健康检查后观察 3 分钟：设了重启策略的长期服务退出、重启、变成不健康，或者换了镜像，都算失败。一次性服务（如 `hydra-migrate`）只要求退出码为 0 | 回滚 |
| `rolling_back` | 停 `core`，从备份恢复核心数据和安装目录，处理核心管理的其他组件，`up`；再查容器跑的是升级开始时记下的那个镜像 | `rollback_failed` |

结果还有 `completed` 和 `rolled_back`。会迁移数据的版本从 `starting` 起不回滚，结果是 `unresolved`，见“不可逆的版本”。升级器不在了、说不清做到哪一步时，核心写 `unknown`，见“状态文件”。

- 每进入一个阶段先写状态文件。阶段都能重做：升级器重启后，`pulling` 和 `backing_up` 从头做，`switching` 和 `starting` 从改 `.env` 开始，
  `observing` 先 `up` 再从头观察，`rolling_back` 从头回滚。
- 回滚写回的是备份里的 compose 文件和配置：新镜像的 `init` 已经改写了它们，只改 `.env` 会用旧镜像配新 compose。
  `--remove-orphans` 删掉同一个项目里新版本多出来的系统容器。
- 健康检查用 compose 文件里定义的，所有长期服务都要过。
- `starting` 和 `rolling_back` 查 `core` 容器时比的是镜像 ID，不是 compose 里的引用：引用（渠道标签）会被移走，
  比字符串分不出跑的其实是别的版本（#669）。回滚的期望值在发起升级时从运行中的容器记进状态文件（`from.image_id`）。
- `.env` 写临时文件、fsync、改名，再 fsync 所在目录；`install.sh` 写 `.env` 也改成这样。升级器读到的 `.env` 缺必需的键时不写回，按失败处理。
  `install.sh` 看到 `wonton-updater` 还在运行时停下，不和它抢 `.env`。

### 升级没结束时核心不动插件

回滚只退备份里的东西，插件容器、`apps/` 下的数据和核心经 API 管的组件不跟着退。如果新核心一启动就按插件规范升级系统插件，回滚后核心的记录是旧的，容器和数据是新的。所以：

- 核心读到 `pulling` 之后的阶段还没结束时，不升级系统插件，不预装，不改经 API 管的组件；插件的安装、升级、卸载回 409 `core_upgrading`，Bot 经总线发起的也一样。
- 状态文件写下任何结果都放行，核心在后台等这个结果。所以每条路最后都要有结果，见“状态文件”和“卡住和反复崩溃”。系统插件的延后升级在放行时做。
- 这样回滚时插件的容器和记录对得上。插件容器本身在整个升级期间不重启。

### 备份

- 放在 `<数据目录>/core/upgrade/backup/<旧 digest>/`，目录 0700。
- **每次都备份**：整个安装目录（`.env`、compose 文件和 `secrets/`，只有几 KB），以及核心数据 `<数据目录>/core`，不含 `upgrade/` 和 `files/uploads/`（没传完的上传）。
- **卷只在这一版声明会迁移它时备份**（见“不可逆的版本”）：先停 `core` 和用着这个卷的服务，用当前镜像跑一次性容器挂上卷复制。
- **磁盘**：要备份的大小加 ADR-0020 文件服务同样的余量（5%），可以删的旧备份算作可用空间。不够就 `failed`，如实报告“磁盘不够”，什么都不删。够了才删旧备份。
- **留多久**：结果是 `unresolved`、`rollback_failed` 或 `unknown` 的那份不能删，它可能是退回迁移前状态的唯一办法，一直留到之后某次升级 `completed`。其余旧备份可以删。`completed` 后只留这一次的，手动退回要用。
- **恢复**：不碰 `upgrade/` 和 `files/uploads/`。自动回滚总是恢复核心数据和安装目录，所以回滚后核心的状态就是升级前的状态；升级期间写的东西（比如观察期里配对的设备）会丢。卷的备份不自动恢复：只有不可逆的版本才有它，而这种版本不自动回滚。

### 核心管理的其他组件

除了 `wonton` 这个 compose 项目，核心还可能管别的组件：compose 项目（如 ADR-0021 的 `wonton-clients`），或者经 Docker API 建的容器（如 ADR-0023 的 `wonton-egress`）。这些是后来的版本才有的，旧升级器叫不出名字，所以规则不按名字写，第一个带升级器的版本就照它实现：

- **这些容器都打标签 `wonton.managed-by=core`。** 经 API 建的再打 `wonton.core.component=<名字>`；compose 项目的名字就是组件名。
- **每个核心镜像用标签 `wonton.core.components` 声明它支持哪些组件**，逗号分隔；没有这个标签等于一个都不支持。
- **切到一个镜像之前（升级、回滚和手动退回都一样），读目标镜像的这个标签**，处理目标不支持的组件：compose 项目 `docker-compose -p <项目> down`，不加 `-v`，卷保留；经 API 建的删容器。不需要 compose 文件。再升回来时数据都在。

### 版本之间的约定

升级器是旧版本，它要操作的是新版本，所以这几样是跨版本的接口：

- `wonton-core init <安装目录> <基础域名>` 的参数，`wonton-core compose-images` 的输出。新版本要多的配置放进 `init` 自己能读到的地方。
- compose 项目名 `wonton`、服务名 `core`、卷名；上面两个组件标签和 `wonton.core.migrations` 的名字和含义。
- 长期服务都设重启策略，一次性服务不设。
- `.env` 新增的变量在 compose 文件里要有默认值：一键升级不写 `.env` 里别的行。需要新必填项的版本只能走 `install.sh`。
- 新版本读得懂旧版本写的状态文件，读不懂的阶段或结果按“不确定”算。
- 新核心遵守上面“升级没结束时核心不动插件”。

### 状态文件

`<数据目录>/core/upgrade/state.json`，原子写入。内容：这次升级的编号、新旧镜像、回滚要用的镜像、发起时间、阶段及其开始时间、升级器第几次启动、结果和失败原因。

- 发起升级在核心里串行处理。发起时核心写第一份。这次发起建或启动升级器失败时，核心把它写成 `failed`（什么都没动）。此后升级器写，只有确认升级器不在了，核心才接手写结果。
- 核心断开时状态还在，新旧版本的核心起来后都读它，所以回滚后的旧核心能说清回滚的原因。
- 核心读到还没结束的状态时再查升级器容器：容器不存在，或者已退出而且重启策略是 `no`，就是升级器不在了。核心查完容器后重读状态文件，还是这次升级、还没有结果才写 `unknown`：升级器先写结果再改重启策略、再退出，这样盖不掉它写的结果。App 上显示**不确定**，
  当前版本以正在运行的镜像为准。容器在，就是升级中，宿主刚重启时它可能还没被 Docker 拉起来。
- 有没结束的升级时，核心不做后台检查和镜像清理。写下结果后恢复，渠道上有比正在运行的新的版本，就能再升级一次。
- `install.sh` 成功跑完后把状态文件改名留档：主人手动修好了，App 不再显示旧的结果。备份留多久不受影响。

### 卡住和反复崩溃

升级不能永远是“升级中”，也不能永远占着“不能再发起”。时限记在状态文件里，升级器重启不重新计时。

- **`pulling` 单独计时，最多 60 分钟**，5 分钟没有进展算卡住。这时什么都没动，主人也能取消。
- **总时限 30 分钟**（已定 6）从进入 `backing_up` 算到 `starting` 结束。`up` 的等待时间取 600 秒和剩余时间里小的。超时按当前阶段的“失败或超时”处理：还没动的 `failed`，动过的回滚，不可逆的版本从 `starting` 起 `unresolved`。
- **`observing` 固定观察 3 分钟**，不受总时限影响：健康的升级不会被截断。这个阶段从第一次进入算起最多 18 分钟（一次 `up` 最长 15 分钟，加观察 3 分钟），升级器重启后先 `up` 再观察满 3 分钟，也不重新计时。
- **回滚 20 分钟**，不占总时限：一次 `up` 的最长耗时是 Tuwunel 的停止宽限 5 分钟加等待 10 分钟，放不进总时限，否则超时后已经没有时间回滚。超过就是 `rollback_failed`。
- 同一阶段升级器最多启动 3 次（状态文件里记次数，每次启动先加一）。超过按这个阶段超时处理，原因写“升级器反复崩溃”。
- 升级器启动后发现状态已结束：把重启策略改成 `no`，退出。

升级器跑不到上面这些判断时（比如启动就崩）靠核心兜底。阶段的上限是：`pulling` 60 分钟，`backing_up` 到 `starting` 30 分钟，`observing` 18 分钟，`rolling_back` 20 分钟。核心发现超过上限再加 10 分钟余量时：

1. 把升级器的重启策略改成 `no`，让它不再被拉起。反复崩溃的这时就停了，核心接着写 `unknown`。
2. 升级器还在运行就先不动它，仍然算升级中：compose 做到一半被杀更糟。它自己写下结果就结束了。
3. 再过 10 分钟还在运行，说明它卡死了，核心停掉它，写 `unknown`。

**取消**只在 `pulling` 阶段有效（已定 6）：核心写一个带这次升级编号的标记文件，升级器在拉取时查它，写下 `backing_up` 之前再查一次，查完立刻写。结果以状态文件为准：`canceled`，或者已经往下走了。核心发起新升级时先删旧标记。

### 检查新版本

- 核心经 Docker 的分发接口（`GET /distribution/<WONTON_CORE_SOURCE>/json`）取渠道 tag 指向的 digest，和正在运行的比较。走守护进程，不用另写一个镜像仓库客户端，
  也不用架目录服务。接口不带凭据，所以镜像包要公开（ADR-0012）。
- 发现新版本就下载核心镜像（已定 1），读镜像的 `org.opencontainers.image.version` 标签得到版本号；比当前旧的不算新版本，只升不降。
- 下载前查数据目录所在磁盘的剩余空间：
  - 定时检查、启动和打开升级页触发的是**自动下载**，剩不到 5 GB 就不下载，如实报告“磁盘剩不到 5 GB，没有自动下载”；
  - 主人点“检查”是**手动下载**，按镜像大小加 5% 余量判断。分发接口不给镜像大小，按当前核心镜像的大小估算。
- Docker 的存储在别的分区时查不到，拉取报错时如实报告。
- 拉到更新的版本就删掉之前预下载的；不删正在运行的、回滚要用的和这次升级的目标。下载不下来时如实显示“有新版本，但下载不了”和原因，打开升级页或者手动检查时再试。
- **下载好才能点升级。** 版本号和“会不会迁移数据”都读自镜像，确认页显示的因此总是真的；反过来，下载不了也升不了。App 不显示其他服务的镜像进度：它们在 `pulling` 阶段才拉。
- `WONTON_CORE_SOURCE` 不是 tag（是 digest）时，如实报告“这次安装固定在这个版本，不跟渠道”。
- 没设 `WONTON_CORE_SOURCE`、`WONTON_INSTALL_DIR` 时，如实报告“这个核心不是正式安装的，不能一键升级”。

### 不可逆的版本

回滚能退镜像、配置和核心数据，退不了没备份的卷，而自动回滚把旧版本配到迁移过的数据上只会更糟。所以要有机制，不能只靠约定：

- **镜像用标签 `wonton.core.migrations` 声明，按 compose 卷写**：`tuwunel@0.5.0,hydra@0.6.0` 表示从比 0.5.0 旧的版本升上来时会迁移卷 `tuwunel`，从比 0.6.0 旧的版本升上来时会迁移卷 `hydra`，并且旧版本读不了迁移后的数据。这个标签只增不减、后面的版本继承，跳版本时也不会漏。
- 当前版本比其中任何一项旧，这次升级就是不可逆的。当前版本没有版本号（开发版）时，声明的都算。
- 核心从预下载的镜像读出这些，写进接口；**确认页醒目提示**“升级后不能自动退回”，受影响的数据放进详情。
- **先备份受影响的卷**，见“备份”。
- **迁移开始后出问题不回滚**：`starting` 之前失败还可以回滚（迁移还没开始）；从 `starting` 起失败或超时，结果是 `unresolved`，停在新版本，报告“不确定”和原因。升级器不再动它，主人按“手动退回”恢复备份，或者等修复版。

不用声明的：旧版本还能读的数据格式变化，以及只迁移核心数据的版本（每次都备份，自动回滚和手动退回都会恢复）。

### 接口

- `GET /_wonton/api/core/upgrade`：当前版本和 digest、渠道、最近一次检查的结果（新版本的 digest 和版本号、下载进展或原因、是否不可逆和受影响的数据）、这次或上次升级的状态；升级中时带上到回滚结束的最长剩余秒数（各阶段上限加余量）。
- `POST /_wonton/api/core/upgrade/check`，请求体 `{"manual": …}`：马上查一次。打开升级页时 `false`，主人点“检查”时 `true`。
- `POST /_wonton/api/core/upgrade`，请求体只有 `{"digest": …}`：发起升级。镜像仓库由 `.env` 决定，请求指定不了别的镜像。digest 和最近一次
  检查的结果不一致时 409 `changed`（主人确认的就是装上的，和插件升级的做法一样）；还没下载好时 409 `not_ready`；已经在升级时 409 `busy`。
- `DELETE /_wonton/api/core/upgrade`：请求取消，回 202，结果看状态。已经过了 `pulling` 时回 409 `too_late`。

只有管理接口能发起，也就是主人的设备；不进 MCP 总线，Bot 发起不了。

### App 显示

状态机在 `wonton-client` 里，壳只渲染。客户端把最后一次从核心看到的升级状态和剩余时限存在本机，App 被杀后重开也接得上。

点“升级”后只确认一次，确认页上是新版本号，不可逆的版本多一条醒目提示。digest、渠道、受影响的数据和失败的详细原因都放进详情。

主人可以跳过一个版本：这台设备不再提示它，想升还能在升级页上升。跳过记在本机，渠道上出了别的版本时重新提示。

| 显示 | 依据 |
| --- | --- |
| 升级中（附阶段） | 核心报告升级中 |
| 升级中，暂时连不上 | 最后一次看到的状态是升级中，连接断了，没超过断开前核心给的剩余时限 |
| 不确定（附原因） | 超过了那个时限；或者核心报告 `unknown`、`rollback_failed`、`unresolved` |
| 已完成 | 核心报告 `completed`，而且它正在运行的 digest 就是目标 |
| 已回滚（附原因） | 核心报告 `rolled_back` |
| 失败（附原因） | 核心报告 `failed`：什么都没动 |
| 已取消 | 核心报告 `canceled` |

等待窗口就是核心给的剩余时限，不另定一个数：比它短，正常的回滚中途就会显示“不确定”。只有核心明确报告才算成功。连接恢复后，不确定随时可以被核心的报告替换。
没看到过“升级中”的设备只显示普通的连不上，不猜。

### 手动兜底

一键升级坏了、核心起不来时，`install.sh` 照旧可用：它不依赖运行中的核心。升级器的日志在 `docker logs wonton-updater`，状态在上面的文件里，`from` 是升级前的镜像。

手动退回（已定 9）给 `install.sh` 一个旧 digest，不改 `WONTON_CORE_SOURCE`，并按“核心管理的其他组件”处理目标不支持的组件：

```bash
curl -fsSL <安装脚本地址> | sudo WONTON_CORE_PIN=<旧 digest> sh
```

退回后照样跟渠道，App 会再提示有新版本，不点就不动。

- **有从这个 digest 升上来时做的备份**：和自动回滚一样，恢复核心数据和安装目录，再 `up`，不在新版本的安装目录上跑旧 `init`。顺序是先停 `core`，再恢复。
- **没有这份备份**：如实提示“核心数据不会退回，旧版本可能起不来”，确认后用旧镜像 `init`、`up`。
- **退回不可逆的版本**：再加上 `WONTON_RESTORE_VOLUMES=1`，同时恢复备份里的卷，要先停用着这些卷的服务。没有备份就拒绝。

退回前要主人确认一次，因为备份之后写的数据会丢（恢复卷时包括聊天）。当前镜像的 `wonton.core.migrations` 表明这次退回跨过了卷的迁移、又没加 `WONTON_RESTORE_VOLUMES=1` 时，确认提示里写明旧版本可能读不了这些卷。脚本经管道运行，标准输入是脚本本身，确认从 `/dev/tty` 读，没有终端就拒绝。

`WONTON_CORE_IMAGE` 不能用来退回：它会把 `WONTON_CORE_SOURCE` 写成 digest，核心从此不跟渠道。

`completed` 之后，核心和系统服务的镜像只留当前用的和回滚要用的那一版，更早的删掉。

### 同一份 compose

`install.sh` 不再用宿主的 compose，改成跑一次性容器 `docker run --rm --network none -v <socket> -v <安装目录>:<安装目录> --entrypoint docker-compose <核心镜像> …`（已定 8）。两条路径用同一个 compose，都读不到宿主的 `~/.docker/config.json`，所以建出的系统容器一样，切换路径时不会全部重建；主机也不用装 compose 插件。

系统容器不继承客户端代理以后，核心靠继承来的代理访问 GitHub 的路就断了。所以实现时 ADR-0023 里“核心显式用主人的代理”的部分要先于这两处发布。

### 默认渠道

新装的主机默认走 stable（已定 11），已经装好的按 `.env` 里的 `WONTON_CORE_SOURCE` 不变。只有不带连字符的 tag 才更新 stable（`release.yml`），所以改安装脚本默认值的同时要有一个正式版本，否则新装拉不到镜像。`install.sh` 和安装说明跟实现一起改。

## 理由与没选的做法

- **单独的 `wonton-updater` 镜像**：要多一条发布链路，升级时还要多拉一个镜像，主机恰好拉不到时连回滚都没有。
- **升级器用新镜像**：新版本的升级器坏了就没人回滚。
- **官方 `docker:cli` 镜像加一段脚本**：同样要多拉一个镜像，核心逻辑写在 shell 里测不了（ADR-0012 的背景就是从 shell 的 OTA 走过来的）。
- **核心自己用 Docker API 重建容器**：等于重写 compose，也解决不了“自己替换自己”。
- **经我们的目录服务发版本信息**（架构里原来的写法）：多一个服务要运营，还是要再问一次镜像仓库。
- **自己的镜像仓库客户端**：代理和 TLS 要再做一遍，而 Docker 守护进程拉镜像本来就要通。
- **把 `wonton-clients` 这类组件的名字写进升级器**：旧升级器不可能认识以后才有的组件。
- **`pulling` 用 `docker-compose pull`**：compose 加载项目时就检查 `env_file` 存不存在，新版本多引用一个由 `init` 生成的文件，这一版就永远升不了。
- **回滚时跑旧镜像的 `init`**：要多一条“`init` 不改已有密钥”的约定；安装目录只有几 KB，整份备份更省事。手动退回没有备份时才这样做，并提示风险。
- **允许观察期升级插件，回滚时把对不上的容器标成孤儿**：要多写一套清理和提示，换来的只是插件早升级 3 分钟。
- **提前判断过不去的版本**（镜像标签声明最低能从哪个版本升上来，确认前就提示）：能少一次断开和回滚，但这样的版本还没出现过，`init` 拒绝后结果同样如实。出现了再加。

### 验证结果

2026-11-03 在 npchy 上实测：

- Docker 29.7.2（containerd 存储）、Compose v5.6.1：
  - `docker-compose` 单个文件在 `debian:trixie-slim` 里、`--network none` 下能运行；
  - 容器的 `Config.Image` 就是 compose 写的 `仓库@digest`；
  - `docker update --restart=no` 对正在反复重启的容器生效；
  - `docker-compose -p <项目> down` 不要 compose 文件，删容器和网络，卷保留；另一个项目的 `up --remove-orphans` 碰不到它。
- 分发接口给的 digest 和拉取后 `RepoDigests` 里的一致：上面的环境用本地 registry 的单架构镜像和 GHCR 匿名拉的多架构镜像（`ghcr.io/matrix-construct/tuwunel:v1.9.4`）；
  Docker 28.5.2（dind、overlay2）用同一个 GHCR 镜像。tag 不存在回 404，仓库连不上回 500。

这次没覆盖：Compose v5.6.1 操作 Docker 28 的引擎，备份和恢复，完整的升级和回滚。

## 代价与风险

- 新 compose 文件用到旧升级器里的 compose 不认识的字段时，`up` 失败，只能走 `install.sh`。
- 升级器和 `install.sh` 的一次性 compose 容器，和核心一样能操作 Docker（ADR-0011）。它们只活在升级或安装期间，不联网，不处理外部输入，目标镜像只来自 `.env` 里的仓库或者主人给的镜像。
- 没有镜像签名：信任 GHCR 和 TLS，和安装脚本一样。
- 升级要几分钟，期间 App 断开、插件的网页和 MCP 走不通。新版本带的系统插件要等升级完成才升。
- 查磁盘只查得到数据目录所在的分区。手动下载时镜像大小是估算的。
- 备份多占磁盘：核心数据、安装目录和声明迁移的卷。留到下次升级；`unresolved`、`rollback_failed` 和 `unknown` 的那份留到之后某次 `completed`。停服务和复制也算在总时限里，聊天库很大时可能超时，这时还没动数据，结果是 `failed`。
- 下载和升级都要拉得到镜像，拉不到时只能走 `install.sh`。
