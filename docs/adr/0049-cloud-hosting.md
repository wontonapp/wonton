# ADR-0049 我们托管的轻量云吞：每个用户一台微型虚拟机，里面照旧跑 Docker

- 状态：暂缓（2026-11-07）：先把自己装的家用版做好。实测和算账留作重启时的起点。

## 背景

主人要我们自己托管多用户的“轻量云服务”：用户不买硬件，在我们的机器上开一台云吞。方向是每个用户一台微型虚拟机，
里面是和家里完全一样的云吞（核心、Hydra、Tuwunel、tusd、模型网关、Hermes），Docker 设计不改；默认轻量档，Immich、
Ollama 这类重应用算升级。不让多个用户共用一个 Docker 守护进程：Docker socket 等于 root，Agent 又会执行代码。

主人另问了一个问题：飞牛这类 NAS 的应用之间有依赖，Node、Python 本身也是能装的应用；我们只用 Docker 是不是不合理，
云上跑很多 Docker 合不合适，插件之间的依赖用 Docker 是不是更难处理。这一问放在“插件的形态”一节回答；
插件依赖本身的设计另写 ADR（见“已定”第 3 条）。

调研只花了机器时间：没注册云账号、没花钱。价格是 2026-11-06 官网标价，合规部分不是法律意见。

## 实测：一台 2 vCPU / 2 GB 的微型虚拟机里装轻量档

条件（2026-11-07）：一台 x86_64 开发机（20 核 125 GB），cloud-hypervisor v54，客机 Alpine linux-virt 6.12.115 + Docker 29.9.3，
云吞是 `deploy/install/install.sh` 装的 beta 镜像，装好后固化成根盘，全程离线；虚拟机钉在宿主 16–19 核、`nice -n 19`。
测量时这台机器在跑别的构建（loadavg 12–17），CPU 和启动时间偏保守，内存和磁盘不受影响。状态 a、b 各空闲 10 分钟、10 秒采一次；
tiny 只看能不能起来、跑稳。模型换成客机里的假 OpenAI 服务，只量云吞自己。

| 指标 | a 刚装好空闲 | b 一台 App 配对待机 | tiny：1 vCPU / 1 GB，配对待机 |
| --- | --- | --- | --- |
| 开机到核心健康 | 3 s | 3 s | 8 s |
| 开机到 Hermes 就绪 | 13 s | 约 13 s | 26 s |
| 客机已用内存（总量减可用） | 740 MB（总 1979，可用最低 1190） | 758 MB（可用最低 1182） | 711 MB（总 973，可用最低 250） |
| Swap、OOM | 0、无 | 0、无 | 0、无 |
| 客机 CPU | 2.8 %（2 vCPU 合计） | 3.2 % | 5.3 %（1 vCPU） |
| 宿主侧 VMM 进程 RSS | 1376 MB | 1382 MB | 440 MB |
| 宿主侧 VMM CPU（折单核） | 10.0 % | 13.5 % | 4.6 % |

各容器（状态 b）：Hermes 314 MB、Tuwunel 105、核心 79、Hydra 62、出网代理 53、tusd 46、模型网关 36 + 默认模型 36。
Hermes 一家占四成。1 GB 时各容器自己收紧（Hermes 282、Tuwunel 61、核心 62），没有换页也没有 OOM。

磁盘：Docker 3.9 GB（镜像为主，Hermes 镜像约占一半），卷 62 MB，云吞数据 9 MB。

聊天时（每分钟 2 条消息）没量成：测量脚本经隧道代理取 Matrix 登录令牌时核心回 405，原因没查清。
空闲时 CPU 已经很低，真实模型下 Hermes 大部分时间在等上游，聊天对密度的影响放进“验证”一节补测。

读法：
- 客机里云吞用掉约 0.75 GB，2 GB 和 1 GB 两档差不多。宿主看到的 1.4 GB 是客机碰过的全部页（主要是客机自己的页缓存）；
  同一份安装开 1 GB 时宿主只占 440 MB。所以**宿主上每用户的实际占用由给多少内存和还不还页决定，不由云吞本身决定**：
  开 2 GB 不还页是 1.4 GB；开 1 GB 或者客机把空闲页还给宿主（free page reporting、balloon）是 0.5–0.9 GB。
- 1 GB 能跑、空闲时还剩 250 MB；但装一个 Node 或 Python 插件就不够了，所以默认档留 2 GB 名义内存，靠还页压宿主占用。
- 空闲时 CPU 几乎不花；瓶颈是内存，不是 CPU 和磁盘。

## 微型虚拟机方案

| 方案 | 隔离 | 启动 | 每台额外开销 | 里面跑 Docker | 快照 / 热迁移 | 许可证 | 生产验证 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Firecracker | 6 个模拟设备 + jailer + 按线程 seccomp | ≤125 ms | ≤5 MiB | 官方内核配置齐全 | 有 / 无 | Apache-2.0 | AWS Lambda、Fargate、Fly.io |
| cloud-hypervisor | 纯 virtio + seccomp，没有 jailer | <100 ms | 约 7–8 MiB | 官方内核缺 netfilter，要自建内核 | 有 / 有（跨主机） | Apache-2.0 AND BSD-3-Clause | Azure 机密容器、Fly.io GPU |
| Kata（qemu） | 每 pod 一台 VM | 约 1.2 s | 数百 MiB | 要独立块盘和额外配置 | 模板 / 无 | Apache-2.0 | 蚂蚁、IBM、NVIDIA |
| QEMU microvm | 主进程复杂 | 约 115 ms | 视配置 | 可以 | 有 / 同版本内 | GPL-2.0（独立进程，不链接） | 机型本身少见 |
| gVisor（对照） | 用户态内核，共享宿主内核 | 约 1.1 s | 约 23 MiB | 不行：要关 iptables，Compose 默认网络挂 | 无 | Apache-2.0 | Google、OpenAI |
| Sysbox（对照） | 共享内核 + userns，官方自认弱于 VM | 秒级 | 接近 runc | 主打 | 无 | Apache-2.0 | Docker Desktop |

要认的事：Firecracker 近两年出过快照加 balloon 组合下的逃逸（CVE-2026-122192，1.16.2 修）；多租户下 KSM 要关（侧信道），
所以不同用户的虚拟机之间不共享内存页，密度只能靠每台自己还页。gVisor 和 Sysbox 共享宿主内核，不做陌生人之间的边界。

## 算账

### 一台机器装几个用户

按一台欧洲独服（16C/32T、128 GB、2×1.92 TB NVMe、不限流量）算，宿主和控制面留 8 GB。欧洲独服只在德国和芬兰
这类机房，美国和新加坡只有云主机；要在美国或新加坡开，换当地有独立服务器的商家重新算。

| 每用户在宿主上的内存 | 一台装下 |
| --- | --- |
| 2.0 GB（按名义内存不超售） | 60 |
| 1.4 GB（开 2 GB、不还页，实测） | 约 85 |
| 0.9 GB（开 2 GB、还页后，估算） | 约 130 |
| 0.44 GB（开 1 GB，实测；只够不装插件的） | 约 270 |

CPU：空闲时每台在宿主上约 0.1–0.14 个核，按 0.14 算 32 线程能撑 200 多台空闲用户，聊天的峰值待补测；内存先到顶。磁盘：每用户按 10 GB 预算（镜像 4 GB、升级时新旧镜像并存、数据），
120 个用户 1.2 TB，一台的盘够。

加上冗余（每 N 台留一台空机接故障迁移）、备份存储、控制面和监控机，按 ×2 估：**轻量档每用户每月机器成本是
个位数欧元**（按宿主占 0.9–1.4 GB），不含模型费、人力、支付手续费。

同内存上云贵 2–3 倍（大内存档的云主机不含盘和流量就比独服贵这么多），云只做溢出和灰度。
国内三家同内存档约是欧洲独服的 1.3–1.4 倍单价，还只是裸实例；5 Mbps 以上的带宽按 Mbps 计费，比国外贵一个量级。

### 重应用

- Immich、Paperless 这类：按插件自己的内存另开档。实测 paperless 空闲 562 MB、Go 写的插件 25–94 MB、Rust 的 4 MB。
- Ollama（本地模型）：只能做共享 GPU 主机加队列的升级项。GPU 独服按月起价不低；国内要企业实名、部分要工单。不进默认档。

### 模型额度

两种都支持，默认经模型网关代收：
- **代收**（默认）：普通用户没有 key，开箱能聊才是“轻量档”。模型网关（magpie）已经按用户计量，接计费出账，按用量预付额度。
  代价：我们成了模型服务的转售方。在大陆这等于生成式 AI 服务提供者（暂行办法第 22 条明写“包括提供可编程接口”），要登记；海外是普通转售。
- **用户自带 key**：设置里填自己的 key，这部分不收模型费。模型网关本来就支持配置提供方，不新增功能。

## 新增部分的范围

### 运营后台

| 功能 | 用什么 | 自研什么 |
| --- | --- | --- |
| 注册和账号 | Ory Kratos（Apache-2.0，和已用的 Hydra 同栈） | 注册页 |
| 计费和订阅 | Lago（AGPL-3.0，原样部署无义务） | 国内收款适配（微信、支付宝要先有执照）；海外 Stripe 或 Paddle |
| 开通和编排 | 第一阶段 Incus（Apache-2.0，每用户一个 project 加一台 VM）；量起来换 Firecracker | Firecracker 阶段的薄控制面：网络、根盘、调度、回收 |
| 备份 | restic（BSD-2）+ SeaweedFS（Apache-2.0）；MinIO 已归档，排除 | 调度 |
| 批量升级 | 虚拟机里照旧用核心自己的升级；宿主镜像用 mkosi | 灰度控制器（1%→5%→全量、健康检查不过就回退） |
| 监控 | VictoriaMetrics + Grafana + Uptime Kuma | 告警规则 |
| 日志 | Vector → Loki | 按租户打标签 |
| 滥用 | CrowdSec + nftables/tc 限速、Rspamd 管出站邮件 | 挖矿检测规则（CPU 长期满载加矿池连接） |

网络比别家省事：云吞对外只走 iroh（ADR-0004），虚拟机只要出站 NAT，不需要每台一个公网地址，也不需要入站端口；
第三方 App 的入口照旧走公网中继和家名服务（ADR-0021）。

### 数据和隐私

托管以后，我们的运维能碰到用户数据，这要直说：
- 聊天在 App 和 Tuwunel 之间端到端加密，但 Bot 在用户的虚拟机里解密才能回复；宿主有 root 的人能读虚拟机的盘和内存。
  所以加密防的是网络上的人和别的用户，不防我们。家里的服务器没有这个问题，这是托管和自己装的根本区别。
- 能做的承诺：每用户一台虚拟机，用户之间不共享内核；运维不进用户的虚拟机，排障要用户在 App 里点同意，每次访问留审计记录；
  备份在宿主端加密，用户注销后按期删除；用户随时能导出整台云吞，搬回家里的服务器（同一份安装，数据目录直接迁）。
- 技术上真正挡住我们的只有机密计算（AMD SEV-SNP、Intel TDX）。Firecracker 不支持，cloud-hypervisor 支持 SEV-SNP，
  要硬件和内核配合，作为以后的“私密档”，不进第一版。
- 模型调用经代收时，提示词经过我们的模型网关到上游；自带 key 时也经过网关（在用户自己的虚拟机里），只是钱不经我们。

### 主体和备案

- **大陆**：对公众卖虚拟机属于 B11 互联网数据中心业务（含互联网资源协作服务）。要公司（注册资本省内 ≥100 万）、
  增值电信许可证、每个域名 ICP 备案（实例要包年包月剩余 ≥3 个月）、等保三级每年测评、实名和日志 6 个月、PIPL 全套；
  代收模型费另要生成式 AI 登记。拿不到 B11 就不能自己卖云主机。
- **海外**：美国最轻（上线前做 DMCA 代理登记）；新加坡居中（公司、DPO、PDPA）；欧盟最重（GDPR 代表、DSA 的 hosting 义务、NIS2 登记），暂缓。
- 推荐顺序：先美国或新加坡；大陆用户在有主体和牌照之前用海外节点，或者走云吞本来的路——买一台家里的机器。

## 插件的形态：继续用 Docker，还是部分改原生包

### 别家怎么做

| 平台 | 包格式 | 应用间依赖 | 运行时 | 原生和 Docker |
| --- | --- | --- | --- | --- |
| 飞牛 fnOS | fpk（INI 清单） | `install_dep_apps`，按名字加最低版本，不递归 | Python、Node、Java 本身是应用 | 两种模板并存，fpk 里也能放 compose |
| Synology | spk | `install_dep_packages` 带版本约束、冲突、依赖系统服务 | Node.js_v18/v20 是独立套件；DSM 7 起 Python 并进系统，官方建议 venv | 原生为主，也有 Docker 套件模板 |
| Umbrel | `umbrel-app.yml` + compose | `dependencies` 强制装序、被依赖的不能卸、依赖链按序停启；`implements` 按能力换提供者 | 打进镜像 | 全 Docker |
| CasaOS | compose + `x-casaos` | 没有 | 打进镜像 | 全 Docker |
| TrueNAS SCALE | compose 模板 | 没有，数据库打进同一个 compose | 打进镜像 | 2024 年从 k3s 改回全 Compose |
| Unraid | plg 插件 + Docker 模板 | 没有结构化字段 | 插件往系统里装包 | 系统功能走插件，应用走 Docker |
| Home Assistant | add-on | `services` 按能力 provide/want/need | 打进镜像 | 全 Docker |
| Cloudron | manifest + 镜像 | `addons` 按能力，平台供给数据库等 | 打进镜像 | 全 Docker |

共享运行时出过的事：Synology 的 Python 套件一次升级，依赖它的 Home Assistant 套件起不来也修不好；homebridge 升 Node
只能等 Synology 发新套件。没找到 2024–2026 年有哪个平台从 Docker 回到原生包；方向是反过来的（TrueNAS）。

### 我们的实测：多一个容器花多少

开发栈上的 5 个官方插件（files、navidrome、miniflux、paperless-ngx、actual），装的是索引固定的提交：

- **容器本身几乎不花**：一个空容器 0.4 MiB；每个容器还有一个 containerd-shim，RSS 约 12 MiB（含和其他 shim 共用的库，是上限）。
- **插件的开销是它自己的软件栈**：files（Rust）4 MiB，navidrome（Go）25 MiB，miniflux（Go + Postgres，4 个容器）94 MiB，
  actual（Node，2 个容器）148 MiB，paperless-ngx（Python，2 个容器）562 MiB。同样是“一个插件”，差 100 多倍，和容器数无关。
- **共用基础镜像能省的很少**：10 个上游镜像 1461 MB，实际共享的只有 12 MB（0.8%）。同叫 bookworm-slim 的两个镜像，
  因为构建日期不同，字节也不共享。假设全改成同一个 debian 底，估算省 81 MB（5.5%），单二进制和 alpine 的插件反而变胖。
- **冷启动**（镜像已在本地）：5–8 s；要等数据库迁移的 25–32 s。

### 插件之间的依赖

- **用别的插件的服务**（A 要 B 的服务）：按能力写，不按插件名，家用版也做，见 [ADR-0053](0053-plugin-dependencies.md)。
  先例：Home Assistant 的 services、Cloudron 的 addons、Umbrel 的 implements、Debian 的虚拟包。
- **构建时依赖**（Node、Python）：打进各插件的镜像，不做运行时插件，也不规定统一基础镜像。统一底实测只省 5.5%，
  却让一次基础镜像升级同时牵动所有插件，正是 Synology 出事的那种耦合。大头是各插件自己的应用层（paperless 一家 820 MB）。

### 云上：虚拟机里跑 Docker，还是跑原生包

- 用户之间的隔离靠虚拟机，不靠 Docker；虚拟机里的 Docker 是为了组件分开、单独升级、单独替换（ADR-0015）。
- 改原生包能省的，是每个容器约 12 MiB 的 shim 和镜像里重复的运行时。轻量档 8 个容器，最多省约 0.1 GB，
  不到每用户 1.4 GB 的十分之一；虚拟机本身的开销（客机内核、页缓存）原生包也省不掉。
- 改原生包要付的：一个插件的依赖和别的插件、和系统绑在一起，升级互相牵连；插件作者要为我们的系统单独打包，
  不能直接用上游的官方镜像；家里和云上不再是同一份安装。

### 结论

继续用 Docker Compose，不改原生包，不规定共用基础镜像；要补的是按能力的插件依赖。按 ADR-0015 判断：每个插件是一个容器组，只做一件事，经能力名（标准接口）连接，
能单独升级、单独替换；共享运行时把多个插件绑在同一份 Node、Python 上，违背“能单独替换”。

## 重启时的方案

1. 每个用户一台微型虚拟机，里面是和家里同一份的云吞安装，Docker 设计不改。用户之间不共用内核，更不共用 Docker 守护进程。
2. 分两阶段：先用 Incus（qemu 虚拟机）跑通注册、付款、开通、备份的闭环；用户量上来、内存成本压过人力时换 Firecracker
   加我们自己的薄控制面。要不停机维护或在线改规格时，备选 cloud-hypervisor。
3. 机器用开服地区当地的独立服务器，云只做溢出和灰度。默认轻量档 2 vCPU / 2 GB，宿主上每用户按 0.9–1.4 GB 排（看还页实测）；
   重应用按插件另开档，GPU 是共享升级项。
4. 模型默认经模型网关代收、按用量预付；用户也能填自己的 key（已定）。
5. 先在美国或新加坡开（法规最轻、亚太延迟低），机器按第 3 条在当地重新算账；大陆等有主体和 B11 许可证再说，在那之前大陆用户用海外节点或家里的机器。
6. 隐私承诺按“我们碰得到”来写：虚拟机隔离、运维进虚拟机要用户同意并留审计、能随时整台导出搬回家。
7. 插件继续用 Docker Compose，运行时打进各自的镜像；插件之间按能力依赖（[ADR-0053](0053-plugin-dependencies.md)）。

## 没选的做法

- **多个用户共用一个 Docker 守护进程**：Docker socket 等于 root，Agent 会执行代码。
- **gVisor、Sysbox**：共享宿主内核；gVisor 里 Compose 的默认网络不能用。
- **Kata**：为 K8s 设计，每台开销数百 MiB，VM 里跑 Docker 要额外配置；只在决定全面上 K8s 或要 GPU 直通时考虑。
- **一开始就写 Firecracker 控制面**：先要验证有人付钱；Incus 开箱就有每用户一个 project 加配额。
- **原生包和共享运行时**：见上一节。
- **统一基础镜像**：实测只省 5.5%，还把所有插件的升级绑在一起。

## 代价与风险

- 我们能碰到用户数据，这和“家庭服务器”的卖点相反；托管要作为“先试用、以后搬回家”的入口来讲，而不是替代。
- 不还页时每用户 1.4 GB，Hermes 占客机用量的四成；Agent 换得更重，密度跟着掉。
- Firecracker 阶段的控制面要自己写；没有热迁移，宿主维护要停机窗口。
- 国内收款要先有执照；大陆业务门槛高到第一版做不了。
- 合规（DMCA、DSA、滥用处理）是常设工作，不是一次性的。

## 已定（主人 2026-11-07）

1. 云托管暂不做，先把自己装的家用版做好。
2. 以后做的话，模型费默认我们代收，用户也能填自己的 key。
3. 插件之间的依赖按能力写，家用版也要；拆到 [ADR-0053](0053-plugin-dependencies.md)。

## 验证

- 选定 VMM 后，在同一台机器上实测：开还页前后宿主上每用户的内存、聊天时的 CPU 峰值、一台机器装满后的聊天延迟。
- 聊天负载（每分钟 2 条消息、10 分钟）补测：上面的测量里，脚本经隧道代理取登录令牌时核心回 405，没量成。
- 测量方法：正式安装的根盘、离线客机、宿主侧采 VMM 的 RSS 和 CPU、客机内采 `/proc` 和 `docker stats`；脚本不进仓库。
