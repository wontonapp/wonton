# ADR-0031 插件的五种来源：官方、社区、添加的仓库、第三方索引和上传的文件

- 状态：已接受（2026-11-04）

## 背景

主人要把插件生态做成 magpie 那样：官方库、GitHub 上的社区插件、自己填的地址、自己上传的压缩包都能装，方便大家自己开发、
自己用、互相分享。ADR-0017 已经有前两种，还有 `github:` 来源和上传接口，但 App 只能装商店列出来的（“上传插件包是开发工具用的，
App 只按来源安装”），没有地方记主人添加的地址，也没有第三方索引。

别人的做法：

| 产品 | 自定义来源 | 上传或本地 | 升级 |
| --- | --- | --- | --- |
| magpie | `plugin add` 收 npm 包名、`github:owner/repo[#ref]`、`owner/repo` 和页面地址 | 收文件夹，就地加载 | git 来源看提交变没变；钉住提交的不提示；文件夹不提示 |
| Home Assistant 的 HACS | “Custom repositories”：填仓库地址加类型，存在本机，出现在列表里 | 没有 | 跟仓库的 release 或默认分支 |
| Umbrel | 社区应用商店：填一个 Git 地址；商店的 `id` 必须是其中每个应用 ID 的前缀 | 没有 | 跟商店仓库 |
| Chrome | 没有 | “加载已解压的扩展”，藏在开发者模式后面，标 Unpacked | 不自动更新，手动重载 |

共同点：地址只有一个入口；非官方的都标出来，但不拦；本地装的不自动更新。

## 决策

### 一条路

这些来源只在“包从哪里取”上不同。取到之后都是同一个 `PluginPackage`：同一套解析和校验、同一个预览、同一个确认页、按同一个
摘要安装（ADR-0017 的“来源与取包”），权限规则也一样。来源写成一个字符串，App 不解析，原样传给预览和安装：

| 来源 | 写法 | 包从哪里取 | 标签 |
| --- | --- | --- | --- |
| 官方索引 | `github:<owner>/<repo>` | 索引记的提交，按 sha256 核对 | 已审核 |
| 社区 | `github:<owner>/<repo>` | 最新的正式版本 tag | 未审核 |
| 添加的仓库 | `github:<owner>/<repo>`，可带 `@<tag>` 或 `@<提交>` | 同社区 | 未审核 |
| 第三方索引 | `index+<索引地址>#<插件 ID>` | 索引记的提交和 sha256 | 未审核 |
| 上传 | `upload:sha256:<摘要>` | 核心暂存的文件 | 未审核 |

“已审核”只认官方索引里的那个版本：`github:` 来源取到的正好是索引里的版本，文件也核对上了，才算官方。其余的都是未审核，第三方
索引也一样，索引的作者不代表云吞审核过。

### 标明是谁、从哪来

`PluginTrust` 不加新值：社区插件、添加的仓库和第三方索引都是 `Community`，上传的是 `Local`。App 上 `Official` 写“已审核”，其余
都写“未审核”，`System` 还是写“系统”（App 上 `Local` 原来写“本地”，看不出没审核过，改掉）。

列表、详情、预览和已安装列表多两个字段，只放核心能核实的来源：

| 来源 | `provider: Option<String>` | `via_index: Option<String>` |
| --- | --- | --- |
| GitHub 上的仓库 | `github.com/<owner>/<repo>` | 空 |
| 第三方索引 | 同上 | 索引的主机，如 `example.com`：装哪个提交由它决定 |
| 上传 | 空，App 写“你上传的文件” | 空 |

清单里的 `author` 是作者自己写的，核心核实不了，所以和 `provider` 分开显示。

未审核的插件，预览的第一条 `notices`（醒目）写明谁提供、谁没审核：

- GitHub 上的：`云吞没有审核过这个插件，代码和镜像由 github.com/<owner>/<repo> 提供`
- 第三方索引的：同上，再加 `，经 example.com 的索引`
- 上传的：`云吞没有审核过这个插件，它来自你上传的文件，清单里写的作者是 <author>，核实不了`

后面再加一条列出镜像的来源：`镜像来自 ghcr.io/foo/bar、docker.io/library/nginx`。

### 添加来源

商店里只有一个地址框。主人填什么，核心都认，判断它是一个插件还是一个索引：

| 主人填的 | 核心的处理 |
| --- | --- |
| `https://github.com/o/r`，可带 `.git`、`/tree/<tag>`、`/releases/tag/<tag>`、`/commit/<提交>`；`github.com/o/r`、`o/r`、`github:o/r@v1.2.0` | 规范成 `github:o/r[@版本]`，再按下面判断 |
| 仓库默认分支的根目录有 `docker-compose.yml` | 插件仓库；没有正式版本 tag、也没写版本时报错，说明要打 tag |
| 仓库默认分支的根目录有 `index.json` | 索引，地址规范成 `https://raw.githubusercontent.com/o/r/HEAD/index.json` |
| 其他 `https://` 地址 | 取回来按索引解析，解析不了就报错 |
| `http://` 地址 | 拒绝：未审核的来源更要靠 TLS 确认内容没被改过 |

添加成功才写下来。存在核心的数据目录 `plugins/store/sources.json`，权限 0600，和官方索引的缓存放在一起：

```json
{ "sources": [{ "address": "github:o/r", "kind": "repo", "added_at_ms": 1794268800000 }] }
```

- 接口：`POST store/sources`（`{"address": …}`，201 给 `AddedSource`），`DELETE store/sources?address=<规范后的地址>`。谁能调用
  和别的管理接口一样：主人，不能是网页发起的；Bot 不能（ADR-0016）。最多 50 个。重复添加是 `conflict`。
- 官方索引里的仓库，不带版本添加时是 `conflict`（“已经在官方商店里了”）；社区列表里的可以加，加了之后只在“我添加的”里列一次。
- 删除只影响发现，不动已安装的插件。记录里的 `origin` 自带来处，插件照常运行。删掉第三方索引后，从它装的插件不再提示新版本，
  已安装列表里说明原因。

### 商店的列表

`StoreListing` 多一项 `added: Vec<AddedSource>`，一个来源一段，顺序是官方、我添加的、社区。

```rust
pub struct AddedSource {
    pub address: String,
    pub kind: SourceKind,          // Repo、Index，比 App 新的是 Other
    pub provider: String,          // github.com/o/r，或 example.com
    pub name: Option<String>,      // 索引自己写的名字
    pub section: StoreSection,     // 插件、时间、问题，同官方和社区
}
```

- 每个来源有自己的缓存和问题，一个来源坏了只影响它那一段。仓库的读法和社区插件相同（`read_repo`），10 分钟一次；索引同官方索引，
  6 小时一次；App 刷新时立即读，一分钟内不重复。
- 列表不等慢的来源：先给上次的结果，后台接着读。核心重启后还没读过时那一段显示“正在读”，不显示成空。
- 添加的来源和官方插件 ID 相同时照样列出（ADR-0017 对社区的隐藏规则不适用）：是主人自己加的，标签和 `provider` 写得清楚。

### 第三方索引

格式和官方索引完全相同（规范的“官方索引”），条目也用 `wonton-core plugin index-entry` 生成，顶层可以多一个 `name`。商店和详情直接用
索引里的 compose。文件先从索引旁边的 `blobs/<sha256>` 取，取不到再按提交从 GitHub 取，都按索引记的 sha256 核对。这样，第三方可以用
任何静态托管分发整个索引，连不上 GitHub 的主机也能装；只放在 GitHub 上时不需要 `blobs/`。

条目的 `source` 还是 `github:`：`blobs/` 只是换个地方取同样的字节。不在 GitHub 上的插件要有 `github:` 来源才能进索引，这一条等
真的有需求再放开。

安装记录的 `origin` 多一个 `index`（它在索引里的来源 `index+<索引地址>#<插件 ID>`）。

### 上传文件

App 用系统的文件选择器选压缩包，把内容交给核心，确认后安装：

1. `POST plugins/preview`，请求体是压缩包。核心校验，把包暂存在内存里，预览的 `source` 是 `upload:sha256:<摘要>`。
2. `POST plugins`，和按来源安装的请求相同（`InstallRequest`）。核心从暂存里取包。
3. 暂存最多 8 个，保留 1 小时，安装后删除。过期了是 `not_found`，App 提示重选文件。

这样 App 的预览、确认、任务进度都不用区分上传和来源，也不用重传文件。开发工具一次上传加 `?grant=` 的写法保留。

校验和其他插件包相同，只放宽了打包格式：

- 格式：tar（`wonton-core plugin pack` 的输出）、tar.gz 和 zip，按文件头认，不看扩展名。
- `docker-compose.yml` 可以在根目录，也可以在唯一的顶层目录里（GitHub 的 “Download ZIP” 就是这样）。
- 只读 compose 引用的文件，其余的不解压也不保存，它们不受单文件上限的限制，所以直接压缩整个仓库也能装。引用的文件照旧：单个 2 MiB、
  合计 16 MiB（ADR-0044 为装下默认状态头像调大），路径不能有 `..`、不能是软链接。
- 防压缩炸弹：压缩包最多 16 MiB，解压后合计最多 64 MiB，最多 1024 项。
- 清单：解析不了时拒绝并说明原因；`spec` 比核心新时提示先升级核心；ID、版本、权限同其他来源。`kind: system` 拒绝。
- 镜像：压缩包不带镜像，`build` 不在 Compose 子集里。镜像从哪个仓库都可以，预览如实列出（见上），没按摘要固定的再提示。
  `pull_policy: never` 允许，用的是主机上已有的镜像，开发时用得上。

预览把摘要显示出来，两个人可以用它核对收到的是不是同一个包。

### 升级和换版本

| 怎么装的 | 新版本怎么来 |
| --- | --- |
| 官方 | 官方索引的版本（ADR-0017） |
| 社区、添加的仓库 | 仓库最新的正式版本 tag，按 tag 装的也提示；按提交装的不提示 |
| 第三方索引 | 那个索引里的版本；索引删了或不再收录时不提示，也不改去看 GitHub 的 tag，否则来源就悄悄变了 |
| 上传 | 不提示：核心不知道去哪里找 |

主人也可以主动换。详情页有“换版本”，两种办法：选一个文件，或者填一个来源（`github:o/r@v1.0.0` 或添加的来源里的项）。

- 接口：`POST plugins/{id}/upgrade/preview`，请求体多收一种 `InstallSource`（JSON）。`UpgradeRequest` 多一个 `source`，空时升到提示
  的版本。预览给 `upgrade_from`，和升级走同一个确认页和回滚（ADR-0017 的“升级”），`id` 不能变，数据保留。
- 确认之后 `origin` 换成新包的。上传的包换到 `github:` 后就开始提示升级，开发完发布时不用重装。反过来，官方插件换成自己的包后
  标签变成未审核，不再跟官方索引。
- 来源变了时，预览醒目写明：`来源从 github.com/a/b 换成你上传的文件，换了之后云吞不再按原来的来源提示升级`。
- 降级不拦，醒目提示：`比装着的 1.3.0 旧。应用的数据可能已经按新版本迁移过，旧版本可能读不了，先备份`。这改了 ADR-0017 的“没有降级”。
  理由：退回旧版本是主人常有的需求，不让换只会逼他卸载再装（数据一样留着，风险一样），提示却没了。自动提示仍然只升不降。
- 版本号和摘要都和装着的相同时预览报 `invalid_input`（“和装着的一样”）。开发时版本号不变、摘要变了可以反复传。

### 留下的数据

不删数据的卸载会留下数据目录、卷和密钥，再装同 ID 的插件会接着用。来源变多以后，别的作者的包可能写同一个 ID。预览发现留着这个 ID
的数据时，醒目提示：`这台服务器上留着 <id> 以前的数据和密钥，这个插件装上后能读到它们；不想这样就先彻底删除`。不按来源拦。

### 接口汇总

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| POST | `store/sources` | `{"address": …}` | 201 `AddedSource` |
| DELETE | `store/sources?address=…` | — | 204 |
| POST | `plugins/preview` | `InstallSource`，或压缩包（新增 gz、zip，并暂存） | `InstallPreview` |
| POST | `plugins/{id}/upgrade/preview` | 空、`InstallSource`（新增）或压缩包 | `InstallPreview` |
| POST | `plugins/{id}/upgrade` | `UpgradeRequest`（新增 `source`） | `InstalledPlugin` |

新的错误都沿用现有类别：地址不认识是 `invalid_input`，地址上没有插件或索引是 `not_found`，连不上是 `source_unavailable`。

客户端核心：`add_store_source(address)`、`remove_store_source(address)`、`preview_upload(bytes)`、`preview_upgrade_from(id, source)`、
`preview_upgrade_upload(id, bytes)`。壳只选文件、读字节，选了超过 16 MiB 的文件时不读，直接提示。

App：商店页右上角一个按钮，打开“添加来源”：地址框，一个“从文件安装”，下面是添加过的来源（能删）。添加的是单个插件时直接打开它的
详情页。

## 理由

- 只有一个地址框：HACS 要主人选类型，这是核心能自己判断的事。
- 添加过的地址记下来，而不是只装一次：出现在商店里，能看到新版本、可以之后再装，第三方索引也只能这样。来源和已安装分开：删地址不影响
  装着的，插件也不必依赖来源列表。
- 上传也用来源字符串：App 不用分两条路，主人确认的还是那个摘要。
- 第三方索引沿用官方格式：作者用现成的工具，核心也只多一个取文件的地方。

## 代价与风险

- 未审核的插件和官方插件的权限规则相同，一个写着高权限的未审核插件，主人确认后就能拿到高权限。这是主人的选择，靠标签和确认页提示，不在底层拦。
- 第三方索引的主机能决定装哪个提交和什么 sha256，也能换掉插件。`via_index` 写明经哪个索引，但主人不一定看得懂这句话的分量。
- 作者可以写和官方插件相同的 ID、名字和图标。列表和确认页上能看出“未审核”和 `provider`，但看名字的人可能会认错。
- 核心按主人填的 https 地址发请求，地址可以指向内网。只有主人能填，响应体按索引解析、不原样返回，风险可以接受。
- 压缩包解压的是不可信输入：靠大小和项数上限，只读引用的文件。

## 没选的方案

- 地址只用来装一次，不记下来（magpie）：简单，但第三方索引还是要记，两条路不如一条。
- 上传放在开发者模式后面（Chrome）：要多一个开关，而这个能力对普通用户分享插件也有用；提示足够。
- ~~按 ID 前缀隔离第三方（Umbrel）：要作者遵守命名，又和 ID 用反向域名的规则（规范的“字段”）冲突；重名靠标签和“留下的数据”的
  提示。~~ [ADR-0086](0086-plugin-id-prefix.md) 改了这条：第三方来源的 ID 必须带 `io.github.<所有者>.` 前缀，由核心按来源仓库的
  所有者核对，不靠作者遵守，也不和反向域名的规则冲突；为什么当时的判断不再成立，见该篇“为什么改 ADR-0031 的判断”。
- 给索引和压缩包加签名：没有发布者身份体系，签名说明不了“谁”。官方索引的签名见 ADR-0017。
- 收任意 HTTPS 地址上的压缩包当来源：相当于没有版本、没有摘要的第三方索引；要分发就写一个索引。
- 不在 GitHub 上的 Git 仓库（Gitee、Gitea）：取文件的接口各家不同。索引的 `blobs/` 已经解决了连不上 GitHub 时怎么取。
