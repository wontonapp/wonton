# ADR-0087 加设备时自动带上聊天密钥：配对后接着做 Matrix 自我验证，恢复密钥只留给旧设备都不在时

- 状态：提议。方向 2026-11-12 主人定：已有设备扫码加新设备时，密钥自动带过去，新设备上不出现“恢复密钥”这一步；
  恢复密钥只在旧设备都不在时用。文末“待主人定”定下后改为已接受
- 修订：[ADR-0046](0046-device-verification.md) 的入口（新设备不再从“输入恢复密钥”提醒进确认）和“不自动接受请求”；
  [ADR-0076](0076-device-verification-fallback.md) 的“QR 先不做”。确认方式本身、秘密交换、`KeysMissing` 和重置的规则不变

## 背景

盲测里 9 个人都没看懂“恢复密钥”：新配对的设备上一排“无法解密”，每个聊天都提示“输入恢复密钥”。

ADR-0046 已经给了不用恢复密钥的路：SAS 自我验证，验证后自动取交叉签名私钥和备份密钥；旧设备在“添加设备”页上显示收到的
确认。但新设备要主人自己发起：配对登录后先落到聊天列表，看到的是“输入恢复密钥”提醒（`chat/recovery.rs` 的
`Incomplete` 分支、`chat/view.rs` 的 `key_notice`），“用另一台设备确认”藏在备份页里。

加设备是两台设备同时在主人手里、旧设备正开着的时刻，正好用来交接密钥。

## 调研：matrix-sdk 0.19.1 和 Tuwunel v1.9.4

版本由 `Cargo.lock`（matrix-sdk、matrix-sdk-crypto 0.19.1，matrix-sdk 在 `vendor/`）和 `deploy/install/compose.yaml`
（Tuwunel v1.9.4）固定。按源码核对：

**A. 设备验证后用 `m.secret.request`/`m.secret.send` 交出秘密：SDK 开箱即用，仓库已接入。**

- 本账号身份经验证（SAS 或 QR）后，新设备自动要缺的秘密：`matrix-sdk-crypto-0.19.1/src/verification/mod.rs:594-615`
  （`request_missing_secrets`：缺的交叉签名私钥，加上没有备份解密密钥时的 `m.megolm_backup.v1`）。
- 旧设备只回给本账号、已验证的设备（`gossiping/machine.rs:415-447`，否则记 “the device isn't trusted” 丢掉）；
  新设备只收本账号、已验证设备发来的秘密（`gossiping/machine.rs:1037-1038`）。秘密经 Olm 加密。
- 请求被丢、迟到的补要见 ADR-0046 的“取回密钥”（`vendor/matrix-sdk` 的
  `Encryption::query_missing_secrets_from_other_sessions`）。
- 应用内 QR 验证：`VerificationRequest::generate_qr_code`、`scan_qr_code`
  （`vendor/matrix-sdk/src/encryption/verification/requests.rs:172,189`），显示端 `QrVerification::confirm`（`qrcode.rs:99`）。
  要显式打开 `qrcode` feature（不在 `default` 里，`vendor/matrix-sdk/Cargo.toml:58-63,121-124`），扫描端要把原始二进制
  载荷交给 SDK（ADR-0076）。

**B. MSC4108 扫码登录并转交秘密：SDK 和 Tuwunel 都有，接不进我们的登录。**

- SDK 两端都有：新设备 `OAuth::login_with_qr_code`（`LoginWithQrCode`、`LoginWithGeneratedQrCode`），旧设备
  `OAuth::grant_login_with_qr_code`（`GrantLoginWithScannedQrCode`、`GrantLoginWithGeneratedQrCode`），
  `vendor/matrix-sdk/src/authentication/oauth/mod.rs:409,418`。秘密装在 `QrAuthMessage::LoginSecrets(SecretsBundle)` 里经
  安全通道送达，新设备导入（`oauth/qrcode/login.rs:186`），旧设备 `OlmMachine::export_secrets_bundle` 导出
  （`oauth/qrcode/grant.rs:45`、`matrix-sdk-crypto-0.19.1/src/store/mod.rs:1078`）。
- 新设备的登录是 OAuth 设备授权（RFC 8628，`oauth/qrcode/login.rs:80`），旧设备要在浏览器里打开 `verification_uri`
  同意（`oauth/qrcode/grant.rs:112-123`）。
- Tuwunel v1.9.4 实现了 MSC4108 和 MSC4388 的 rendezvous，以及带设备授权的内置 OIDC 服务器（上游
  `docs/authentication/qr-login.md`、`oidc-server.md`）。前提：开内置 OIDC 服务器，批准那一步由上游身份提供方或本地密码
  认证；OIDC 建的设备重置交叉签名要经身份提供方重新登录（MSC4312）。
- 云吞的设备和 Bot 都用核心签的 `org.matrix.login.jwt` 登录，服务器关了密码登录（ADR-0009），重置身份的 UIA 也只走
  JWT（ADR-0076）。

## 决策

### 机制：A，配对完成后自动接着做自我验证

用 Matrix 标准的自我验证加秘密交换（A），接进“添加设备”：新设备配对、登录后自动发起，旧设备在还开着的“添加设备”页上
自动接受，主人在两台设备上完成一次确认，密钥随即交过去。新设备上不出现“恢复密钥”。

确认方式分两步上（见“待主人定”1）：先用已实现的 SAS（两边对表情、各点“相同”）；再加 QR，之后默认**再扫一次**——旧设备
把配对码换成 Matrix 验证码，新设备的相机还开着、接着扫，旧设备点一次“新设备显示完成了”。没有相机、扫不上时退回 SAS。

### 接进配对的每一步

1. 旧设备：设置 → 添加设备，显示配对码（`Action::InviteDevice` → `DeviceInvite::Ready`，不变）。
2. 新设备扫码，经隧道配对（`PairHome`），核心签 JWT，新设备登录 Matrix、上传设备密钥（不变）。
3. 新设备核心：首次登录、本设备未验证、`has_devices_to_verify_against()` 为真时，**自动**发自我验证请求，不等主人点。
   交接期间核心不给“输入恢复密钥”提醒和 `key_notice`，`recovery_next_step` 是新类别“等另一台设备”；壳整屏画交接页
   （“在<旧设备名>上继续”），盖住聊天列表，主人看不到一排“无法解密”。
4. 旧设备核心：“添加设备”页开着（显示着码，或码刚被用掉、页没关）时，收到本账号的自我验证请求就**自动接受**，同一页
   接着显示确认。只自动接受一个；页关了、或第二个请求，照 ADR-0046 走手动接受和并发取消。
5. 确认：SAS 时两边对表情各点“相同”；QR 时旧设备显示验证码（模式 `0x01`：账号主公钥、新设备的设备公钥、共享秘密），
   新设备扫，旧设备点一次确认。
6. 双方完成后 SDK 在新设备上自动要三把交叉签名私钥和 `m.megolm_backup.v1`；旧设备回给已验证的新设备；新设备开启备份、
   按需下载房间密钥，时间线原地解开。期限、补要、`KeysMissing` 照 ADR-0046。
7. 新设备拿齐私钥、备份可用（`VerificationStage::Done`）后交接页关掉，进聊天列表；旧设备那页显示“已加好”。

### 核心和壳

- **核心**（`wonton-client`、`wonton-matrix`、`wonton-protocol`）：什么时候自动发起、什么时候自动接受、等多久、每一步的
  阶段和失败类别、交接期间压住恢复提醒、`recovery_next_step` 的新类别；QR 时显示端给出码的字节，扫描端接收扫到的字节
  （新 `Action`）。
- **壳**：按阶段和类别画交接页和“添加设备”页上的确认，文字按类别取本地化资源（ADR-0043）；QR 时把核心给的字节画成码，
  把相机读到的原始字节交给核心。壳不判断该不该交接、该不该接受。

### 失败时

都不自动重置、不自动转到恢复密钥。交接页上恢复密钥只是次要的文字按钮“手边没有别的设备”，点了才进备份页。

| 情况 | 核心判定 | 新设备上说的话（类别由核心给，文字在壳） |
| --- | --- | --- |
| 旧设备没开着、“添加设备”页已关 | 请求发出 60 秒没人接受（请求本身按 SDK 10 分钟过期） | 在另一台设备上打开云吞、回到“添加设备”；“再试一次” |
| 任一边取消 | `Cancelled { ByMe / ByOther }` | 已取消；“重新开始” |
| 表情不一样、扫到的码对不上 | `Mismatch`，不交任何秘密 | 两台设备没对上，已停止，这台设备没拿到密钥；“重新开始” |
| 确认了但 30 秒内没取全秘密 | `KeysMissing`，之后继续补要（ADR-0046） | 没从另一台设备取全；“重新开始”，迟到的秘密到齐后自动完成 |
| 旧设备自己缺私钥 | 旧设备核心不自动接受，旧设备页上报类别 | 那台设备也没有完整的密钥 |
| 两台新设备同时来 | `ConcurrentRequest`，两个都取消 | 同时有两台设备在确认；“重新开始” |
| 隧道或服务器出错 | `Failed`，详情在 `problem` | 一句人话，原始错误收进“详情” |
| 账号里没有别的已验证设备（第一台设备、`sudo wonton pair` 找回、旧设备都丢了） | 不发起交接 | 直接进备份页输入恢复密钥（ADR-0076 的顺序） |

### 安全

- 秘密只经 SDK 的标准路径交出：Olm 加密，只给本账号、已验证的设备。新设备只能靠在这次加设备里完成的 SAS 或 QR 成为
  已验证；两者都经两台设备之间的线下通道比对，核心伪造不了。配对码里不放任何 Matrix 秘密，核心看不到秘密。
- 自动接受只是接受请求，不给信任：确认那一步仍由主人在旧设备上做（不自动点“相同”、不自动确认扫码）。核心造一台假设备
  抢先发请求，最坏是这次交接失败，拿不到秘密。
- 不用 `Device::verify()` 直接签名代替确认（ADR-0076 的理由）。
- 回应秘密请求的规则是 SDK 的：旧设备也会回应以后任何已验证的本账号设备，这是 Matrix 标准行为，本文不收窄。“只交给
  这次配对里确认过的设备”由“只有确认能让新设备变成已验证”保证。

## 理由

- 主人要的“扫码加设备、密钥自动过去”，标准做法只有 A 和 B 两条。A 的密码学、秘密交换、补要和确认界面都已实现，缺的
  是自动发起、自动接受和交接页。
- 加设备时两台设备都在主人手里、旧设备开着，ADR-0046 里“旧设备要开着 App、推送唤醒不了”的问题在这一刻不存在。
- “再扫一次”和 MSC4108 的体验接近（MSC4108 也要旧设备上一步确认，外加浏览器同意页），却不动登录体系。

## 没选的

- **MSC4108（B）**：一次扫码同时登录和交秘密，SDK 和 Tuwunel 都支持，但要把设备登录从核心签的 JWT 换成 Tuwunel 的
  OAuth 设备授权：开内置 OIDC 服务器、把 Hydra 接成 Tuwunel 的上游身份提供方、给 JWT 建的账号补关联、重置身份改走
  MSC4312 的重新登录、旧设备多一个浏览器同意页。新设备要先经隧道配上才到得了 rendezvous，配对码和 MSC4108 的码仍是
  两个码，或者要自己拼一个格式。这是改 ADR-0009 的身份体系，收益只比“再扫一次”少一下点击；两个 MSC 都在 unstable
  命名空间。
- **自己转交 `SecretsBundle`**（旧设备在配对码里放一把临时公钥，经核心转发加密的 bundle）：要自己设计密钥交换和防重放，
  等于重写 MSC4108 的安全通道，违背“不造轮子”。
- **把 Matrix 验证码塞进配对码**：扫配对码时新设备还没有 Matrix 设备密钥，QR 模式 `0x01` 要的设备公钥写不进去（ADR-0046）。
- **自动确认**：确认是核心伪造不了的那一步，去掉就挡不住核心换设备。

## 代价与风险

- 加设备多一步确认，且两台设备要同时开着；放下旧设备、关掉“添加设备”页，交接就停在“等另一台设备”。
- QR 要开 `qrcode` feature，两端扫码页要交原始字节（ADR-0076 记的成本）。
- 只能解开旧设备手里有、或备份里有的消息（ADR-0046）。
- 主人给家人出码时（ADR-0045）出码的是别的账号，不会自动接受；家人的新设备按自己账号里有没有别的设备走交接或恢复密钥。

## 测试

行为测试放客户端核心，两台真实客户端对一次性的真实 Tuwunel（`crates/wonton-client/tests/it/chat/support.rs` 的
`Home`、`Phone`），都要 Docker，标 `#[ignore = "需要 Docker，…"]`：

- 旧设备开着“添加设备”、新设备用这个码配对：新设备自动发起、旧设备自动接受，确认后新设备已验证、备份启用，配对前发的
  加密消息在新设备时间线里解开；全程新设备的快照里没出现过输入恢复密钥的提醒和 `key_notice`。
- 旧设备没开“添加设备”页：请求不被自动接受，旧设备是 `Incoming`；新设备 60 秒后给“等另一台设备”的类别。
- 取消、表情不一样：新设备没得到任何秘密，仍未验证。
- 旧设备缺私钥：不自动接受，旧设备给出类别。
- 账号里只有这一台设备：不发起，下一步是输入恢复密钥。
- QR：测试直接把显示端核心给出的字节经 `Action` 交给扫描端核心，不经相机。

不要 Docker、跑在默认 CI 里的：交接阶段、`recovery_next_step` 和恢复提醒的推导写成纯函数，逐个状态断言。两端界面在 iOS
模拟器和 Android 模拟器上端到端实测：扫码加设备 → 历史解开，没有恢复密钥这一步。

## 待主人定

1. **确认方式**：再扫一次（QR，扫不了退回对表情），还是一直对表情（SAS）。推荐：先上对表情，QR 做完后默认再扫一次。
2. **新设备等不到旧设备时**：一直停在交接页，还是 60 秒后放主人进聊天列表（列表顶上留“在另一台设备上继续”的提醒，不提
   恢复密钥）。推荐：60 秒后可进列表，提醒只说“在另一台设备上继续”。
3. **交接页上恢复密钥的入口**：只留次要文字按钮“手边没有别的设备”，还是和交接并列成两个选项。推荐：次要文字按钮。
