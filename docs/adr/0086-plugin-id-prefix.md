# ADR-0086 第三方插件的 ID 带可核实的作者前缀：`io.github.<所有者>.…`，核心按来源核对

- 状态：已接受（2026-11-12）
- 修订 [ADR-0031](0031-plugin-sources.md)：“没选的方案”里“按 ID 前缀隔离第三方”一条不再成立，改为按本文采纳

## 背景

插件的 ID 规则一直是“反向域名形式，全局唯一”（插件规范“字段”）：至少两段、每段小写字母数字加单个连字符、总长不超过 63。
但规则只管格式，不管 ID 和来源的关系：五种来源（[ADR-0031](0031-plugin-sources.md)）里，社区、添加的仓库、第三方索引、上传和
Bot 写的插件（`dir`）都可以声明任意 ID——包括和官方插件相同的 ID、名字和图标。现在只靠三样东西兜着：

- 标签：官方之外一律“未审核”；
- `provider`：核心能核实的来源，如 `github.com/<owner>/<repo>`；
- 社区发现里，插件 ID 和官方插件相同的仓库不列出；装的时候同 ID 被“留下的数据”的醒目提示盖着（接用以前的数据和密钥）。

Issue #234 的现象：看名字的人仍可能认错；同 ID 的包装上就接着用以前留下的数据和密钥；Agent 写的插件经仓库分享给别人以后
（[ADR-0033](0033-plugin-tabs.md) 的 `dir` 加 [ADR-0051](0051-friends-and-plugin-sharing.md) 的分享），这类冒充更容易发生。

别人的做法：

| 产品 | 怎么防 | 靠什么核实 |
| --- | --- | --- |
| [Umbrel 社区应用商店](https://github.com/getumbrel/umbrel-community-app-store) | `umbrel-app-store.yml` 给一个商店 `id`，店内每个应用的 ID 必须以它为前缀（`sparkles-hello-world`） | 没有核实：作者自己遵守，商店主人自己把关 |
| [MCP 官方注册表](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/authentication.mdx) | 名字空间 `io.github.<用户>/`（GitHub 登录授权）或 `<反域名>.*`（DNS TXT 或 `/.well-known` 验证域名） | 发布者向注册处登录，注册处发放名字空间 |
| Chrome Web Store | 不让装商店外的扩展；开发者模式“加载已解压的扩展”藏起来并标 Unpacked | 不核实 |

Umbrel 的前缀是平台自己起的（`sparkles`），和我们的反域名规则对不上；MCP 的名字空间本身是反向域名（`io.github.alice`），而且
有核实。这两个差别正是 ADR-0031 当年不选前缀的原因（见下文“为什么现在改”）。

## 决策

### 1. 一条规则：非官方来源的 ID 必须以来源所有者的 GitHub 名字空间开头

- 走 GitHub 取的包（社区、添加的仓库、第三方索引条目、子目录来源），清单的 ID 必须是
  `io.github.<owner>.<至少一段>`：`owner` 是来源仓库的所有者，比较不分大小写（GitHub 用户名不分大小写），ID 本身仍必须全小写。
  前缀按段核对：`io.github.alice`（后面没有段了）不算匹配。
- 核对是核心做的，不是靠作者自觉：来源指到哪个仓库，ID 就得挂哪个所有者的名字空间。想冒充 `io.github.alice.*`，得先能往
  alice 的仓库提交——冒充的成本从“改一行清单”变成“控制别人的仓库”。
- ID 合法但和来源对不上时拒绝。错误类别新增一种（`author_mismatch`，HTTP 422），和现有的两类分开：
  - 不是 `invalid_input`：格式合规，不是“输入非法”；
  - 不是 `permission_denied`：和主人的授权无关。
  类别进核心的错误清单，App 按类别配四种语言的文字（ADR-0043）。
- 核对的时点：取到包、清单和来源都在手的那一处，一条函数，新装的预览和安装共用。升级和“换版本”不查前缀：来源是主人
  自己填的，和上传同理（主人 2026-11-12 定），预览按 ADR-0031 醒目写明来源换成谁；官方插件换到个人仓库从此不是官方版，
  升级改跟新来源。商店列表直接跳过不符合的来源，日志记原因，和“清单读不懂不列出”同一待遇——不列出来再让安装失败。
- 子目录来源（ADR-0079）不改变这条：所有者看仓库，不看子目录。

### 2. 官方索引豁免；官方 ID 不改

身份来自审核加摘要核对，不来自来源所有者，所以官方索引走的是另一条路，豁免前缀：

- 豁免的条件就是现有的“官方”判定（ADR-0031）：取到的包和官方索引条目完全一致——仓库（含子目录）、提交、全部文件的 sha256
  都对上。对上了，信任是 `Official`，不查前缀；对不上，按第三方查前缀。不需要新的信任计算。开发镜像和冒烟测试用
  `WONTON_STORE_INDEX` 顶替官方索引（规范“官方索引”）：对那台核心来说它就是官方索引，条目同样豁免。
- 由此：
  - 社区插件被官方索引收录后照常能装能升级（正好是官方版本时）；
  - 别人的仓库发布一个 ID 同官方插件的包（自己的提交）装不上——走 `github:` 来源，官方索引是这些 ID 的唯一通道；上传是
    主人亲手给的例外（第 3 节），由“留下的数据”的提示兜着；
  - 官方插件作者本人发的、索引还没收录的构建，走社区路径也拿不到官方 ID；
  - 官方插件“换版本”到个人仓库（同 ID）允许：预览醒目写明换成谁的仓库、从此不再是官方版、升级改跟新来源——这是主人
    自己选的操作，和上传同理（主人 2026-11-12 定）；
- 官方索引的 ID 不跟着改。官方插件包的是上游产品，ID 按上游产品写（`app.immich.immich`、`org.navidrome.navidrome`）比按我们的
  GitHub 名（`io.github.geraldpeng6.immich`）对用户更有意义，也不冒充谁。绿地（还没有第一个外部用户）：本篇不写迁移，也没有
  要迁移的东西——规则只约束新装的第三方包，官方条目和已装插件原样。

### 3. 每种来源

| 来源 | 名字空间 | 谁核对 |
| --- | --- | --- |
| 官方索引条目、随核心预装 | 官方惯例（上游产品的反域名） | 审核 + 摘要核对（不变） |
| `github:`（社区、添加的仓库、子目录） | `io.github.<owner>.…` | 核心，按来源仓库的所有者 |
| `index+<索引地址>#<ID>` | 同上：索引条目的 `source` 指到哪个仓库，就按那个仓库的所有者核对 | 核心；条目不符就不列出 |
| `upload:sha256:…` | 任意合法的反域名 ID | 没有外部所有者可核。上传是主人自己的动作，有摘要预览、“你上传的文件”、未审核标签和“留下的数据”提示 |
| `dir`（Bot 写的插件） | 任意合法的反域名 ID；但 ID 和官方索引条目相同时拒绝 | 核心按磁盘上最近一次取到的官方索引查（本地就有）；一次都没取到过时拒绝，提示先刷新商店再装。`written_by` 照旧标“你的 Agent · 名字” |

- 索引不引入新规则：ADR-0031 已要求索引条目必须有 `github:` 来源，所以核对条目的 `source` 就够了，索引作者没法把
  `app.immich.immich` 洗进自己的索引——除非条目指向的仓库和提交就是官方索引里的那份（那是镜像官方，无害）。
- Bot 写的插件不加 owner 前缀要求：Bot 不是 GitHub 所有者，硬造一个前缀只会是假的。Bot 写的插件常以主人自己的
  `io.github.<主人>.…` 起草、之后由主人发布，拦这个前缀反而卡死正常流程。Bot 是核心认得的身份（ADR-0033），装卡上写
  “你的 Agent · 名字”；它想冒充的口子只剩显示名和图标，见“代价”。
- 好友分享不装包：好友的 App 经隧道用主人服务器上的实例（ADR-0051），好友那边没有安装动作，这条规则不适用。

### 4. 自有域名的名字空间：暂不做

将来会有人想用自己域名当名字空间（`com.example.notes`），仓库搬家、换组织也不动 ID。证明归属有两条现成的路（MCP 注册表的做法）：

| | DNS TXT | `/.well-known`（HTTPS） |
| --- | --- | --- |
| 放什么 | 域名 apex 上一条 TXT，带着公钥（`v=…; k=…; p=…`） | `https://<域名>/.well-known/…` 一个文件，内容带证明 |
| 核心怎么核 | 安装时查 DNS。问题：查询走 UDP 53，不过主人的代理（ADR-0023 管的是 HTTP），国内还有污染和劫持，TXT 的可信度打折 | 安装时取一次 HTTPS。走核心现成的取文件路径，能经代理；但多一次对任意外域的请求（SSRF 面、缓存、失败语义都要定） |
| 密钥轮换 | 要管理公钥、换记录 | 改文件就行，没有密钥 |
| 谁都能核 | 是（公开数据） | 是（公开数据） |

MCP 注册表能“发布者登录一次、名字空间长期有效”，是因为它有一个中心注册处。我们的来源是分散的——任何仓库、任何索引——域名
验证就得在每台核心、每次安装时用公开数据重做一遍，两条路都比 MCP 的贵，而今天一个用域名名字空间的作者都没有：第三方包只可能
来自 `github:`，索引条目也必须有 `github:` 来源。所以暂不做；等真有“组织要在仓库搬家后保住 ID”的需求，再按上表二选一（倾向
`/.well-known`：走代理、无密钥管理）。在那之前，域名形式的 ID 出现在 `github:` 来源上就是 `author_mismatch`。

### 5. 和“留下的数据”的关系

同 ID 接着用旧数据和密钥（ADR-0031“留下的数据”）的口子，被这条规则堵上最大的一个：跨作者抢 ID（`github:` 路径）装不上了。
剩下的口子是上传、Bot 写的插件，和把装着的插件换版本到别人的仓库——都要求主人或主人的 Bot 亲手选，预览写明（第 1 节）。
“留下的数据”的醒目提示保留，仍是最后一道。

## 为什么改 ADR-0031 的判断

ADR-0031“没选的方案”原文：*按 ID 前缀隔离第三方（Umbrel）：要作者遵守命名，又和 ID 用反向域名的规则（规范的“字段”）冲突；
重名靠标签和“留下的数据”的提示。* 当年的两条理由现在都不成立：

- **“要作者遵守命名”**——当时设想的前缀是 Umbrel 式的：作者或商店自己起一个词，全靠自觉。现在的核对是机械的：ID 第 3 段和
  来源仓库所有者比对，核心有双方的值，作者没有不遵守的空间。Umbrel 做不到这一步，是因为它的商店 `id` 和作者身份没有绑定；
  我们的来源（`github:o/r`）天生带着所有者。
- **“和反向域名的规则冲突”**——Umbrel 的前缀（`sparkles-hello-world`）确实不是反向域名。`io.github.<owner>` 本身就是反向
  域名，规范的“字段”一个字不用改：ID 仍是反向域名，只是第三方可用的名字空间限定为“能核实的那个”。ADR-0080 的示例
  （`io.github.alice.snake`）已经是这个写法。
- **“重名靠标签和提示”**——生态长到五种来源、Agent 开始写插件并互相分享之后，不够了：标签盖不住“看名字认错”，提示盖不住
  “同 ID 接用数据和密钥”。issue #234 记的就是这两个不够。

## 契约测试

规则是“来源 ↔ ID 绑定”，提供方是核心的安装管线，消费方是商店列表、预览和 App。契约是：同一个包，从哪个入口进，结果都一样。
测试挂在 `crates/wonton-core/src/plugin/tests/source_prefix.rs`（同 `source_subdir.rs` 的挂法），商店列表的跳过在 storefront 的
行为测试里：

1. `github:o/r`，ID `io.github.o.x`：预览和安装都过。
2. `github:o/r`，ID `io.github.other.x`、`app.foo.x`、`io.github.o`（后面没段了）：都是 `author_mismatch`，不是
   `invalid_input`、不是 `permission_denied`。
3. 所有者大小写：仓库 `github:ItzCrazyKns/...`（来源大小写照写），ID `io.github.itzcrazykns.x`：过。
4. 官方豁免：包的仓库、提交、文件摘要和官方索引条目一致，ID 是官方的反域名（不含 `io.github.`）：过，信任 `Official`。
5. 同一官方 ID、同一仓库但提交不是索引里那份：`author_mismatch`。
6. 第三方索引：条目的 `source` 所有者和 ID 前缀不符——列表跳过并记原因；直接按来源装，`author_mismatch`。
7. 上传：任意合法 ID 都过（含官方 ID 的形状——上传路径不查前缀）。
8. `dir`：ID 和官方索引条目相同，拒绝；非官方 ID 照常，`written_by` 不变。
9. “换版本”和升级：装着的插件换来源不查前缀（来源是主人自己填的，预览按 ADR-0031 醒目写明换成谁）；官方插件换到个人
   仓库（同 ID）允许，标签变成未审核，升级改跟新来源。
10. 子目录来源：`github:o/r/sub` 的所有者按 `o` 核对。
11. 社区列表：ID 不符合规则的仓库不出现，理由进“没列出的”。

## 考虑过的做法

- **维持现状（标签 + `provider`）**：issue #234 的现象就是不够；冒充成本是改一行清单。
- **只拦和官方 ID 相同的**：拦不住第三方之间互相冒充和“看起来官方”的擦边 ID（`app.immich.immich-pro`），上传和 `dir` 也照样
  能拿官方 ID；而且要识别“官方 ID”得先定义官方名单，第三方索引上的包又不在名单里。
- **Umbrel 式平台前缀**（商店给 `id`，应用以它为前缀）：前缀含义是“平台”不是“作者”，和反域名规则冲突，且没有核实。
- **所有来源统一强制 `io.github.<owner>`**：上传和 `dir` 没有外部所有者，强制只能造出假 owner 段；上传还有“开发完从上传换到
  `github:` 来源”的正当场景（ADR-0031 的换版本），卡死它逼人重装。
- **作者签名 / SBOM**：没有发布者身份体系，签名证明不了“谁”（ADR-0031 已写）。前缀 + 来源核对就是最小可行的“谁”。
- **自有域名名字空间现在就做**：见“暂不做”——没有真实用户，两条路都比 MCP 的贵，先欠着。

## 代价与风险

- **ID 更挤**：总长 63 不变（网关给插件网页的子域名是一段，由 ID 的点换成连字符而来，一段不超 63 是它的硬约束）。GitHub 所有者
  最长 39 字符，`io.github.` 占 10，剩下给名字的最少 13 字符。作者要挑短名字。
- **仓库搬到别的所有者名下 = 换 ID**：ID 安装后不可变，重装意味着数据不自动跟。同所有者内改仓库名、搬子目录不受影响（前缀只看
  所有者）。这和 MCP 注册表一致：名字空间绑定身份，不绑定仓库。
- **显示名和图标还是随便写**：本篇只堵 ID 冒充。第三方包可以叫“Immich Pro”、画一个像 Immich 的图标；辨认仍靠“未审核”标签和
  `provider`。要管到名字和图标得做相似度判断，误伤面大，不做。
- **官方插件被换到别人的仓库后，ID 冒充防护对它失效**：跑的从此是那个仓库的构建，升级也跟它。换版本预览醒目写明换成谁、
  不再是官方版（主人 2026-11-12 定，和上传同理）；新装的官方 ID 仍不可冒充。
- **App 四语**：新错误类别要补四种语言的文字（ADR-0043）；错误列表、HTTP 映射、日志各加一条。
- **已装插件不受影响**：规则只在新装的预览和安装入口查；升级和换版本不查（第 1 节），已装的不重新核对，官方索引照常。
