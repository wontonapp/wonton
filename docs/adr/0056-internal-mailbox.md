# ADR-0056 每个人一个不变的内部邮箱，应用发的信转进聊天

- 状态：已接受（2026-11-08，主人选定内部邮箱）；取代 [ADR-0022](0022-owner-identity.md) “邮箱和时区不兜底”里邮箱的部分，
  以及 [ADR-0030](0030-owner-profile-in-app.md) 里“邮箱交给插件”的部分

## 背景

主人 2026-11-08 在四个办法里选了 B：应用里永远只用一个不变的内部邮箱，改真实邮箱不影响任何应用（A 重启、C 现状、
D 禁改都没选）。要求：用现成的开源组件收信，不自己写 SMTP 服务器；找回密码的信必须收得到；不写迁移，官方插件下次
升级时换过来。

按邮箱认人的应用（Beszel、Linkding）和把邮箱存进账号的应用（Immich、Memos、Paperless）出问题，根子都是邮箱会变。
用户名本来就不变（ADR-0022，家人的也不变、不复用，ADR-0045），把邮箱钉在用户名上，问题就没了。

## 决策

### 地址

- **每个人（主人和家人）的内部地址是 `<用户名>@wonton.internal`**，跟用户名一起定下，永远不变。用户名的字符集
  （小写字母开头，`a-z0-9_-`）是邮箱本地部分的子集。
- `.internal` 是 ICANN 留给私有网络的顶级域，核心的插件别名本来就在 `wonton.internal` 下。查过的九个应用的校验器
  （Django、egulias、govalidator、PocketBase、`net/mail`、zod 等）都接受；它们都不查 MX，信只交给配置的 SMTP 服务器。
  地址必须带点：单段的 `alice@internal` 会被 Django、Nextcloud、Vikunja、PocketBase 拒掉。
- 插件自己的发信地址是 `<插件 ID>@plugins.wonton.internal`，和人的地址分开，插件 ID 和用户名重名也不撞。
- 好友（ADR-0051）在这台服务器上没有内部地址。

### 身份的取值

- OIDC 的 `email` 声明、代登录的 `{email}`、`lan.client` 的 `{email}`、容器里的 `WONTON_OWNER_EMAIL`，一律是
  内部地址；`email_verified` 为真（信确实收得到）。
- 因为永远有值，ADR-0022 的“主人没配邮箱，要邮箱的插件装不上”这条错误路径删掉，清单的 `webui.oidc.requires_email` 一起删。
- 认人仍然优先 `sub` / `{user}`（ADR-0022 不变）。
- 内部地址不变，按邮箱认人的应用也不会再断：**规范保持“插件不写对账代码”**，不需要改邮箱后重建容器、也不需要
  `plugin check` 查对账。

### 真实邮箱

- 资料页照旧能填能改（ADR-0030），核心存着，**不交给任何插件**：不进声明、请求头、环境变量和局域网账号。
- 留着它，是为了以后把重要通知转发到真实邮箱；改它不影响任何应用。

### 收信组件：Mailpit

- 核心组件 `mailpit`（MIT，Go，镜像约 15 MB，`axllent/mailpit` 固定版本），和 tusd 一样只在核心的私有网络里，
  另外接入申请了 `notify` 的插件网络，在那里的别名是 `smtp.wonton.internal`，SMTP 端口 25。
- **不认证、不加 TLS。** Go 写的应用（Gitea、Vikunja、Memos）在明文连接上不肯做 PLAIN 认证，要认证就得给每个应用配
  证书信任，Memos 还关不掉证书校验。插件网络本来就隔离，核心认插件一直按来源网段（ADR-0047，`notify`、`mcp` 都是），
  这里照旧：Mailpit 把来源 IP 写进最上面一行 `Received` 头，核心按网段认出是哪个插件。插件伪造的 `Received` 只能
  写在它下面，核心只看最上面一行。`From` 头不作为来源依据。
- **收件人在 RCPT 阶段就挡**：`MP_SMTP_ALLOWED_RECIPIENTS` 由核心按当前的人生成，只放
  `^(alice|bob|…)@wonton\.internal$`。外部地址、`plugins.wonton.internal`、不存在或已移除的人都回 550，应用当场
  报发送失败（失败即停，不悄悄丢）。家人加入、移除时核心改写这一项并重启 Mailpit（几秒；信存在卷上的 SQLite 里，
  `MP_DATABASE`，重启不丢）。
- 网页和 API 用 `MP_UI_AUTH_FILE` 的密码保护，密码由核心生成、只有核心拿着；插件网络里能连到这个端口，但读不了别的
  插件发的信（比如找回密码的链接）。
- 单封上限 `MP_MAX_MESSAGE_SIZE` 25 MB；`MP_MAX_AGE` 7 天兜底清理。

### 核心怎么把信送进聊天

- 核心订阅 Mailpit 的 websocket（新信事件），启动时和断线重连后再按 API 列一遍未处理的信，补上漏掉的。每封信投递成功
  才从 Mailpit 删掉；聊天服务不可用时留着，恢复后再投。不用 webhook：它默认一秒最多发一次，失败会不会重试没核实。
- **投给收件人本人的“Wonton”私聊**（每人一个，ADR-0045），不是 Bot 房间，也不是主人的私聊。一封信有几个内部
  收件人（To、Cc、Bcc 里的）就各投一份；只看 Mailpit 放行的信封收件人，不按 To 头猜。
- 消息由核心账号发，`m.text`（照常推送：信是发给这个人的，找回密码时人正等着），通知类别和插件通知同一个
  `plugin_notice`（ADR-0047），主人能在系统设置里一起关。结构化字段 `app.wonton.plugin_mail`：插件 ID、插件名、
  主题、正文、附件列表。纯文本 `body` 是“插件名：主题”加正文，给别的客户端和不认识这个字段的旧 App 看。
- **正文**：有纯文本部分用纯文本；只有 HTML 的，核心用 `html2text`（MIT crate）转成文本，链接保留成可点的地址。
  超过 4000 字的截断，原始 HTML 作为 `.html` 文件附在同一条消息后面。不渲染 HTML 本身：私聊不加密，HTML 里的
  远程图片会暴露“已读”，还要做一套消毒。
- **附件**：每个不超过 20 MB 的，核心上传成 `m.file` 跟在后面；更大的只列名字和大小。
- **频率**：和插件通知共用每个插件每分钟 10 封、每天 200 封的计数（ADR-0047）。信在 SMTP 阶段已经收下了，超了的
  核心丢弃，按 ADR-0047 的做法在主人私聊里说一次。

### 插件怎么用

发信算在 `notify` 权限里，不新增权限；安装页那一行写“给家里的人发通知和信”。申请了 `notify` 的插件额外拿到：

| 变量 | 值 |
|---|---|
| `WONTON_SMTP_HOST` | `smtp.wonton.internal` |
| `WONTON_SMTP_PORT` | `25` |
| `WONTON_MAIL_FROM` | `<插件 ID>@plugins.wonton.internal` |

规范写明：不配用户名和密码、不开 TLS / STARTTLS。各应用的写法（调研里核实过）：Paperless 的 `PAPERLESS_EMAIL_HOST`
不能是 `localhost`，用别名正好；Gitea `PROTOCOL=smtp`、不填 `USER`；Vikunja 不填用户名；Memos 不填用户名；
Nextcloud `SMTP_SECURE` 留空（Mailpit 不提供 STARTTLS，不会被自动升级）；Audiobookshelf 端口改 25、关 secure。

### 已装的插件

不写迁移。核心换上新取值后：

- 按 `sub` 认人的应用（Immich、Paperless、Memos 等）照常登录，账号里存的还是旧邮箱；插件升级前应用没有配
  SMTP，本来就不发信。
- 官方插件下一次升级时：配好 SMTP，初始化服务把应用里的账号邮箱改成内部地址一次（内部地址不变，以后不会再触发）。
  Beszel、Linkding 已经改成不按真实邮箱认人（2026-11-07），不回退。
- 核心升级到插件升级之间，Immich 详情页的局域网账号显示内部地址，应用里还是旧邮箱，照着登录会失败。官方插件和核心
  同一批发，窗口很短。

## 理由

- 邮箱不变，就不用任何“变了以后怎么跟”的机制：不重建、不对账、不标异常，比 A 少一整套核心逻辑，也不靠第三方插件
  作者自觉。
- 应用发的信本来就无处可去（都没配 SMTP），转进聊天以后，找回密码、Gitea 的通知、Paperless 的提醒第一次能收到。
- Mailpit 是唯一同时满足“记来源、能实时通知、RCPT 阶段按规则拒收、自动清理、许可证宽松、体积小”的现成组件。
  按来源网段认插件和 ADR-0047 一致，免掉了证书和凭据分发。

## 没选的做法

- **改邮箱后重启用到它的插件、插件写启动对账**：每个按邮箱认人的插件都要写对账，第三方插件作者不写就断；核心要
  多一套找出受影响容器、先渲染再替换、失败标异常的逻辑。
- **维持现状**：按邮箱认人的应用改邮箱就断，新插件只能靠作者自己注意。
- **邮箱一旦被插件用过就不许改**：换邮箱要先卸应用。
- **另起一个 `mail` 权限**：更清楚，但安装页多一行，用户多一个要懂的词。
- **Mailpit 开认证、每个插件一个账号**：Go 应用在明文上不肯认证，要给每个插件发证书和 CA；Memos 无法跳过证书
  校验，还得改它的信任库。按网段认插件已经够了。
- **Inbucket、MailCrab**：不检查凭据、记不下来源。**smtp4dev**：.NET，镜像 177 MB。**mox、maddy**：完整的公网邮件
  服务器，配置要 DNS 和 ACME，太重。**Haraka、Postfix**：要自己写投递流程。**Rust 的 SMTP crate**：等于在核心里
  自研 SMTP，而且都不活跃。
- **`home.arpa`、`.test`、`.invalid`、`.localhost`**：`.localhost` 按 RFC 6761 解析到本机回环；`.test`、`.invalid`
  字面意思是测试和无效，用户在应用里会看到；`home.arpa` 家用路由器的 DNS 可能会应答。
- **核心把 HTML 原样发进聊天**：要做 HTML 消毒，远程图片会暴露阅读状态；App 也要先能渲染。

## 代价与风险

- `notify` 的含义放宽：通知仍只发主人（ADR-0047），信可以发给家人。装了 `notify` 插件的主人，等于允许它给家人发信。
- 多一个核心容器，要接入每个申请了 `notify` 的插件网络。
- 靠 `Received` 头认来源：实施时要测清楚 Mailpit 写的那一行格式，并用测试锁住“只看最上面一行”。
- 应用里看到的是 `alice@wonton.internal`，不是自己的邮箱；有人会想往这个地址从外面发信，那不行。
- 以后接入的 PHP 应用如果用 egulias 的 DNSCheckValidation，会把 `.internal` 当保留名拒掉（Nextcloud 默认不用）。
- 内部地址只在这台服务器上有效；多服务器（ADR-0042）时每台各管各的，同名不冲突，信也不出服务器。
