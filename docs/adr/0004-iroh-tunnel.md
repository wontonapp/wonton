# ADR-0004 远程网络：iroh 1.x 应用内隧道

- 状态：已接受（2026-10-28），M0 验证

## 背景

家里的服务器通常没有公网 IP。可选方案的问题：

- Tailscale / Headscale 组网（Olares 的做法）需要系统 VPN，而 iOS 同一时间只能开一个 VPN，
  会和国内用户常用的代理软件冲突。
- FRP、Cloudflare Tunnel 等公网隧道让所有流量经过我们的服务器，带宽成本和暴露面都大，
  Cloudflare 在国内也不稳定。

旧 Lucy 用的 iroh 0.98 已停止维护。它的问题都出在应用层的用法上：事件队列无界泄漏、Android 每个
请求新建连接、iOS 会话从不关闭、6 秒硬性在线门禁、服务端不按设备 ID 授权。

## 决策

- 客户端核心和服务端核心都内置 iroh 1.x。App 内的本地代理把 Matrix 客户端请求和小程序 WebView
  的流量经隧道转发到核心网关。不占用系统 VPN。
- 局域网直连、P2P 打洞、中继兜底由 iroh 自动选择。
- 核心只接受已配对设备的 endpoint ID。
- 服务端节点纯部署，不开发：官方 `iroh-relay` 和 `iroh-dns-server` 镜像，访问控制用共享令牌加限速。部署安排见
  [GOAL](../GOAL.md) 的 M2 第 11 项。
- 中继节点列表由签名的目录文件下发（App 内置一份兜底），加节点不需要发新版 App。
- 隧道层参考 n0 官方的 dumbpipe（TCP 经 iroh 转发），不从零设计。
- 第三方原生 App 不经这条隧道，见 ADR-0021。

## 理由

- 应用内隧道不和用户的 VPN、代理软件冲突；P2P 优先让大部分流量不经过我们。
- 中继和发现服务是官方现成程序，各节点互相独立，随时可以加。

## 代价与风险

- 打洞失败时（运营商级 NAT、部分运营商限制 UDP），小程序页面、照片、视频全部经中继，带宽是主要成本，
  必须有限速和监控。
- 内地节点的域名需要备案。
- 隧道层代码量不大，但连接复用、断线重连、前后台切换必须写对，并有测试。

## 待验证（M0）

- 蜂窝网络下的直连比例和延迟。
- iOS 前后台切换后的重连表现。
- 与 matrix-rust-sdk、WKWebView、Android WebView 的集成方式（本地 HTTP 代理）。

## 验证结果（M0，2026-10-28）

实现在 `crates/wonton-tunnel`：服务端按 endpoint ID 白名单授权；客户端所有请求复用一条连接，断开后下一次
使用时自动重连；本地 HTTP 代理把每条 TCP 连接映射成一条隧道流（dumbpipe 的做法）。iroh 1.4.1，中继用 n0
公共中继。

### 行为

行为测试（`crates/wonton-tunnel/tests/tunnel/`，只走本机回环地址）覆盖并通过：

- 未配对的设备在握手后被服务端以错误码 403 关闭连接，请求到不了上游；吊销设备会立即断开它现有的连接。
- 错误分得开：未授权（HTTP 403）、连不上服务端（502）、服务端连不上上游（503），本地代理用
  `x-wonton-tunnel-error` 头标明原因。
- 连接复用：25 个 HTTP 请求只建一条 QUIC 连接。
- 服务端正常重启时，客户端立即知道连接断了；服务端崩溃、不发关闭帧时，靠 QUIC 空闲超时发现。两种情况下
  服务端恢复后，下一个请求都自动重连成功，客户端不用重建。

旧 Lucy 的问题逐条对应：状态用 `watch` 只保留最新值，没有无界事件队列；所有请求复用一条连接；客户端、
代理、服务端都有显式关闭，丢弃时也会关闭；不设在线门禁，连不上时由 iroh 判定失败（QUIC 握手超时，默认
30 秒）；服务端按远端 endpoint ID 授权。

### 实测

服务端在家宽（深圳电信）局域网里的一台 Linux 主机上，客户端是同一局域网里的其他机器。每轮用新的 endpoint
冷启动建连，记录建连耗时（含服务端确认授权），之后 10 秒内每 200 ms 一次的 ping 往返，以及 20 个经本地
代理的 HTTP GET（每个一条新 TCP 连接）。数值为中位数 / P90：

| 场景 | 轮数 | 走直连 | 冷启动建连 | ping 往返 | HTTP GET |
| --- | --- | --- | --- | --- | --- |
| 有线，只给服务端 ID（靠 n0 DNS 发现地址） | 10 | 10/10 | 1741 / 3817 ms，最慢 21.6 s | 1.2 / 1.8 ms | 1.5 / 2.5 ms |
| 有线，给出中继和局域网地址 | 10 | 10/10 | 5.1 / 5.9 ms | 1.1 / 1.7 ms | 1.6 / 2.6 ms |
| Wi-Fi，客户端开着代理 TUN，给出中继和局域网地址 | 5 | 5/5 | 15 / 39 ms | 4.2 / 16 ms | 6.0 / 8.9 ms |
| Wi-Fi，客户端开着代理 TUN，只给服务端 ID | 10 | 全部连不上 | 30 s 超时 | — | — |
| 强制只走中继（n0 新加坡 aps1） | 10 | 0/10 | 1054 / 1215 ms | 259 / 408 ms | 270 / 502 ms |

吞吐（经本地代理下载 4 MiB）：直连约 11.5 MB/s，跑满服务端的 100 Mbit/s 网卡；强制走中继只有 90–260 KB/s，
排队让往返时间从 0.6 s 涨到 4.8 s（这一次走的是 n0 美西 usw1）。

蜂窝网络的结果见下一节；手机经本地代理访问和前后台切换见最后一节“iPhone 真机”。

### 蜂窝实测（2026-10-28）

客户端是一台 Mac，经 iPhone 个人热点接入中国移动（深圳）蜂窝网络，有 IPv4 和 IPv6；服务端是家宽（深圳电信）
局域网里的另一台 Linux 主机，home relay 是 n0 新加坡 aps1。方法同上（`field-test.sh probe`），测量进程不走
本机代理。数值为中位数 / P90：

| 场景 | 轮数 | 走直连 | 冷启动建连 | ping 往返 | HTTP GET |
| --- | --- | --- | --- | --- | --- |
| 只给中继地址 | 10 | 10/10 | 6031 / 7781 ms | 78 / 125 ms | 68 / 114 ms |
| 预先给出直连地址 | 5 | 5/5 | 151 / 176 ms | 71 / 133 ms | 72 / 127 ms |
| 开着代理 TUN，只给中继地址 | 5 | 5/5 | 3449 / 5170 ms | 156 / 909 ms | 182 / 469 ms |
| 开着代理 TUN，预先给出直连地址 | 5 | 5/5 | 275 / 1189 ms | 84 / 262 ms | 77 / 140 ms |
| 强制只走中继 | 10 | 0/10 | 5183 / 5513 ms | 535 / 1011 ms | 636 / 1032 ms |

吞吐（经本地代理下载 4 MiB）：直连 6 次中位 2.3 秒（约 1.8 MB/s）；强制走中继一次 53 秒（约 80 KB/s）。

- 每一轮最终都走 IPv6 直连。
- 只给中继地址时，客户端先经中继连上，5–6 秒后才切到直连；预先给出直连地址时第一包就直连，建连降到
  0.15 秒左右。这台家宽路由器的 IPv6 不拦入站；换成拦入站的家庭网络，仍要经中继协调打洞。
- 强制走中继时，客户端在移动蜂窝下选到的 home relay 是 n0 美西 usw1（10 轮都是），吞吐那轮是德国 euc1，
  往返 0.5–2.8 秒。用 n0 默认的中继表时，客户端可能挑到很远的节点；自建后中继表只放我们的节点。
- 开着代理 TUN 时仍然走 IPv6 直连、没有绕行，但只给中继地址时抖动明显变大（ping P90 约 0.9 秒，最长 11 秒）；
  预先给出直连地址时基本不受影响。

### 结论

- 隧道的形态可行：直连时隧道本身的开销可以忽略，局域网 HTTP 往返 1–2 ms，吞吐跑满链路。
- n0 的 DNS 地址发现在国内靠不住：家宽下查一次要 1–20 秒，客户端开着代理 TUN（fake-IP DNS）时完全查不到。
  配对二维码必须带服务端的中继地址和直连地址，客户端要缓存上次连上的地址；自建 `iroh-dns-server` 只做兜底。
- n0 公共中继离国内太远：往返约 260 ms，吞吐只有几百 KB/s，照片和视频走不动。自建香港中继是 MVP 的前提，
  中继带宽要按“打洞失败时全部流量都经中继”预算。
- 家里路由器的 IPv4 NAT 映射随目标地址变化（iroh 报告 QAD 结果不一致），蜂窝侧通常也是运营商级 NAT，
  IPv4 打洞大概率失败；家宽和蜂窝都有 IPv6，跨网络直连主要靠 IPv6。蜂窝实测证实了这一点：每一轮都走 IPv6 直连。
- 代理 TUN 会干扰选路：在一台开着代理 TUN 的 Mac 上同时跑两端时，iroh 两次选中了经代理 UDP 出口绕行境外的
  “直连”路径（往返 80–700 ms），而不是不到 1 ms 的本地路径。国内用户的手机普遍开着这类代理，M1 要在真机上
  验证，必要时在选路时排除代理的 fake-IP 网段或优先局域网候选。蜂窝实测里开着代理 TUN 没有绕行，但抖动
  明显变大，预先给出直连地址后基本不受影响。
- 本地代理监听回环地址，同一台设备上的其他 App 也能连上并借用本机的配对身份。网关不能只凭隧道身份放行，
  仍要校验 Matrix 令牌和插件会话，或者给代理加会话令牌。

### 调整（2026-10-28）

主人决定开发和内测期先用 n0 的公共中继，自建节点移到 M2。n0 官方对公共中继的说明是：免费、限速、
适合开发和测试，没有可用性和性能保证。上面“自建香港中继是 MVP 的前提”改为：内测中打洞失败多、
经公共中继体验差时提前部署（#8）。配对二维码带直连地址（#16），不依赖 n0 的发现服务。

### 本地代理的会话凭据（#21）

上面的结论之一是本地代理可能被同机其他 App 借用。选了“给代理加会话凭据”，而不是在网关逐个校验 Matrix
令牌或插件会话：后者要让每个插件网页都带上网关能认的凭据，而 WebView 里的插件网页本身就不可信。

- App 的本地代理是 HTTP 正向代理（`ProxyAccess::Credential`），每次启动随机生成一份凭据（256 位），只交给
  本 App 的 WebView 和 HTTP 客户端。没带凭据的连接回 407，连隧道都不建；其他 App 拿不到凭据，也就借用
  不了配对身份。网关因此可以把隧道身份当作设备身份，规则见 ADR-0009 的验证结果（#21）。
- 两端 WebView 都把 HTTP 代理设为本地代理，`Host` 原样保留：
  - iOS 17 的 `WKWebsiteDataStore.proxyConfigurations` 只能配 HTTP CONNECT 代理，每条连接先 `CONNECT`，
    凭据用 `applyCredential`。
  - Android 的 `ProxyController` 对 http 地址发绝对形式的请求行。代理改写成源站形式，并让服务端回完一个
    请求就关连接，凭据不会随后续请求进入隧道。
- 代理只转发家里服务器基础域名下的地址（基础域名和它的子域名）。别的地址回 403（`foreign-host`），不建
  隧道连接，CDN、字体等外部资源和别的浏览流量不会被送回家。WebView 也只让这个域名走代理，外部资源直连。
- 不校验调用方的反向代理形态（`ProxyAccess::Open`）只留给开发工具和测试，示例默认用它；加 `--auth` 和 App
  一样。
- 验证：`crates/wonton-tunnel/tests/tunnel/local_proxy.rs` 覆盖了以下行为：
  - 没带凭据、凭据不对、`Bearer` 方案都被拒，隧道没有建连。
  - 绝对形式的请求到服务端时 `Host` 取自 URL、没有代理专用的头。
  - `CONNECT` 之后的字节原样转发。
  - 隧道错误照样回说明原因的 HTTP 错误。

  `deploy/dev/core/smoke.sh` 用带凭据的代理经隧道打开 Grafana，按 Android 和 iOS 两种方式各走一遍，都直接以
  主人进入；不带凭据的请求被拒（407）。

### App 内经隧道打开插件网页（#21）

客户端核心（`crates/wonton-client` 的 `home` 模块）内置隧道客户端和带会话凭据的本地代理，经 UniFFI 导出：
壳发 `ConnectHome { ticket }`、`AppForegrounded`，订阅 `HomeViewModel`（设备 ID、状态、路径、本地代理地址、
凭据和基础域名）。基础域名来自核心（`/_wonton/api/tunnel`），写在连接信息里。设备密钥和连接信息存在 App 的数据目录里，重启后自动重连。这组验证的连接信息由开发脚本
直接给出；App 扫码配对（`PairHome`，ADR-0009 的“接口：扫码配对”）后由核心按配对码生成。

- **iOS 17+**：`WKWebsiteDataStore.proxyConfigurations` 设为 `ProxyConfiguration(httpCONNECTProxy:)`，
  `applyCredential` 带上凭据，`matchDomains` 只放基础域名（实测它的子域名也走代理）。iOS 模拟器实测：WKWebView 打开 `http://app-grafana.wonton.localhost:18480/`，
  直接进入 Grafana 首页；同一个 WebView 打开 `/api/user`，返回 `login` 为 `owner`，`authLabels` 是
  `Generic OAuth`。
- **Android**：androidx.webkit 的 `ProxyController` 把 WebView 的代理设为本地代理，用反向绕过规则
  （`setReverseBypassEnabled`，名单是 `<基础域名>` 和 `*.<基础域名>`）只让家里的地址走代理。不能再加
  `removeImplicitRules()`：它对应的 `<-loopback>` 在反向模式下会把 `*.localhost` 排除出名单，实测 WebView
  因此直连 `*.wonton.localhost`，连接被拒。WebView 第一次请求不带凭据，收到 407 后由
  `onReceivedHttpAuthRequest` 交出凭据；只对代理自己的主机交，插件网页要认证时不给。Android 模拟器
  （API 36）实测同样以 `owner` 进入 Grafana（Grafana 日志里 WebSocket 的用户是 `owner`）。
  - Grafana 的 WebSocket 经 `CONNECT` 走代理，Chromium 对 ws 总是用 `CONNECT`。
  - 模拟器上从启动到首页通常 2–8 秒，偶尔卡 30 秒左右。卡顿时代理和网关都在 100 ms 内处理完，
    卡在 iroh 的路径层：模拟器虚拟网卡的 GSO 发送报 EIO，原因见下面的“手机上关掉 GSO”。
- **构建**：
  - wonton-client 引入 iroh 之后，iOS 静态库要链接 `SystemConfiguration.framework`。
  - libc 0.2.190 起只在 macOS 上提供 `in6_ifreq`，iroh 依赖的 netdev 0.46 在 iOS 上也用它，iOS 编译失败，
    所以 libc 固定在 0.2.189（见 `crates/wonton-client/Cargo.toml`）。上游修好后去掉。
  - Android 上没有调用 `iroh::dns::install_android_jni_context`，DNS 用 iroh 的备用公共服务器（日志会警告）。
    连接信息里给了直连地址时不受影响；靠中继和地址发现时要补上。
- 手机经本地代理访问、iOS 前后台切换后的重连：见下一节。

### iPhone 真机：经本地代理访问和前后台切换（#21，2026-10-28）

iPhone 16（iOS 27.2，Debug 构建，用主人的开发团队签名）和 Mac 连同一个 Wi-Fi；核心跑在 Mac 的 Docker 里
（`dev.sh up`，`WONTON_DEV_TUNNEL_BIND=0.0.0.0`），连接信息给出 Mac 的局域网地址和 n0 中继。核心镜像的代码是
main 上 #42 合并后的版本（`ddbeb67`）：`deploy/dev/core` 的编译缓存被各个 worktree 共用，镜像实际由 #42 的
分支编出，和合并后的 main 一致。App 用 `devicectl` 带 `WONTON_DEV_OPEN_WEB=1`、
`WONTON_DEV_RELOAD_ON_FOREGROUND=1` 启动：本地代理就绪后自动打开 Grafana，每次从后台回来都重新加载网页。
切后台是用 `devicectl` 打开“设置”，等若干秒再把 App 拉回来（方法见 `apps/ios/README.md`）。

- **经本地代理访问**：WKWebView 每条连接先发不带凭据的 `CONNECT`，收到 407 后换一条连接带上凭据重发。
  Grafana 经 OIDC 自动登录，以 `owner` 进入（核心日志里 OIDC 登录的用户、Grafana 日志里 Live WebSocket 的
  用户都是 `owner`）。
  启动到首页加载完成约 2 秒，WebKit 缓存为空时两条连接各下载约 3.7 MB 脚本，用 1.3 秒。
- **问题**：后台 30 秒左右再回来，请求全部挂住，30 秒后才失败，网页显示本地代理的 502。iroh 的直连路径
  空闲 15 秒、中继路径空闲 30 秒就被放弃：App 挂起期间服务端放弃了连接（服务端日志
  `no viable network path exists: last path abandoned`），关闭帧却到不了手机，手机要等自己的 30 秒空闲
  超时才发现。挂起明显更久时反而没事：手机的空闲超时在恢复时立刻触发，或者服务端已经忘了这条连接，
  对手机的第一个包回 stateless reset，手机马上重连。
- **修复**：核心收到 `AppForegrounded` 时调用 `TunnelClient::revalidate`，在现有连接上限时 1.5 秒做一次
  往返，没有回应就关掉它、立刻建新连接；检查期间新开的流等检查结果，不会落到失效的连接上。时限不按 QUIC
  的往返时间估计算：挂起期间积压的确认会把它拉高，实测局域网上估出 0.5–0.95 秒。iOS 壳在离开后台时就发
  `AppForegrounded`，不等 `.active`（实测晚约 0.4 秒），尽量赶在网页恢复后的第一个请求之前开始检查。
  慢路径检查的期限按 [ADR-0032](0032-connection-quality.md#2-保活) 放宽；这里的 1.5 秒是本节真机验证时的版本。
- **修复后**（同一台 iPhone，最终版本连续 6 轮）：

  | 后台时长 | 回来时连接的情况 | 隧道检查完成 | 网页重新加载完成 |
  | --- | --- | --- | --- |
  | 5 秒 | 仍然可用 | 10 ms | 0.44 秒 |
  | 30 秒 | 手机的空闲超时立刻触发，重连 | 31 ms | 0.56 秒 |
  | 30 秒 | 服务端已放弃，1.5 秒后换新连接 | 1.55 秒 | 1.95 秒 |
  | 35 秒 | 服务端已放弃，1.5 秒后换新连接 | 1.61 秒 | 2.17 秒 |
  | 35 秒 | 手机的空闲超时立刻触发，重连 | 179 ms | 0.69 秒 |
  | 60 秒 | 服务端已忘了这条连接，回 stateless reset，重连 | 780 ms | 1.25 秒 |

  修复过程中的几个版本又跑了 16 轮（后台 5–120 秒），隧道都在 3 秒内恢复，没有再出现 30 秒的挂起。其中在
  `.active` 才发 `AppForegrounded` 的版本有一轮，重新加载的请求抢在检查之前落到失效连接上，页面显示 502；
  改成离开后台就发之后没再出现。本地代理的监听套接字每次回来都还能用，没有遇到 Apple TN2277 说的挂起时
  被系统回收。
- **锁屏**（修复后的版本；核心用 `--no-cache` 从 main 的 `ddbeb67` 重新编译，重新起的 `wonton-e2e`）：主人
  锁屏约 4 分 50 秒后解锁，锁屏时云吞在前台。锁屏期间服务端在 30 秒后判定空闲超时，结束了连接；手机这边的
  iroh 没有自己发现：休眠时它的单调时钟停走，也没有收到 stateless reset。回到前台的限时往返 1.5 秒后判定
  连接失效、换新连接，新连接 1.2 秒后建好（平时几十毫秒，可能是 Wi-Fi 刚从休眠中恢复）。解锁后 3.6 秒隧道
  检查完成，5.9 秒网页以 `owner` 重新加载完成。切换期间有 3 个请求收到 502：1 个是检查开始前网页自己发出的
  （#45 的第一条），另外 2 个等到了新连接，却在新连接上被服务端复位（`stream reset by peer: error 1`）。
  网页本身没有出错。
- **遗留问题**跟踪在 #45：回到前台后最先发出的请求失败一次、偶发页面加载卡顿、换连接后请求被服务端复位、
  固定 1.5 秒期限在慢中继上可能误判。

### 手机上关掉 GSO（#154，iroh 1.4.1、noq-udp 1.4.0）

- **现象**：Android 模拟器（virtio 网卡）冷启动后发一条消息，停在“发送中”几十秒到几分钟，连接页却显示“直连 · 3 ms”。
  卡住时抓到的 UDP 只有几十字节的包来回，请求到不了服务端；回到前台通常能恢复。
- **根因**：网卡不支持 GSO 时（内核对没有校验和卸载的网卡和 IPsec 都这样）多包的 `sendmsg` 报 EIO。noq-udp 随后
  关掉这个 socket 的 GSO，但 iroh 的发送端把分段上限存在建连那一刻（`TransportsSender::max_transmit_segments`），这条
  连接之后每一批多包发送都 EIO，错误还被吞掉当作丢包。拥塞窗口再小也有两个包，所以多包的请求一直发不出去，单包的心跳
  和确认照常往返，QUIC 认为连接活着。之后建的连接读到关掉的 GSO，不再有这个问题：所以换连接（回到前台、空闲超时）就
  恢复，而每次 App 启动的第一条连接都可能中招。
- **决定**：客户端的 endpoint 关掉 GSO（`enable_segmentation_offload(false)`）。手机上行的流量用不上它省下的那点 CPU，
  也不用按平台分。服务端不动：它跑在 Docker 的 veth 上，veth 有校验和卸载；下行大文件才用得上 GSO。
- **对照**（模拟器 → 1k，局域网直连，每轮杀掉 App 冷启动，等 12 秒发一条，看“发送中”多久消失）：

  | 版本 | 各轮耗时 |
  | --- | --- |
  | 关 GSO 之前 | 31 秒、168 秒，另有两轮 311 秒内没等到 |
  | 关 GSO 之后 | 4、3、3、3、4 秒 |

### 卡住的连接（#154）

- **现象**：连接页显示“直连 · 3 ms”，请求却过不去。QUIC 只知道包有没有被确认，单包的心跳和确认还能往返时，连接
  算活着，路径和往返时间也好看，空闲超时不会触发。状态里的“已连接”是最后一次成功时留下的，没有谁再去确认。
- **决定**：客户端核心定时用 `TunnelClient::probe` 走一次真实的流：每 5 秒一次，限时 8 秒。没有回应就断开，状态变成
  断开、路径清空，随后退避重连（节奏见 ADR-0032）。和回到前台的 `revalidate` 不同，检查期间新请求照常走现有连接，
  所以时限可以放宽：判错的代价是断开正在传的流，中继的往返在负载下出现过 2.8 秒，大文件传输时还要排队。定时
  probe 固定 8 秒，只有前台 revalidate 按 ADR-0032 区分快直连和慢路径。服务端不认这台设备时不重试，等重新配对。
- **没解决的**：`probe` 只有几十字节，只丢大包的路径它查不出来。这种路径 QUIC 自己的 MTU 探测管（丢了就退回基础
  MTU），在转发器里只放行 300 字节以下的包时能复现卡住，但真实网络的基础 MTU 是 1200 字节。
