# ADR-0040 镜像加速：核心经加速地址按摘要拉 Docker Hub 的镜像

- 状态：已接受（2026-11-06）。方向由主人确认（见“背景”）；“只加速 `docker.io`”和“同时只用一个”已被 [ADR-0074](0074-registry-mirrors-per-registry.md) 取代（2026-11-09，主人已同意）

## 背景

国内主机大多连不上 Docker Hub。不少插件和核心自己用的镜像在 Docker Hub 上，装到一半卡在拉镜像，
出网代理（[ADR-0023](0023-egress-proxy.md)）帮不上：镜像由 Docker 守护进程拉，不经出口容器。代理插件
（[ADR-0039](0039-egress-proxy-plugin.md)）还多一个自举问题：mihomo 的官方镜像只发到 Docker Hub，装代理插件时还没有代理。

社区的通常做法是在 `daemon.json` 里写 `registry-mirrors`。这要 root，要重启 dockerd（所有容器跟着重启），
主人自己也很难判断哪个加速地址还活着：公开的加速服务换得很快。

主人 2026-11-06 定的方向：

- 设置里加一个开关和几个预置的加速地址，加一个“测速”按钮，小白用户也能自己打开。
- 地址名单放在官方索引的数据里，像模型服务商的名单一样，不写死在 App 里。
- 核心发现 Docker Hub 直连不通或者很慢，就在 App 里推荐打开，但不替主人打开。
- 经加速拉下来的镜像必须和官方摘要一致，不一致就拒绝并如实报错，不能悄悄换成别的镜像。
- 尽量不碰宿主的 Docker 配置。

## 决策

### 核心自己经加速地址拉，不改 `daemon.json`

核心拉镜像本来就经 Docker API 自己拉（`create_image`），不调 `docker compose pull`。打开加速后，
`docker.io` 上**按摘要固定**的引用改成从加速地址按同一个摘要拉：

```text
metacubex/mihomo:v1.19.33@sha256:9211…  →  拉 dockerproxy.net/metacubex/mihomo@sha256:9211…
```

- **摘要由 Docker 核对。** 按摘要拉取时，Docker 校验拉到的清单和每一层的摘要，对不上就失败。加速地址给不出这个摘要的内容，
  就拉不下来，换不成别的镜像。核心拉完再查一次本地镜像的摘要，和引用里的一致才用。
- **只加速按摘要固定的引用。** 只写标签的引用（`foo:latest`）没有可核对的东西，加速地址给什么都会被收下，所以一律直连。
  官方索引的插件都按摘要固定（`plugin check --official` 检查）。
- ~~**只加速 `docker.io`。** ghcr.io、quay.io 等其他仓库照旧直连。~~（已被 [ADR-0074](0074-registry-mirrors-per-registry.md) 取代：按仓库主机各一份名单，ghcr 和 quay 一起加速。）
- **拉不下来就报错，不改成直连。** 错误写明加速地址和 Docker 的原文，提示去设置里测速、换一个。主人打开加速，
  就是因为直连不通，悄悄回退只会让错误变成长时间的卡住。
- **建容器时用实际拉到的引用。** 实测两种存储（见“实测”）：containerd 存储里，给拉到的镜像打上原来的标签后，
  原引用（`名字:标签@摘要`）就能解析；老的 overlay2 存储只按拉取时的仓库名记摘要，打标签也解析不了原引用。
  核心统一按“原引用能解析就用原引用，否则用加速地址的引用（`加速地址/仓库@摘要`）”建容器。`docker ps` 里看到的是
  加速地址，如实反映镜像从哪里来。
- **核心自己用的 Docker Hub 镜像**（出口容器的 gost 等）也按这条路拉。

没选：

- **写 `daemon.json` 的 `registry-mirrors`：** 要 root，要重启 dockerd，Docker 只对 `docker.io` 生效且失败时悄悄回退直连，
  核心也无法知道这次到底经没经加速。
- **用 ghcr 上的同摘要副本：** 要我们替每个上游维护一份副本，还要能在插件仓库的 Actions 里复制；只解决我们自己的插件。

### 设置：一个开关，加一个地址

- 设置里一个开关，打开后选一个地址：官方索引给的预置地址，或者主人自己填的（比如云厂商给账号单独发的加速地址）。
  ~~同时只用一个：加速出错要知道是哪个出的错。~~（已被 [ADR-0074](0074-registry-mirrors-per-registry.md) 取代：按名单顺序换站，全失败时错误里逐站列出失败。）
- **地址名单在官方索引里。** `wonton-store` 维护一份 `registry_mirrors` 名单，和推荐的插件、模型服务商一样随索引更新；
  名单失效不用发 App。索引读不到时只能手填。
- **测速：** 核心对每个地址按摘要取一个固定的小镜像的清单，报延迟、能不能用和失败原因（403、401、超时、证书错误等）。
  测的是核心容器到加速地址，和 Docker 守护进程拉镜像的路径一样出宿主的网卡，不经出口容器。

### 什么时候推荐打开

核心开机后和测速时，按摘要取一次 Docker Hub 上同一个小镜像的清单：连不上，或者 5 秒内没取到，就在设置里标出“推荐打开”，
插件因为 Docker Hub 拉不下来装失败时，错误里也提示打开。核心不自动打开：选哪个地址等于决定信任谁的服务。

### 风险由谁承担

加速地址看得到主机拉了哪些镜像，拿不到别的东西，也换不了镜像内容（见上）。确认文字写明这一点，主人决定。

## 实测

2026-11-06，两台国内主机，都没有代理：一台 Docker 28.2.2（overlay2 存储），一台 Docker 29.7.2（containerd 存储）。
按摘要取 `metacubex/mihomo` 的索引清单（`sha256:9211…82e9c`），再下载 amd64 最大的一层（23.3 MB，最多等 30 秒）。
请求带 Docker 的 User-Agent，跳到别的主机时不带 Authorization，和 Docker 一样。

| 地址 | 取清单 | 摘要对 | 下载速度 | 说明 |
| --- | --- | --- | --- | --- |
| registry-1.docker.io | 超时 / 连接被拒 | | | 直连不通 |
| dockerproxy.net | 0.7–2.3 秒 | 是 | 0.3–1.9 MB/s | 两台都能用，最快 |
| docker.1panel.live | 3.5–4.5 秒 | 是 | 0.2–1.2 MB/s | 能用 |
| docker.1ms.run | 1.9–4.1 秒 | 是 | 0.06–0.12 MB/s | 能用，很慢 |
| docker.m.daocloud.io、docker.xuanyuan.me、docker.nju.edu.cn | 403 | | | 有白名单或者要登录 |
| hub.rat.dev、docker.hlmirror.com | 401 | | | 要登录 |
| docker.kejilion.pro、registry.dockermirror.com | 525 | | | 后端挂了 |
| lispy.org | 429 | | | 限流 |
| 其他 6 个常见地址 | 解析不到 / 超时 / TLS 错误 | | | 已停用 |

同一天各测了一次，速度在两次之间相差几倍。所以名单要放在能随时改的索引里，App 里要有测速。

用 `docker pull dockerproxy.net/metacubex/mihomo@sha256:9211…`（144 MB，28 秒）拉下来以后：

- containerd 存储：`docker tag` 成 `metacubex/mihomo:v1.19.33`，原引用 `metacubex/mihomo:v1.19.33@sha256:9211…` 能解析，
  `docker create` 用原引用直接建，不再去拉。
- overlay2 存储：打完标签，原引用和 `docker.io/metacubex/mihomo@sha256:9211…` 都解析不了，只有标签和加速地址的引用能解析。

## 代价与风险

- 公开加速服务说停就停，名单要有人维护。名单在索引里，CI 里可以定期测，测速也让主人自己能看出来。
- 加速地址知道这台主机装了哪些插件。
- 只写标签的第三方插件得不到加速。插件规范里写明：Docker Hub 上的镜像按摘要固定才能经加速拉。
- 安装脚本在核心起来之前拉系统镜像（Hydra、tusd 在 Docker Hub 上），这一步得不到核心的加速。
