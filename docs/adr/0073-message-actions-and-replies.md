# ADR-0073 消息菜单和回复：菜单项由核心按消息给，回复、转发、撤回都用 Matrix 的标准做法

- 状态：已接受（2026-11-08）

## 背景

#745 要长按消息的菜单里有复制、回复、转发、删除，并且能右滑回复。协议里的菜单项原本只有复制。哪条消息能回复、能撤回，取决于
发送状态、消息类型和本账号在房间里的权限，这些只有核心知道。

## 决策

### 1. 菜单项由核心按消息给

`TimelineMessage::actions` 按菜单顺序列出这条消息能做的事：`Copy`、`Reply`、`Forward`、`Redact`。壳照平台习惯画（iOS 的系统
上下文菜单，Android 自绘菜单），不认识的菜单项不显示。核心的规则：

- 回复：已经发出（有事件 ID），不是已撤回的、不是确认卡片。
- 转发：已经发出的文字和图片。
- 撤回：自己发出的；或者本账号在这个房间的权限能撤回别人的消息（Matrix 的 power level）。已撤回的没有。
- 没发出去的消息照旧用“重发”“取消发送”，不进这个菜单。

### 2. 回复用 Matrix 的 `m.in_reply_to`

- 发送时由壳显式给出回复的是哪条（`SendText`、`SendImage` 的 `reply_to`），核心不存“当前在回复谁”的隐式状态：壳显示的引用就是发出去的引用。
- 引用由核心给（`ReplyQuote`、`QuotedMessage`）：文字摘要、图片缩略图、已撤回、解不开等类别，壳按类别画，不自己摘要原消息。
  原消息不在本地时核心经 matrix-sdk 向服务器取，先给 `Loading`，取不到给 `Unavailable`，不伪装成已取到。
- 菜单里的 `Reply` 自带引用，壳进入回复状态时直接画它。
- 回复对象和正文一起进草稿（matrix-sdk 的 `ComposerDraftType::Reply`），换房间、杀 App 再进还在，发送成功后清掉。
- 点引用跳到原消息依赖 ADR-0071 的时间线定位，不在这次。

### 3. 滑动回复

消息有 `Reply` 时，两个平台都允许右滑这条消息：滑过阈值给一次触感反馈，松手进入回复状态，输入框获得焦点。没有 `Reply` 的消息滑不动。

### 4. 转发是照原样再发一条

Matrix 没有标准的“转发”关系，各客户端都是把内容重新发一遍。核心照原样发到目标房间：文字带格式，图片复用原来的媒体地址和加密信息，
不重新上传；不加“转发自”标记。一次转发到一个房间，壳随后打开目标房间，进展看那里的本地回显和发送状态。

### 5. 撤回是 Matrix 的 redaction

对所有人生效，所有设备上都变成“已撤回”。壳在发出前请主人确认。Matrix 没有“只在自己这里删除”，不做。

## 考虑过的做法

- **核心记住“正在回复谁”，发送时自动带上**：壳少传一个参数，但壳显示的引用和实际发出的可能不一致（比如设置回复的操作失败了），
  发送时显式给出更可靠。
- **转发时带“转发自某某”**：没有标准字段，别的 Matrix 客户端看不懂，只能写进正文，会污染原文。
- **编辑消息一起做**：输入框要多一种“编辑中”状态，和回复、草稿互相影响，单独做。

## 代价与待验证项

- 把加密房间里的图片转发到不加密的房间，图片的解密信息会随消息进入那个房间，等于把图片发到了那里；这和主人手动重发一样，不另外提示。
- 回复别的客户端发来的旧格式回复（带回退正文）时，正文里的回退部分要由核心去掉，实现时用真实的 Element 消息验证。
