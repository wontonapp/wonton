# ADR-0058 Agent 的话题会话：都能干活，互相知道对方在做什么，改同一个文件时排队

- 状态：已接受（2026-11-07）；“核心和协议不改”、话题名字的取法和“主对话里一行提示”的格式已被 [ADR-0088](0088-side-chats.md) 取代

## 背景

主人想在和 Agent 的聊天里另开话题（Matrix 的 thread），和主对话并行做别的事，而且：
- 话题也要能干活，不只是旁问；不支持只读模式的 Agent 也要有话题；
- 主对话要自己知道话题做了什么，不用人手动带回；
- 不重复干活，也不抢资源（同一个文件被两边同时改）。

ACP 的一个 Agent 进程可以开多个会话（`session/new`），每个会话各自一轮一轮地跑。桥（wonton-acp-bridge）在 Matrix 和
ACP 之间，看得到每个会话的请求、回复、工具调用（含 `locations`）和权限请求（`session/request_permission`）。

## 决策

所有这些都在桥里实现，对所有 ACP Agent 一样有效。~~核心和协议（`wonton-protocol`）不改；`wonton-matrix` 只放开
消息所属的话题根（见“前提”）。~~ App 一侧的话题界面和协议改动见 ADR-0088。

### 会话和工作板

- 一个房间里有一个主会话（主对话）和若干话题会话，都是同一个 Agent 的 ACP 会话，都能干活。话题的第一条消息开一个新会话。
- 桥为每个房间维护一张**工作板**，每个会话一行：名字（主对话，或按 ADR-0088 第 1 节取的旁聊标题）、在做什么（用户最近一次的要求）、
  状态（进行中、等你确认、空闲、已结束）、最近一轮的结论（Agent 这一轮最后回复的前两三行）、这一轮改过的文件（ACP 工具调用里
  类别为 edit、delete、move 的 `locations`）。只记结论和状态，不记过程。工作板存在桥的数据目录，重启后恢复。

### 互相知道

- **每轮开头注入动态**：任何会话开始新的一轮时，桥在用户这句话前面加一小段“其他会话的动态”：从这个会话上一轮到现在，工作板上
  别的会话的变化（谁做完了什么、改了哪些文件、现在在做什么）。只在一轮开头加，不打断正在进行的一轮。
- **主对话里一行提示**：话题的一轮结束时，桥在主对话里发一条结果行（格式见 ADR-0088 第 1 节，取代原来的纯文字 `m.notice`），
  点开就是那个话题。主对话的一轮结束时不往话题里发，话题下一轮开头会带上。
- **话题开局**：话题第一轮的说明里有话题起点那条消息及它前面最多 6 条（标明是主对话的片段、仅供参考）、当前的工作板、分工规矩
  （“只负责这个话题里用户要的事；主对话和其他话题在做的事不要接着做；要碰它们正在改的文件，先停下问用户”）和用户的第一句话。

### 改同一个文件

- 桥记一张“正在改的文件”表：一个会话这一轮改过的文件，到这一轮结束后 10 分钟内都算它在改。
- **Agent 改文件前会问权限时**：另一个会话要改表里的文件，桥不自动批准，弹确认卡片写明谁正在改哪个文件，三个选项，默认（排第一）
  是**等它做完再改**：桥先不回答 Agent，等对方这一轮结束后自动批准。另两个是“现在就改”和“不改”；被拒绝时 Agent 收到原因。
- **Agent 改文件前不问时（全自动模式）**：桥事先拦不住，发现两个会话改了同一个文件就在两边各发一句提示，并写进双方下一轮的动态。
  为此话题会话一开，桥就尽量用 `session/set_mode` 切到“改前先问”的模式；Agent 没有这种模式时，在话题里如实说一句
  “这个 Agent 改文件前不会问，只能事后提醒冲突”。
- 执行命令（类别 execute）桥不知道会碰哪些文件，不排队，只写进工作板。

### 上限

- 同时活跃的话题最多 3 个，第 4 个排队，并在话题里写明在排。
- 话题空闲 30 分钟自动结束：结论留在工作板上，Agent 支持 `session/close` 就关掉会话。用户在话题里发 `/wonton end` 手动结束。
- 不给话题做 worktree 隔离：主人要话题和主对话处理同一批东西，隔离之后两边各改各的副本，反而要合并。

### 前提

- `wonton-matrix` 的消息带上它所属的话题根（`m.relates_to` 里 `rel_type: m.thread` 的 `event_id`），桥按话题把消息分给会话；
  桥回复话题里的消息时也发进同一个话题。
- App 按 Matrix 标准的 thread 显示话题；主对话里那行提示点了能跳进话题。

## 考虑过的做法

- **Meta Muse**：同一个 Agent 加一份跨对话的记忆，主对话和旁聊都“知道”对方，不把旁聊的消息贴回主对话；它不跑代码，没有改文件冲突
  （Meta 帮助中心《How to get started with Muse》，2026-09-11 快照）。同家的 Muse Code 相反，旁聊读得到主对话，主对话看不到旁聊
  （ai.developer.meta.com 的 side chats 文档）。
- **Grok**：会话彼此独立，靠记忆把事实带进别的会话；在 X 上 @Grok 派活时帖子里只回“收到”，过程留在 Bot 自己的会话里（docs.x.ai 的 Grok Bot 文档）。
- **Claude Code agent teams**：共享任务表、认领时加锁，成员每轮结束把结论发给主会话；两个成员改同一个文件会互相覆盖，官方不加锁，
  靠分工（Claude Code 文档）。“每轮交回结论”和“分工规矩”取自这里。
- **Cursor、Devin**：要写的会话各自隔离（worktree、独立虚拟机），只读的共用工作区。没有一家做通用的文件锁。没选隔离，原因见“上限”。
- **只读旁问、手动带回**：第一版设计，主人否了：话题也要能干活，主对话要自己知道。
- **把话题的过程逐条转进主会话**：没有一家这么做，会把主会话的上下文挤满；只交回结论和状态。

## 代价与待验证项

- 每轮开头的动态占上下文；话题多、改动多时要截短（只列最近的变化和文件数）。
- 全自动模式的 Agent 只能事后提醒，冲突已经发生。
- 排队靠 Agent 等权限请求不超时；Agent 自己对权限请求有超时的，等太久会当成拒绝，要实测各家的行为。
- 同一个 Agent 进程并发跑多个会话，内存和模型额度随话题数增加，上限 3 个是估计值，按实测调。
