# ADR-0124 客户端渲染层统一 React：PWA 先做，Electron 后做，核心仍是厚 Rust

- 状态：已接受（2026-11-26 主人拍板；2026-11-27 改定网页和 TLS 都在家里，见第 5 节）。P1 指第一期：M2 的 PWA 内部预览（团队 + 愿意试的家人）；未定项见文末“待主人拍板”。
- 部分取代：[ADR-0005](0005-native-clients-thick-core.md) 的客户端 UI 选型（桌面 Compose Multiplatform、Web 的 Compose 编译到 Web）、
  [ADR-0029](0029-platform-material.md) 的“每个客户端都套 iOS/Android 平台材质”、
  [ADR-0120](0120-dumb-shell-pages.md) 的“每种组件每个壳各实现一次”。各自保留什么见“和现有 ADR 的关系”。
- 关联：[ADR-0081](0081-local-agent-host.md)（Electron 包里的本机 Agent 主机和本机服务）、
  [ADR-0033](0033-plugin-tabs.md)（插件网页仍在 WebView）、[ADR-0043](0043-app-languages.md)（界面文字）、
  [ADR-0026](0026-design-system.md)（令牌）、[ADR-0062](0062-desktop-vm-host.md)（Mac/Windows 宿主虚拟机）。
- 原型：11-07 的 Electron + React 壳（分支 `scratch/desktop-proto`，原 ADR-0068，未合入 main）验证了“核心旁路进程 + 帧 + 只渲染 ViewModel”的形态，
  仍然成立的部分见“原型”；分支已删，结论已并入，不再引用本机路径。

## 一句话

浏览器和桌面用同一套 React 渲染层，核心仍是厚 Rust：Web 上核心跑在服务器端每用户一个的独立容器里，Electron 里核心跑在本机旁路进程里；
界面只渲染 ViewModel、只发 Action，不碰网络、存储和业务逻辑。

## 背景

主人 2026-11-26 早会定了四件事：

1. 客户端技术栈固定 React。
2. 第一期先做 PWA：main 一合并就自动部署，浏览器打开就是最新版，不用总打包；方便实时预览和调试，像 Agent 应用那样在网页里选元素标注。
3. 桌面壳用 Electron + React，桌面端以后做，形态像 Alma：不只是界面，还带装在这台电脑上的服务，方便手机远程控制这台电脑。
4. Electron 三平台一起，第一期只做 PWA；GOAL、ARCHITECTURE 和 ADR 跟着改。

[ADR-0005](0005-native-clients-thick-core.md) 定的是“iOS SwiftUI、Android Compose、桌面 Compose Multiplatform，维护两套 UI”，
Web 则计划在 M3 把 Compose 编译到 Web（Kotlin/Wasm），核心在服务器上、浏览器经 WebSocket 收发。
[ADR-0029](0029-platform-material.md) 按平台画材质的前提只在 iOS/Android 成立。
[ADR-0120](0120-dumb-shell-pages.md) 想让核心发页面描述、每个壳把每种组件各实现一次；渲染层一旦统一，壳的数量和实现归属都变了。

这份 ADR 只定渲染层、核心放在哪、预览通道和它与旧 ADR 的关系；这期不动原生移动端，去留另定；不定聊天界面和远程控制的协议。

## 主人已定（2026-11-26、11-27）

- 核心放服务器端、每用户一份，不编译到 wasm。
- iOS 的 PWA 推送 P1 就做，要求用户把 PWA 添加到主屏幕。
- 设计沿用移动端令牌，但桌面不照搬手机的交互和比例，按桌面重做。
- 11-27 改定：网页不部署在中继。React 前端包和 TLS 都在家里，用这家的家名子域名，中继只按 SNI 转发加密字节。
- main 合并即更新保留：家里核心自动拉我们签过名的最新前端包，验签通过才换。
- 手机 App 照旧先打洞。
- Electron 第一版只带客户端；本机 Agent 主机和被控端第一版不带，以后做时默认关。

## 决策

### 1. 渲染层统一 React，界面不做业务

- Web 和 Electron 共用一套 React + TypeScript 渲染层，未来落在 `apps/web`（PWA）和 `apps/desktop`（Electron 壳），
  共用 `apps/web` 的界面代码。本期不动原生移动端（`apps/ios`、`apps/compose`），去留另定。
- 渲染层只有三件事：把 ViewModel 画出来、把用户操作发回去、调用壳提供的平台能力（窗口、剪贴板、选择文件、通知权限）。
  网络、Matrix、iroh、SQLite、推送登记、重试和业务状态全在 Rust 核心里。
- 所有 ViewModel 和 Action 类型来自 `crates/wonton-protocol`，渲染层的 TypeScript 类型由 Rust 生成，不手写第二份。
  帧协议本身也在 Rust 侧定义和测试。
- 渲染层允许保留的本地状态只有：滚动位置、输入框里正在合成的文字、选择与焦点、窗口尺寸、还没被核心确认的乐观回显。
  房间列表缓存、未读数、重试逻辑不算本地状态。

### 2. 核心仍是厚 Rust，Web 和 Electron 只换核心的位置

- 原生移动端继续在进程内用 UniFFI 嵌核心，接口仍是 `dispatch(Action)` 和 ViewModel 流。
- Web 和 Electron 用同一个 `wonton-client-host` 二进制：它链接 `crates/wonton-client`，加一层换行分隔的 JSON 帧，两种传输：
  - Electron：Electron 主进程拉起本机子进程，stdin/stdout，一行一帧；渲染进程经 preload 只拿到 `send`、`onMessage`、`onClose`。
  - PWA：服务器上每个用户一个独立容器（不是每个窗口一个，也不在核心容器里，见第 3 节），浏览器窗口经这家网页地址的 WSS 连同一份核心。
- 两种传输的帧完全一样；换传输不动渲染层，也不动核心。
- 浏览器永远拿不到 Matrix 令牌、设备密钥和 SQLite 存储。

### 3. PWA 的核心放在服务器端、每用户一份，不编译到 wasm

主人 11-26 选定的方案，理由和别的做法见“核心放在哪”。具体形态：

- 每个用户在服务器上只有一份网页核心，它是一台独立的 Matrix 设备：核心为它建数据目录、SQLite 存储和 Matrix 登录；同一用户的所有窗口、不同电脑的浏览器都连这份核心，不按窗口复制核心；第一次从网页配对时创建，之后配对只是授权新浏览器连上同一份核心，不新建核心。浏览器只拿到一个 HttpOnly 的授权 Cookie（只属于这家的网页地址），WSS 升级也只带它，不另发令牌（谁签、谁验见第 5 节“授权凭据”）。
- 和 [ADR-0009](0009-identity-pairing-sso.md) 的设备模型偏差：0009 是“每次安装生成密钥对、配对即一台设备”。网页反过来：每个用户只有一台网页核心 Matrix 设备，浏览器不是新设备，而是核心下的一条授权。设备列表分两层：网页核心一条设备，下面挂授权条目（浏览器名、首次配对、最后活跃）；吊销一条只断那个浏览器，吊销核心才删设备、断所有授权和窗口。0009 继续管手机和桌面 App 的设备身份，不改。
- 每个浏览器授权一条独立凭据：Cookie 只代表这一条授权，核心按（授权, 窗口）管理连接；授权可单独吊销（笔记本被偷只吊销它），不影响同一用户别的浏览器。配对、登出都走核心的 `/api/web-auth/*`（第 5 节）。
- 窗口 id 的作用域是 `(AuthorizationId, 连接序号)`：帧宿主在每条授权下分配、单增不复用，跨浏览器不撞；未知或过期窗口返回 `WindowGone`。
- 每个窗口一个连接、一个 `WindowId`，只带自己的导航栈和当前页等视图状态；聊天、房间、未读、设置这些共享数据只有一份。
- **网页核心是独立容器，不是核心容器里的子进程。** 每个用户一个容器，里面只跑 `wonton-client-host`，由核心经 Docker API 按用户建删（和 [ADR-0021](0021-third-party-clients.md) 的入口容器同一种管法，镜像随核心发布、同一个 digest）：
  - 不挂 Docker socket，非 root，`cap_drop: ALL`、`no-new-privileges`、根文件系统只读、限内存和 CPU；只挂这个用户的数据目录 `core/home/<用户名>/web/`（核心建目录时按 [ADR-0011](0011-security-model.md) 的挂载规则逐级检查）。
  - 它和手机一样是一台已配对设备：经 iroh 隧道连回本机核心，网关按设备身份认它，不为它另开认证路径。每个网页核心容器一个自己的内部网络，上面只有它和核心：它只够得着核心的隧道端口，核心经这个网络把浏览器的连接转给它，别的用户的容器连不到它；不进 `core` 网络（Hydra 管理端口、Tuwunel），也不和入口容器、连接器同网。
  - 浏览器发来的帧只在这个容器里解析（XSS、扩展、被改过的前端都能发任意帧）；核心只在入口专用监听（ADR-0021 的 8484）上做 HTTP 升级和查授权，然后转字节，不解析帧。这个容器被攻破，拿到的是这个用户的网页设备身份和数据，和偷到他的一台手机相当；拿不到 Docker socket，碰不到别的用户。
  - 为什么不用子进程：核心容器挂着 Docker socket，攻破即宿主 root（ADR-0011）；ADR-0021 已定面向公网的 TLS 和协议解析不进核心，浏览器发来的帧同样是外面可控的输入。把浏览器可控的帧交给核心容器里的子进程，等于退回这条线；[ADR-0015](0015-small-components-standard-interfaces.md) 的“一个组件只做一件事”也指向独立容器。代价是每用户多一个容器的开销，核心多一类要建、删、回收的容器。
- 网页核心在设备列表里可见、可吊销；吊销核心时删容器、删设备、所有授权和窗口失效。每用户一份核心，不按会话数封顶；窗口/连接上限和回收时间待拍板。
- 默认停在最近一次 ViewModel 快照上重连；没有本地业务状态，离线时只能看最后一屏和“重连中”。
- P1 做 Web Push（iOS 要求先把 PWA 添加到主屏幕）：按 RFC 8030/8291、VAPID 发系统通知；没添加主屏幕的退化成应用内未读。

### 多窗口

- 每个用户一份核心、所有窗口共用；聊天、房间、未读、设置这些共享数据只有一份，只有导航栈、当前页、媒体提示这类视图状态按窗口。
- 理由：Home/Chat/Unread/timeline 的订阅每次独立，各窗口可以各自订阅；页面导航（`PagesLink`、`PageAction::OpenPage`/`ClosePage`）如果全局一份、`dispatch` 不带窗口，两个窗口会互相顶页面，所以导航状态按窗口。
- 决策：`WindowId` 按（授权, 连接序号）分配、单增不复用；`PagesViewModel` 的导航字段拆成每窗口 `PageWindowViewModel`；`PageAction` 和帧带窗口；窗口过期返回 `WindowGone`。原生移动端用固定默认窗口。
- 实施拆分、测试和估时见 [#1111](https://github.com/wontonapp/wonton/issues/1111)。


### 4. Electron 是本地旁路进程，不是网页套壳

- Electron 主进程拉起本机的 `wonton-client-host` 子进程，客户端核心直接走 iroh 隧道，和手机一样。
- 渲染进程开 `sandbox`、`contextIsolation`，关 `nodeIntegration`；preload 只暴露三个函数；sidecar 从 `process.resourcesPath` 启动，
  不经 shell。打包开齐 Electron fuses（关 RunAsNode、NODE_OPTIONS、inspect 参数，开 Cookie 加密、只从 asar 加载、asar 完整性校验），
  安装包和自动更新都签名。
- 包里有三个角色，各自进程、各自隧道身份、各自开关（[ADR-0081](0081-local-agent-host.md)）：客户端、本机 Agent 主机、被控端。Electron 第一版只带客户端；本机 Agent 主机和被控端第一版不带，以后做时默认关。
  React 渲染层只是客户端角色，看不到另外两个身份和令牌；被控端的状态经核心转给界面显示。
- [ADR-0081](0081-local-agent-host.md) 的“电脑被手机远程控制”由被控端实现，协议另写 ADR；那份 ADR 固定它装在同一个包里的位置和独立的身份、开关。
- 第一版只启客户端；托盘常驻，退出就停 sidecar；登录自启可选。

### 5. 网页和 TLS 都在家里：家名子域名、签名的前端包，中继只按 SNI 转发

- 主人 11-27 改定（参照飞牛 FN Connect：每台 NAS 一个子域名和证书，网页由 NAS 自己提供）：网页不部署在中继；React 前端包和 TLS 都在家里，中继只转加密字节。
- **地址和证书**：每家的网页版在 `https://web.<家>.<域名>`（[ADR-0021](0021-third-party-clients.md) 的家名；主人用自己的域名时是 `web.<后缀>`，[ADR-0089](0089-https-own-domain.md)）。`web` 是核心保留的标签，插件不能占。证书就是 0021 的 `*.<家>.<域名>` 通配证书：钥匙由核心生成、只在家里，lego 经家名服务的 acme-dns 做 DNS-01，不为网页另签。
- **怎么到家**：浏览器只认这一个地址，走 0021 的公网入口：
  - 主人配了路由器转发或自己的服务器（[ADR-0090](0090-public-access.md)）：名字指向家，浏览器直连。
  - 否则经我们的中继：frps 读 ClientHello 里的 SNI，把加密字节原样交给这家的 frpc 连接器。中继不持证书。
  - 两条路都在家里的入口容器终止 TLS，再进核心的入口专用监听（0021 的 8484）：静态文件和 `/api/web-auth/*` 由核心处理，`/ws` 查过授权后转给这个用户的网页核心容器（第 3 节）。
  - 不要求这家有公网 IP 或端口映射；要有家名（在家名服务注册）或主人自己的域名，两样都没有就用不了网页版，App 写明原因。
  - P1 不做在家走局域网和 WebRTC 打洞：局域网入口是另一个名字 `web.lan.<家>.<域名>:8483`，换名字就换了 origin，Cookie、Service Worker 和推送订阅都不通用，所以在家也经公网名字。手机 App 和 Electron 经 iroh 照旧按局域网、直连、打洞、中继的顺序选路。
- **和 #1097（入口云部署）的接口**：云端复用它已有的 frps（443 读 SNI、带 PROXY v2 转发）、家名服务（注册、写 A/通配/CAA 记录、返回 acme-dns 地址）、PowerDNS/dnsdist 和 acme-dns，不为网页加组件。家里这侧缺两样：核心的 frpc 只登记 `<家>.<域名>` 一条，要再登记 `*.<家>.<域名>`（#1097 的名字归属钩子已接受“家名加它的通配”这两条，和插件子域名是同一件事）；入口容器公网前端的 `crt-list` 加上 `web` 标签。
- **前端包：谁签、怎么拉、失败怎么办**（main 合并即更新）：
  - 谁签：main 合并后 CI 构建前端包，生成清单（单增的构建号、提交号、每个文件的 sha256、支持的核心协议版本范围），用 minisign 签清单，和 [ADR-0017](0017-plugin-ecosystem-and-store.md) 以后给索引签名用同一种。
  - 密钥在哪：私钥只放在仓库的受保护 environment 密钥里，只有 main 上的发布工作流读得到；公钥编进核心、随核心发布。换钥时核心新版本同时带新旧两把公钥过渡。核心用 `minisign-verify`（MIT）验签。
  - 怎么拉：核心定期查最新清单（默认 10 分钟），从 GitHub 或国内镜像取都行，文件按清单里的 sha256 核对，来源不算信任。验签通过、每个文件哈希对上、协议范围包含自己、构建号比当前大，四样都满足才整个目录原子替换，保留上一版。
  - 失败即停：验签失败、哈希不符、构建号回退都不换，继续提供当前那版；App 的网页版状态和网页的“关于”如实写“新版本校验没通过”和原因类别，写审计。协议范围不含自己也不换，写“要先升级核心”。一次都没装成功过，网页地址只回一页“网页版还没装好”，不提供没验签的文件。
  - 回滚：用新的构建号重发旧内容；核心不接受构建号回退，防降级。
  - 浏览器这边：新文件由家里提供，Service Worker 下次打开时换新，不强制刷新正在用的页面。帧握手带 `ui_build` 和协议版本，核心回自己的版本，对不上就显示“请刷新”，不静默坏。
  - P1 只有一个跟 main 的通道（内部预览 = 团队 + 愿意试的家人，不保证兼容）；1.0 前加一个只在打 tag 时发的正式通道，正式发布不再随 main 更新。
- **配对**：家里人在手机 App 上“添加网页登录”，出一个一次性码（时效同 [ADR-0009](0009-identity-pairing-sso.md) 的配对码），在电脑浏览器打开这家的网页地址输入它。网页不用 0009 的二维码格式，地址就是这家的网页地址。没配对的人能打开外壳，但没有核心可连。
- **确认码**：一个一次性码只能被一个浏览器认领，第二个认领直接失败。认领后核心给这次尝试随机生成一个 6 位确认码，显示在浏览器上；手机在批准页显示同一个确认码和浏览器的名字。数字一致才点批准；不一致就点“不是这台”，配对直接中止、这个一次性码作废、要重新出码，没有“仍然批准”。
  确认码防的是码被别人看到或截图后，别人的浏览器抢先认领、主人在手机上批准错了浏览器。中继只见密文（见下面的信任），不需要它防；家里的核心和验过签的前端本来就在信任里。所以不做 ECDH 和 SAS，确认码只是核心生成的随机数。
- **授权凭据**：
  - 谁签：手机批准后，核心为这个浏览器建一条授权，签发不透明凭据（授权 id + 256 位随机秘密），自己只存秘密的哈希；用 `__Host-` 前缀、HttpOnly、Secure、`SameSite=Strict` 的 Cookie 下发。
  - 谁验：核心在入口专用监听上查授权，对不上回 401，吊销了就断开这条授权的已有连接。WSS 升级只带这个 Cookie，不另发令牌。
  - 插件的子域名 `<标签>.<家>.<域名>` 和网页同站，`SameSite` 挡不住插件页面带着这个 Cookie 发请求（[ADR-0011](0011-security-model.md)“浏览器里的隔离”），所以 `/ws` 和 `/api/web-auth/*` 只认 `Origin` 正好是网页地址的请求，改状态的请求另验 CSRF。
- **推送**：每家自己的 origin、自己的 VAPID 密钥（在核心），核心按 RFC 8030/8291 直接发给浏览器的推送服务（[ADR-0003](0003-matrix-and-encrypted-push.md)）；Service Worker 的 scope 是 `/`；iOS 仍要求先添加到主屏幕。
- **离线**：家里或入口不通时浏览器连不上这个地址；装过的 Service Worker 显示最后一屏和“连不上家里的服务器”，按 1/2/4…最多 30 秒退避重试，不排队、不缓存操作。
- **信任：中继只见密文和 SNI 里的子域名。**
  - 中继（frps）看得到 SNI 里的 `web.<家>.<域名>`（知道这家在用网页版）、来源 IP、流量大小和时间；看不到内容、改不了代码，也拿不到 Cookie。frp 登录令牌泄露能把这家的流量劫到别处，但没有证书，浏览器只会报证书错误（ADR-0021）。
  - 页面代码只来自这家的核心，核心只提供验过签的包。能改代码的是拿到前端签名私钥的人：仓库 main 的写权限或这条 CI 密钥被盗，就能给所有家推一版恶意前端。缓解：受保护 environment、清单哈希留在公开的 CI 记录里可比对、构建号不能回退；挡不住，只能事后发现。
  - 家名服务的 DNS 和 acme-dns 由我们运营（#1097 的入口云；单机阶段这一台就是所有家的信任根，ADR-0021）。证书由 Let's Encrypt 签发、钥匙在家里，但控制 DNS 就能为 `web.<家>.<域名>` 另申请一张证书做中间人，那时既能读也能改网页。缓解沿用 0021：CAA 的 `accounturi`，核心定期查 CT 日志、发现不是自己申请的证书就告警；同样是事后发现。不信任我们的主人用自己的域名（ADR-0089）。
  - 主人在 ADR-0090 里选 Cloudflare Tunnel 当入口时，TLS 在 Cloudflare 的边缘终止，网页也一样被它看到，代价照 0090 写明。

### 6. 安全基线

- 传输只有 HTTPS/WSS，TLS 在家里的入口容器终止；没有 `http`、`ws://` 退化（0021 的局域网入口也只给 https）。CSP `default-src 'self'`，无第三方脚本；`connect-src` 只到网页自己的地址。
- 授权 Cookie 见第 5 节；刷新页面重连同一核心，Cookie 丢了才重新配对。
- 浏览器可控的帧只在每用户的网页核心容器里解析，核心只做 HTTP 升级和查授权；网页核心容器不挂 Docker socket（第 3 节）。
- 渲染层不存 Matrix 令牌；浏览器扩展或 XSS 在页面开着时能替用户点，但拿不走设备和推送密钥；网页核心和单个浏览器的授权都可随时吊销。
- 插件网页不走 React，仍在独立的 WebView（Electron）或受限 iframe（Web）里，按 [ADR-0033](0033-plugin-tabs.md) 的桥通信。
- Electron 的 sidecar 继承本机用户的网络和文件权限，和原生 App 一样；被控端的屏幕录制、辅助功能授权按 [ADR-0081](0081-local-agent-host.md) 的规则单独申请。

### 7. 文案和设计

- 文案按 [ADR-0043](0043-app-languages.md)：核心给类别和原始值，渲染层按语言查自己的资源。Web/Electron 用和核心同一份 Fluent 目录，
  构建时转成前端资源，不新造一套键。
- 设计令牌仍来自 `design/`，桌面沿用移动端的颜色、间距、字号、圆角、动效，但不照搬手机：密度、栏高、列表行高、窗口控件、快捷键和右键菜单按桌面交互与比例重做；同一件事用桌面上惯用的控件，不把手机界面放大。
  原生移动端按 [ADR-0026](0026-design-system.md)、[ADR-0029](0029-platform-material.md) 用自己的令牌；Web 不假装 iOS 的 Liquid Glass 或 Android 的 Material，窗口控件跟随桌面系统。
- 可访问性按 Web 做：语义 HTML、焦点管理、读屏、IME、键盘操作；插件 iframe 的焦点进出要能回主界面。

## 核心放在哪

| 做法 | PWA 的核心在哪 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| A. 编译到 wasm，跑在浏览器 | 浏览器标签页 | 不占服务器内存；断网还能操作本地状态；和 Electron 共用核心代码 | matrix-sdk、iroh、SQLite、加密随机数都要移植或换实现；包大、冷启动慢；密钥和存储落在浏览器，扩展和 XSS 能读；iOS 标签页回收、存储清理；等于维护第二套核心运行时 | 以后做，P1 不做 |
| B. 服务器端核心 | 家里的服务器，每个用户一个容器 | 直接复用现有核心和全部网络栈；浏览器不拿密钥；和 Electron 是同一个二进制、同一套帧；多窗口共享同一份数据和网络连接；不需要 wasm 工具链 | 每用户占服务器 CPU/RAM；核心生命周期、唤醒、回收、吊销要写；多窗口视图状态和连接要管；每次操作走一趟网络；离线差 | **主人已选** |
| C. 浏览器加本机 helper | 浏览器旁边的本机进程 | 兼顾本地核心和浏览器渲染 | PWA 在手机上还得回到服务器端核心，helper 只对桌面浏览器有意义；多一条安装路径 | 只作为 Electron 的形态，不解决 PWA |

选 B 的具体理由：

- `crates/wonton-client` 已经是完整客户端核心，直接跑在服务器上就是复用，wasm 是重写一遍它的依赖栈。
- 浏览器不落密钥：设备密钥、Matrix 令牌、SQLite 都在服务器端的网页核心里，吊销网页核心就断掉，和手机被吊销同一条路。
- 延迟在局域网和隧道里都是一次本地 RTT 量级；文本输入、滚动这些高频动作留在渲染层本地，不逐字往返。
- 编译到 wasm 的坑是真实的：matrix-rust-sdk 依赖 tokio、reqwest、SQLite，iroh 依赖 UDP/QUIC，浏览器里要换 WebSocket/WebTransport 实现；
  这是独立的一大摊，不该压在第一个 PWA 上。体积和可行性要在“待验证”里实测，不能拿设计当结论。

切换点：帧契约和 `Transport` 边界不变，如果以后离线成为硬需求，把宿主从服务器端容器换成 wasm 模块即可重评；那时另写 ADR。

## 原型

11-07 的桌面原型（`scratch/desktop-proto`，原 ADR-0068）已经跑通过这些，仍成立并沿用：

- 新行分隔的 JSON 帧，`ClientFrame` 是 `call` / `subscribe` / `cancel`，`HostFrame` 是 `ready` / `ok` / `err` / `next` / `end` / `bad_frame`；
  开发时走本机 WebSocket，正式 Electron 走 stdio。PWA 把 WebSocket 换成 WSS。
- 渲染层只依赖 `Transport` 的 `send`、`onMessage`、`onClose`；`useTopic(topic)` 只暴露 `loading` / `ready` / `ended`。
- TypeScript 类型由 Rust 生成（`ts-rs`），渲染层不手写 ViewModel。
- Electron 安全基线就是上面第 4 节那一套；原型用 Playwright 断言过渲染进程没有 `require`、`process`，`window` 上只有三个函数。
- 设计令牌由生成器出 CSS 自定义属性，`--check` 比对。

不沿用的：原型只做 Mac、只做桌面；“桌面用 Compose Multiplatform、Web 在 M3 才做”是旧结论；
原型里 WebSocket 只给开发用，这里 WSS 是 PWA 的生产传输。

### 契约、提供方、消费方

- 契约：`wonton-protocol` 的 `ClientFrame`/`HostFrame` JSON 帧（带窗口、`ui_build`、协议版本）、核心的 `/api/web-auth/*` HTTP 面和前端包的签名清单。
- 提供方：`wonton-client-host`（PWA 的服务器端每用户容器；Electron 的本机 sidecar）。
- 消费方：React 渲染层（Web/Electron）。
- 契约测试：同一组帧金样本分别走 stdio 和 WSS，`Transport` 换实现时渲染层不改。

### 和 ADR-0021（第三方 App 的公网入口）的关系

- 网页版就是 0021 公网入口上的一个标签：同一张通配证书、同一个 frps 按 SNI 转发、同一个入口容器和 8484，TLS 在家里终止，中继不解密。0021 的入口规则、隔离和“面向公网的 TLS 和协议解析不进核心”都不改，浏览器的帧在网页核心容器里解析（第 3 节）。
- 多出来的只有：保留标签 `web`；8484 上多放行网页的静态文件、`/api/web-auth/*` 和 `/ws`；frpc 登记通配名字（第 5 节和 #1097 的接口）。

### 和 ADR-0123（受管设备）的边界

- [ADR-0123](0123-hubs-and-managed-devices.md) 的受管设备是用户电脑上的守护进程，替人执行任务；本篇的 Electron 包是客户端渲染层，本机 Agent 主机和被控端是同一包里另外两个角色。三者可以同在一台电脑上，但身份和开关各是各的。
- 受管设备不跑 Matrix 客户端；网页核心的 Matrix 设备也不执行 0123 的任务；设备密钥和 Agent 主机身份不是同一把。

## 不做

- P1 不把核心编译到 wasm，不做离线优先。
- 不做 React Native、不做 Capacitor 套原生移动；React 只做 Web DOM 和 Electron 渲染进程。
- 不恢复 Compose Multiplatform 桌面端，不在 `apps/compose` 里加桌面目标。
- 不在云端托管网页，不运营公开账号系统和云端会话，不做公开注册。
- P1 不做在家自动走局域网和 WebRTC 打洞（第 5 节）。
- 不在这里定远程控制的屏幕、输入协议；不在 P1 做被控端。
- P1 不改原生移动端的渲染技术，也不把手机 App 改成 PWA（P1 暂定）；长期去留另定。
- 不新造页面 DSL；声明式页面仍按 [ADR-0120](0120-dumb-shell-pages.md)，聊天、相册、播放器等继续手写。

## 代价与风险

- **信任落到签名密钥和家名服务**：前端签名私钥或 main 的写权限被盗，能给所有家推恶意前端；家名服务被攻破，能另签证书做中间人。两样都只能事后发现（第 5 节）。
- **前端更新取决于每一家**：核心离线、验签失败或核心太旧时那家停在旧版，不同的家同时跑不同的前端构建。
- **服务器资源**：每个用户一个网页核心容器和一份 SQLite 存储；同一用户开多个窗口不复制核心，只多连接和每窗口的视图状态。五人家庭、每人多台设备的并发用户数会上去；靠挂起和回收压住，默认值要实测。
- **生命周期**：网页核心容器要处理崩溃重启、核心升级（镜像跟着换）、服务器重启、吊销时的清理；这些比手机上的本地核心多一套监督逻辑。吊销单个浏览器只断它的窗口，吊销核心才断掉这个用户的所有窗口和浏览器。
- **延迟**：每个操作一次网络往返。高频状态留在渲染层，但网络差时按钮和列表会有可感延迟，UI 要如实显示进行中。
- **离线**：服务器连不上时只能看最后一屏；比原生 App 的本地库弱。这是选 B 的主要代价。
- **浏览器侧攻击面**：页面开着时 XSS 或扩展能以用户身份驱动网页核心；HttpOnly 挡不住“代替点击”。CSP、依赖锁定和单个浏览器的吊销是缓解，不是根除。
- **第三个 UI 技术**：SwiftUI、Compose 之外多一套 React；好处是 Web/Electron 共用一套，坏处是团队要同时维护三种渲染栈。
- **带宽和配额**：没配路由器转发的家，网页流量全经我们的中继，在家也绕一圈（P1 不走局域网）；算不算进 0021 的每家配额见“待主人拍板”第 2 项。单台中继挂了，网页和第三方 App 的入口一起不通。
- **家里或入口离线**：浏览器连不上，装过的页面显示“连不上家里的服务器”并退避重试；配对要求服务器在线，不能离线排队。
- **iOS PWA 限制**：Web Push 只在“添加到主屏幕”的 Web App 里可用（iOS 16.4 起），后台同步、存储配额都受限；推送体验达不到原生。
- **Electron 的本机服务**：旁路进程以后带上被控端会扩大本机攻击面；签名、fuses、第一版不带、逐项授权是底线。
- **依赖和供应链**：React、Electron 和前端构建链更新快；锁文件、许可证审查、CSP、自动更新签名都要跟上。
- **没有家名的家用不了**：要在家名服务注册，或者用自己的域名（ADR-0089、ADR-0090）。

## 待验证

- 浏览器核心的 WSS 延迟、重连、同一用户多窗口/多标签（同一核心多连接、各自订阅）和慢网络表现；每用户的实际内存。
- 核心挂起、恢复、吊销、重启后的窗口恢复；10 个用户同时在线和同一用户 10 个窗口的负载。
- iOS 主屏幕 Web App 的 Web Push、存储清理、后台切换；Android Chrome 的安装和推送。
- 经中继（frps 按 SNI）和路由器转发时网页 WSS 的延迟、断线、重连；网页流量占每家月流量的多少。
- 配对、确认码和授权凭据；前端包清单的拉取、验签、原子替换、失败提示，构建号防回退，Service Worker 换新。
- 核心 frpc 登记通配名字、入口容器加 `web` 标签之后，#1097 的名字归属钩子、`crt-list` 和入口自检在入口云上的表现。
- 网页里的插件 iframe 怎么到插件（插件的公网入口按插件开关，ADR-0021、ADR-0090）。
- 网页核心容器经 iroh 隧道连本机核心的网络布置（只够得着隧道端口和网页专用监听），和每用户容器的内存开销。
- 在家时页面能不能安全地改走局域网（不同 origin 的 Cookie、Service Worker、推送订阅怎么接上），做之前另写设计。
- wasm 核心的体积、冷启动和 matrix-sdk/iroh 移植成本，决定以后要不要做。

## 待主人拍板

1. **网页入口和“公网访问”总开关的关系。** [ADR-0090](0090-public-access.md) 的总开关默认关，关掉就是关掉所有公网入口；网页版在外面能用，就得开一个公网入口。可选：
   - 甲：网页入口算总开关下的一项。在手机上“打开网页版”时，总开关关着就在确认页写明“会打开公网访问，只放行网页版”，一起打开；关总开关时网页版也停。
   - 乙：网页入口单独一个开关，不受总开关管。

   推荐甲：保住“一键全关”的承诺（0090 吸取的 Home Assistant 教训）；网页露在外面的只有静态外壳、配对接口和要凭据的 `/ws`。
2. **网页流量和中继配额。** 没配路由器转发的家，网页流量都经我们的中继；ADR-0021 按家限速、限每月流量、限开着的公网入口数，超了这家所有公网入口停到下月初。推荐：网页流量照算、网页入口照算一个入口，超了网页显示恢复时间；数值和 0021 的配额一起按中继实测定。原来“按用户限流”的要求由这套按家的限额代替。
3. 每用户窗口/连接上限（不再按会话数封顶）、挂起和回收时间（推荐无连接 15 分钟挂起、24 小时回收）。
4. 在家自动走局域网、WebRTC 打洞的时机（P1 都经公网名字）。推荐 P1 不做，单开 issue 调研不同 origin 之间怎么切。
