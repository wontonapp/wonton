# ADR-0105 插件运行意图与中断续建

- 状态：已接受（2026-11-13，插件重建中断修复任务）

## 背景

Docker 的 create 或 start 请求超时只表示核心没收到结果，不表示 Docker 没执行。重建删除旧容器后，create 可能已经留下 `Created`，但核心没走到配置交付和启动。只观察容器会把它归成普通停止，无法区分主人主动停止与未完成的操作。

Docker restart policy 不会完成尚未启动的容器，也不了解 Compose 服务依赖、配置交付和核心的核对步骤。继续复用 Docker Engine API、Compose 渲染和现有安全替换路径，不引入另一个调度器或依赖。

## 决策

安装记录把运行意图与观测状态分开：安装和明确启动表示期望运行；明确停止先持久化停止意图，再停容器。没有意图的旧记录只观察，不根据 `Created`、退出码或缺失容器猜主人的意图。

已安装插件在替换或启动的副作用之前持久化恢复日志：最后阶段、错误类别、原始原因、后台尝试次数、下次尝试的 Unix 秒。执行中日志使用 `interrupted`；Docker 超时使用 `docker_timed_out`，不伪装 Docker 拒绝请求。普通错误沿用 `InstallError` 类别。

后台和手动操作复用每插件的重建互斥，后台还遵守依赖事务锁和核心升级冻结。巡检到期才续建，最多五次，失败后的间隔为 30、60、120、240、300 秒；次数在 Docker 写操作前消费并持久化。重启核心不重置额度，额度耗尽保留降级状态与最后原因，明确启动才重置。

续建先 inspect 同名容器。替换或启动阶段中断，配置交付是否完成不确定时，走原有安全替换路径，重新按依赖顺序交付配置、完成一次性服务、启动常驻服务，不创建第二个同名服务，不删卷和应用数据。不承诺回滚应用数据库或外部副作用。

明确停止取消自动续建。停止失败或超时保留 `stopping` 类别和原因，不伪装停止成功，也不安排自动启动。明确启动可以重新改为运行意图。

## 接口与消费方

- `GET /_wonton/api/plugins/{id}/lifecycle` 返回 `PluginLifecycle`：运行意图与可选恢复日志。
- `POST /_wonton/api/plugins/{id}/stop` 记录停止意图并停止容器；启动沿用 `/start`。
- 两个新接口沿用启动入口的 `InstallApps` 授权，含被授予该权限的家人管理员；不另改授权边界。
- 提供方是核心插件管理器，消费方是容器巡检和管理接口调用方。现有插件状态枚举不变；中断显示降级及原因，结构化阶段从生命周期接口查询。

明确停止的插件升级请求报冲突，不隐含恢复运行；先由主人明确启动，再升级。权限、密钥与设置变更同样不能绕过停止意图。

## 代价与边界

- 安全替换会重新执行一次性服务；插件仍须遵守已有重建契约，不能假设只运行一次。
- 旧记录没有足够证据证明主动停止或意外中断，保持观察模式；主人明确启动后才进入自动续建。
- 本决策不改变网络隔离、容器归属、凭据签发和插件权限。
