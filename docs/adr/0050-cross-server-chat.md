# ADR-0050 跨服务器聊天：配对过的两台服务器经 iroh 互相联邦

- 状态：已接受（2026-11-06）；配对 2026-11-07 改成长效码加请求（见“服务器配对”“码和请求的安全”）

## 背景

两台不同主人的 Wonton 服务器，主人想让两边的人互相私聊、拉跨机的群，也能和对方的 Bot 说话（GOAL 的 M3）。
ADR-0045 的“跨机（M3）留的位置”已经定了方向：Matrix 联邦走 iroh，Tuwunel 只对配对过的服务器开联邦，服务器配对用
`wonton/peer/0`，记在 `core/peers.json`，跨机的联系人两边的归属人都批，跳数只在本机 Bot 发送时数。
前提是每台的 Matrix 服务器名唯一、永远不变（ADR-0009 的“补充：Matrix 的服务器名”，#490）。

要解决的是怎么落地：联邦是 HTTPS，要按服务器名找到对方、校验证书和签名；家里的服务器没有公网地址、没有公共证书，
也不该查 DNS。

## 别人怎么做（2026-11-06 查）

- **Pinecone、P2P Matrix**（matrix.org，Go）：给 Dendrite 换掉 HTTP 的拨号器，服务器名用公钥。2023 年起没有实质开发，Dendrite 进了维护模式；
  2026 年的 P2P 重启（Neutrino）是不和标准 Matrix 互通的方言。Tuwunel 没有换拨号器的口子，只能用 TUN 加 SOCKS5 套一层，等于再引一套身份和覆盖网。
- **规范**：没有定义 P2P 传输的 MSC。
- **Tuwunel**（conduwuit 系）：没有可替换传输的讨论。联邦写死 HTTPS，没有静态解析表。
- **dumbpipe**（n0）：只认 ticket，不能按 endpoint ID 设白名单，适合开发时手工打通，不适合常驻。
- **我们自己的 `wonton-tunnel`** 已经是“本机端口 ↔ iroh 流”：每条 TCP 连接一条 QUIC 流，按 endpoint ID 设白名单，取消即断，带重连和探活（ADR-0004）。

所以不引入新组件，在 `wonton-tunnel` 里加一个联邦转发模块。

## Tuwunel 1.9.4 的实测（2026-11-06，三台 Tuwunel 容器，A、B 配对，C 不在任何名单）

| 事项 | 结果 |
| --- | --- |
| 名单制联邦 `allowed_remote_server_names_experimental` | 可行。名单外出站、入站都是 403。名单是正则（点要转义），标了可热加载：原地重写配置文件加 `SIGUSR1` 秒级生效，不用重启。配置文件是 bind mount 时不能用 `sed -i`（换了 inode，容器读不到） |
| 不查 DNS 固定对方地址 | Tuwunel 没有静态解析配置。`/etc/hosts` 有效（hickory 会读），Docker 网络别名也有效，出站代理（`proxy`）也有效（见“验证”）。伪造 `.well-known` 自己就要先解析对方的名字，不能单独用 |
| TLS | 官方镜像带 `direct_tls`，`[global.tls]` 挂自签证书即可。`.wonton.internal` 拿不到公共证书，Tuwunel 又只认内置的 Mozilla 根，所以发送方必须开隐藏选项 `allow_invalid_tls_certificates = true`（只管出站） |
| 签名密钥 | `trusted_servers = []`（默认是 `["matrix.org"]`）时只向对方直取 `/_matrix/key/v2/server`，不碰公共 notary。没有预置对方公钥的配置或命令。对方换整套密钥，联邦自动恢复，旧密钥按 ID 留着，旧事件照样能验 |
| 端到端 | 跨机私聊、跨机拉群、Bot（普通用户账号，同 Hermes）在群里回复都通过。同机网络下稳态消息 4–5 ms，Bot 往返 18 ms |
| 取消配对 | 名单撤掉、热加载后：新邀请双向 403；已有房间的跨机消息停在发送方。恢复后续传，缺的事件由对方 backfill 补齐，不丢 |
| 能不能从 API 分清原因 | 不能。只有“本机名单拒绝”是同步 403；“对方离线”和“对方把我们移出名单”对客户端都是 200 加静默失败 |

另外两个坑：
- `ip_range_denylist` 默认含 10/8、127/8，会拦掉到内部网络上核心的出站，要置空。
- Docker 客户端配了代理时，`docker run` 会给容器注入 `HTTP_PROXY`，联邦出站全走宿主代理而失败。正式 compose 的空代理变量要保留。
- 出站目的地缓存 18–36 小时，对方地址变了会黏在旧地址上。经代理出站时缓存的是 `<服务器名>:8448`，不含地址，
  代理的地址变了不受影响。

## 决策

### 服务器配对

像加好友的码：码长期有效，可以当面扫，也能发给对方；扫了只是发一条请求，出码方的主人点同意才配对。

- **码**：主人在 App 的设置里打开“其他服务器”，点“添加”，看到本机的配对码：一张二维码，加一个“分享”按钮。
  - 分享走系统的分享面板，分享的是 `wonton://peer?…` 这段文字，不放进剪贴板。
  - 码里有本机的 endpoint ID、中继地址、Matrix 服务器名，和一个请求令牌（128 位随机数）。不带直连地址：码会发到群里，
    带了就等于把本机的公网 IP 给了每个看到的人；对方经中继连上后，iroh 自己找直连的路。
  - 令牌要能再显示，所以核心存的是令牌本身（数据目录里，同其他密钥的权限），不是哈希。
  - 一台服务器同时只有一张码，一直有效，直到主人点“重置”。重置换一个新令牌，旧码作废，用旧码发来、还没处理的请求一并清掉。
  - 令牌不变，中继地址每次显示时按当时的取：码里的地址只是提示，对方按 endpoint ID 连。
- **请求**：对方主人扫码，或者把收到的文字粘贴进来。他的核心经 `wonton/peer/1` 连过来，出示令牌，报上自己的服务器名、主人的用户 ID 和显示名、能被回连的地址。
  - 出码方的核心验过令牌、按下面的限制收下，记一条待处理的请求（落盘），回“等对方同意”。扫码方也记一条“等对方同意”（落盘）。
  - 令牌不对时回“码已作废”：对方拿的是重置前的码，要一张新的。
- **同意**：出码方的主人在“其他服务器”页的“请求”里看到每一条：对方主人的显示名、对方的服务器、什么时候发来的，点“同意”或“拒绝”。
  - 自报的显示名或服务器名和一台已配对的服务器重名、endpoint ID 却不一样时，这条请求醒目标出“和已配对的某某重名，不是同一台”。
  - 核心同时在“Wonton”私聊里发一条提醒，带 App 链接 `wonton://settings/peers`（ADR-0041），点了直接跳到“请求”。
  - 不用确认卡片（ADR-0016）：卡片背后是一次等着的调用，默认 30 分钟过期，核心重启就没了；请求可能隔几天才处理。
- **结果送到扫码方**：出码方点同意后，记成已配对、放进名单，再把结果送给扫码方，送不到就重试。
  扫码方在等的时候也自己去问：启动时问一次，之后每 10 分钟一次；没问到（连不上）时从 5 秒起翻倍很快再问，封顶 10 分钟。对方点同意时扫码方不在线，上线后一问就成立。拒绝也这样送到。
- **两边互相发了请求**（A 扫了 B 的码，B 也扫了 A 的码）：两边都表示了同意，直接成立，不用再点。
- **认证**：码里的 endpoint ID 认证了出码方，iroh 握手认证了扫码方的 endpoint ID。令牌只说明对方拿到过这张码，真正把关的是主人点同意。
  所以一次扫码加一次同意，就等于“互相扫码”。
- **限制**：码会被转发，按会泄露来设计。
  - 同一台服务器（按 endpoint ID）同时只有一条待处理的请求。再发只更新那一条，不再提醒。
  - 被拒绝过的 endpoint ID 记下来。它之后的请求直接回“对方拒绝了”，不再提醒主人。
    “请求”里留一节“已拒绝”，主人点错了能撤销；撤销后对方再发就照常收下。主人自己去扫对方的码时，这条记录也清掉。
    endpoint ID 生成起来不花钱，挡得住正常人反复发，挡不住有心的；有心的靠下一条的总量限制和重置。
  - 待处理的请求最多 20 条，每小时最多收 10 条新的。超出时回“对方暂时收不了请求”；“请求”里提示主人，码可能泄露了，可以重置。
  - 请求不过期。扫码方能取消（在“等对方同意”那行点“移除”）；出码方处理掉、或者重置码时清掉。
- **没有一次性密钥**：原来那种 10 分钟、用一次的密钥不再要。长效码泄露了也只能发请求，把关的是同意；两套并存只会多一条路径要维护、要解释。
- 成立后两边各记一条 `core/peers.json`：服务器名、endpoint ID、地址、对方主人、时间。服务器名和 endpoint ID 的绑定只在这里定，以后不变；对方换了 endpoint ID 要重新配对。
- 任何一方随时能移除。移除以后两边的名单各自撤掉，已有的跨机房间留着，消息停发。
  被移除的一方留着那条记录，显示“对方已断开连接”，由主人再点“移除”才删掉（拆除自己这边的痕迹）；
  在它移除之前对方重新配对时，这条记录直接换成新的配对。

### 码和请求的安全

**码泄露了会怎样。** 拿到码的人能做的：
- 看到 endpoint ID、中继和服务器名。码里没有公网地址；真去连本机的人，在连上以后会知道它（P2P 连接本来就会）。
- 发配对请求，受上面的限制。

不能做的：
- 不经主人同意就配对。
- 进联邦：服务器名单里只有配对过的。
- 进 App 的隧道：设备名单分开（见“联邦流量”的名单分开）。
- 看到本机配对过哪些服务器、有哪些家人。

被打扰了，主人点“重置”：旧码立刻作废，它发来的待处理请求一并清掉。

**请求里能伪造什么。**
- 伪造不了：
  - 扫码方的 endpoint ID：iroh 握手认证。
  - 令牌：没拿到码的人猜不中（128 位随机数）。
  - “同意”：只有主人的设备经隧道调核心的接口（ADR-0017 的设备门）。
  - 配对过的服务器的身份：服务器名已经绑定了 endpoint ID。只要本机还留着这个名字的记录（包括“对方已断开连接”的），
    别的 endpoint ID 报同一个名字来的请求就回“已经配对过”；同一个 endpoint ID 来的才能替换那条记录。
- 能伪造，都是对方自报的：主人的显示名、用户 ID、服务器名、地址。
  - 所以“请求”里的“某某”只是对方自称，主人按自己知道的判断，比如是不是刚把码发给了这个人。界面上不把它写成核实过的身份。
  - 不加两边对照的短校验码（主人定）。冒充已配对的那几台最容易让人上当，所以和已配对的服务器重名的请求单独标出来（见“同意”）。
  - 服务器名是 120 位随机数，用户看不到。冒用别人的服务器名，得先知道这个名字（跨机房间里的用户 ID 带着它）。
    冒用的请求被同意了，就占住了这个名字，真正的那台配不进来；被拒绝不影响真正的那台，因为拒绝按 endpoint ID 记。
  - 用户 ID 必须在它报的服务器名下（`@x:<服务器名>`），对不上的请求直接拒。
- **反过来也一样**：发出去的码可能在转发途中被换成别人的。扫码方看到的对方显示名，是出码方在回应里自报的。
  经聊天发的码，可信程度就是那个聊天渠道的可信程度。拿不准就当面扫。

### 联邦流量

- `wonton-tunnel` 新模块 `federation`，ALPN `wonton/federation/0`，和 App 的隧道（`wonton/tunnel/0`）、配对（`wonton/peer/1`）挂在同一个 endpoint 上：
  对外只有一个 UDP 端口、一个 endpoint ID，中继表也只有一份（ADR-0048）。
- **名单分开**：服务器名单只放行联邦的 ALPN，设备名单只放行隧道的 ALPN。配对过的手机进不了联邦，配对过的服务器也进不了 App 的隧道。
- **出站**：
  - 转发组件是一个 HTTP CONNECT 代理，Tuwunel 的出站都经它走（`proxy.by_domain`）。Tuwunel 不查对方的名字，
    也不用 `/etc/hosts`。
  - 核心在私有网络 `core` 上有别名 `federation-proxy.wonton.internal`，代理只绑在核心在这个网络上的地址（启动时
    解析别名得到），端口 8448。插件网络里连不到它。地址由 Docker 分配，不用固定子网，同机装几套互不冲突。
  - `CONNECT <服务器名>:8448`：按 `peers.json` 找到 endpoint ID，开一条 QUIC 流，对方接上它的 Tuwunel 后回 200，
    之后字节原样转发。Tuwunel 先发 `CONNECT <服务器名>:443` 取 `.well-known`，代理回 502，它随即改拨 8448。
  - 不终结 TLS，TLS 在两台 Tuwunel 之间。
  - 每台对方服务器一个隧道客户端，共享一条连接、带退避。配对成立就建客户端并开始探活，不等联邦流量。
    探活用 `probe`；App 回前台时用的那套检查不用。
  - 对方移除本机又加回：被 403 拒后隧道客户端停在原地等显式重试（设备被移除后不该自己反复重拨打扰
    服务器，ADR-0032），联邦不同——名单恢复不需要本机动作，探活周期里清退避强制重拨一次，一个探活
    周期内回到 `Connected`。退避期间本机 Tuwunel 的 CONNECT 立刻回 502，不替它等退避，Tuwunel 自己会重试。
- **入站**：经服务器名单认过的流，原样接到本机 Tuwunel 的 8448。
- 不在配对名单里的服务器名：出站回 403，入站在握手后拒绝，各自记下原因（见“状态”）。

### Tuwunel 的配置

由核心生成（`install.rs`），配对变化时由核心改：

- `allow_federation = true`，`trusted_servers = []`，`ip_range_denylist = []`。
- 联邦端口 8448 只在 Tuwunel 的内部网络上，不映射到主机。
- `[global.tls]` 用安装时为本机服务器名生成的自签证书。
- `allow_invalid_tls_certificates = true`：只和这套转发一起开。
- `[[global.proxy.by_domain]]`：`url` 是核心的代理，`include` 为空（所有域名：服务器名可以是安装时指定的任意名字），
  `exclude` 推送代理 `push.wonton.internal`。Tuwunel 的其他出站因此也只能到配对过的服务器。
- `allowed_remote_server_names_experimental`：`peers.json` 里的服务器名，转义成正则；没有配对时是一个谁也匹配不上的式子。
- 改名单：原地重写配置文件，向 Tuwunel 发 `SIGUSR1`，不用重启。
- 网关照旧不转发 `/_matrix/federation/` 和 `/_matrix/key/`：联邦只经 iroh 进来。

### 信任落在哪

- TLS 不再认证对方：自签，而且出站不校验。它只是规范要求的形式，加上单机内的那一段传输。
- **认证对方服务器**靠 iroh 握手认出的 endpoint ID（服务器名单），加上 Matrix 每个请求的 X-Matrix 签名。
  签名用的公钥向对方服务器名直取，而这个名字只会被转发到配对时绑定的 endpoint ID。所以配对过的 P 冒充不了另一台配对过的 Q。
- **机密性**靠 iroh（QUIC 加密，两端按 endpoint ID 认证）。房间内容照旧端到端加密，联邦和中继都看不到。

### 谁能和谁说话

- 配对的是服务器，等于两边主人互相信任：
  - 两边主人互为联系人。
  - 两边的人能互相私聊、拉群，同机的“人邀请人不限”照旧适用。
  - 对方服务器上还有谁，配对时不交换（主人定），靠房间里认识（有人把他拉进群），或者对方报自己的用户 ID。
- Bot 照 ADR-0045 的联系人：本机 Bot 和对方的人或 Bot 结成联系人，要两边的归属人都批。
  - 两台核心经各自的核心账号（`@wonton-core:<服务器名>`）在一个不加密的房间里交换请求和结果，事件类型 `app.wonton.contact`。
    房间在配对时建；对方离线时 Tuwunel 自己排队重发。
  - 成立后记进 `core/contacts.json`。对方的用户 ID 加进本机 Bot 的 `WONTON_MATRIX_ALLOWED_USERS`。
  - 没成联系人的远端用户，Bot 不理（Hermes 的白名单同时管邀请和消息）。
- 网关管不到经联邦进来的邀请。本机 Bot 靠它自己的白名单挡住生人；本机的人收到远端邀请，和收到同机邀请一样，自己决定加不加入。
- **跳数**照 ADR-0045：经联邦来的消息不经网关，频率和跳数只在本机 Bot 发送时数，远端的人说话不清零。双方各自限住自己的 Bot，环路照样停得下来。

### 状态

Tuwunel 分不清对方离线、没配对、拒绝我们，由核心按转发组件的状态分：

| 情况 | 核心怎么知道 | App 上 |
| --- | --- | --- |
| 正在确认 | 刚配对，第一次 `probe` 还没出结果 | “正在确认”，不显示连上也不显示连不上 |
| 已连上 | 最近一次 `probe` 成功 | 正常 |
| 对方离线 | 连不上，或 `probe` 超时 | “对方服务器连不上”，带最后连上的时间；消息会在连上后补发 |
| 对方移除了配对 | 收到对方的移除通知，或握手后被对方的服务器名单拒绝 | “对方已断开连接”，带最后连上的时间，按钮“移除” |
| 没配对 | 本机名单里没有，Tuwunel 同步回 403 | 邀请时提示“这台服务器还没连接”，按钮“添加服务器” |
| 等对方同意 | 请求送到了，对方还没处理 | “等对方同意”，按钮“移除”（取消请求） |
| 对方拒绝了 | 对方点了拒绝 | “对方拒绝了”，按钮“移除” |

状态经 ViewModel 给壳，壳按类别显示文字（ADR-0043）。“详情”里写服务器名、endpoint ID 前 8 位、最后一次错误。

核心不往客户端推状态变化，客户端按核心的探活周期（30 秒）取列表：状态变化和设置首页的台数在一个周期左右跟上，
不用退出页面再进。出码页开着、在等对方同意或有一行在确认时，几秒取一次。

别人发来的请求不是一行状态，在“其他服务器”页单列一节“请求”，每条带“同意”“拒绝”。

### ViewModel 和接口

- `wonton-protocol`：
  - `PeersViewModel`：
    - 配对过的服务器列表。每项有服务器名、对方主人的显示名、状态（`Checking`、`Connected`、`Offline`、`RemovedByPeer`、`AwaitingApproval`、`Declined`，认不出的落到 `Other`）、最后连上的时间。
    - 别人发来的请求：请求 ID、对方的服务器名、主人的用户 ID 和显示名、收到的时间。
    - 出码页开着时是本机的码，没有过期时间。
    - 已拒绝的请求：同请求的几项，加拒绝的时间；动作 `UnrejectPeerRequest(id)` 撤销。
    - 每条请求带“和已配对的哪台重名”：没有重名时为空。
  - 动作：
    - 码：`ShowPeerCode`（打开出码页）、`HidePeerCode`（关掉出码页，客户端不再快速取）、`ResetPeerCode`。
    - 请求：`ScanPeerCode(code)`、`ApprovePeerRequest(id)`、`RejectPeerRequest(id)`、`UnrejectPeerRequest(id)`。
    - `RemovePeer(server_name)`：移除配对，也用来取消自己发出的请求。
  - 请求按 ID 认，不按服务器名：服务器名是对方自报的，两条请求可能报同一个名字。
  - 错误类别多了“码已作废”和“对方暂时收不了请求”，去掉了“码过期”。
  - 设置首页多一项“其他服务器”，只给主人。
- 核心：`/_wonton/api/peers`（列表、出码、重置码、扫码后提交、同意和拒绝请求、移除），只收主人设备经隧道来的请求（ADR-0017 的设备门）。

### 跨机 Bot 联系人的接口

- 远端发来的请求和同机的一样（ADR-0045）：存在核心里、不过期，归属人在 Bot 的“联系人”页或“等你确认”列表里同意或拒绝，
  新请求有推送，不往“Wonton”私聊发提醒。
  等这个人处理的请求跟确认卡片走同一条长轮询（`GET /_wonton/api/confirmations` 的 `contact_requests`），推送是同一个
  通知类别，各带 Bot 和对方的用户 ID，不做成卡片：卡片要有到期时间，回答的接口也不同。
- **对象是对方家里的人**（不是 Bot）时照 Matrix 的做法，本人接受邀请才算同意（主人 2026-11-11 定）：
  - 归属人加联系人时选“人”还是“Bot”，核心不去对方那里查是哪种，也不另做查账号是否存在的接口。
  - 发起方只在自己这边记下对方的用户 ID，Bot 给他发一个标准私聊邀请（`is_direct`），`m.room.create` 的内容里带
    `app.wonton.bot_contact: true`。放 create 内容而不是状态事件，和好友请求一样（ADR-0051）：受邀者接受前看得到。
  - 他在云吞 App 已有的“请求”里看到“某某的 Bot 想加你”，接受就是同意；用 Element 之类的只看到一个普通私聊邀请，接受同样算数。
    不另做一份“给我的联系人请求”列表。接受只让那个 Bot 理他的话，不因此成为好友。
  - 接受之前，发起方显示“等对方接受”，不显示“已添加”。他拒绝邀请时显示“对方拒绝了”；用 MSC4155 屏蔽了这个 Bot 或这台服务器时，
    邀请回 403，同样显示“对方拒绝了”。只是忽略（ignore）的，邀请照常发到、他不处理，就一直是“等对方接受”：忽略本来就不让对方知道。
  - 邀请因查无此人被对方服务器拒绝时显示“没有这个人”；对方服务器连不上时这次请求失败，不记下。
  - 邀请由核心代 Bot 发：核心用 Matrix 管理接口给 Bot 登录一台常驻设备（“Wonton contacts”），建房、邀请、之后查他的成员状态、
    撤回邀请都用它。不每次登录再退出：Bot 的设备列表一变，和它在加密房间里的人的客户端都要刷新设备。接受与否只能从
    成员状态看出来，核心每分钟查一遍，取联系人列表时也顺带查；App 在有“等对方”的行时每几秒取一次列表。
- 联系人请求的推送是核心自己发的（不对应消息），`room_id`、`event_id` 为空，带 `contact_request`（Bot 和对方）；
  通知类别同确认卡片，正文类型借用“邀请”，壳看到 `contact_request` 按它写文字。
- 两边互相发了请求直接成立（同配对）。不另外限频、不记拒绝：对方服务器已经配对过，同一对只有一行，再发只更新那一行。
- 不进 `PeersViewModel`：配对页只给主人，联系人归 Bot 的归属人管（可能是家人）。跨机联系人和同机的是同一份列表
  （ADR-0045 的 `/_wonton/api/bots/{插件}/{Bot}/contacts`），客户端放进按 Bot 看的 `BotContactsViewModel`。
  远端的一行多带对方的服务器名和那台的配对状态，配对移除后状态为空，壳据此说明消息为什么过不去。
- 列表里一个用户 ID 只有一行，同意、拒绝、删除都按用户 ID 认，不像配对请求那样另发 ID：`from` 由下一条的核对
  保证在发送方的服务器上，用户 ID 不是自报的。
- `app.wonton.contact` 的内容三种：请求（带发请求的核心生成的 ID）、结果（同意、拒绝、没有这个人，带原请求的 ID）、
  删除。`from` 总在发事件的那台，`to` 总在收事件的那台；收的一方核对发送者是已配对服务器的核心账号、两个用户 ID 的
  服务器名对得上，对不上整条忽略。结果对不上自己发过的请求 ID 时忽略：删了再请求，旧请求迟到的拒绝不算数。
- 删除的通知和收到请求后回的结果，和行的改动一起写进 `core/contacts.json` 再发；发不出去的后台定时再发，重启后照样发，
  配对移除了也留着等重新配对。归属人自己点的请求、同意、拒绝发不出去当场失败、什么都不记。发任何一条前先把给那台
  排着的发完，对方按先后收到：迟到的删除不会删掉之后新请求的那一行。至少送到一次，重复的结果和删除在对方是空操作。
- 每对服务器一个房间，`m.room.create` 的 `type` 是 `app.wonton.contact`。服务器名按字节序较小的一方在配对成立后
  建房并邀请对方：两边同时发请求直接成立时没有“出码方”，按名字定谁建就不会建出两个。
  收到的邀请先记下再加入：增量同步不会再带上收过的邀请，加入失败（联邦还没通）或这边还没记下配对时只能靠记下的重试。
  房间没建成时发事件按原因报：本机建房失败是 `upstream`，邀请没送到、对方还没加入是 `peer_unreachable`。

### 远端联系人只聊天

“已定”第 3 条的落地。总线只知道调用来自哪个 Bot（ADR-0045 的总线令牌），不知道这一轮是谁的话，所以先按 Bot 整体挡：

- **门**：一个 Bot 只要有一行 Active、对方用户 ID 的服务器名不是本机的联系人（人和 Bot 都算，认不出服务器名的也算），
  它列工具时就只看到下面几个核心工具；调别的工具（插件的、核心的）一律不执行，`isError`，`app.wonton/failure` 是
  `remote_contact`，审计记一条拒绝。归属人也受影响：他和这个 Bot 说话时同样拿不到插件工具，要用就先删掉远端联系人。
  等对方同意、等对方接受、对方拒绝了的行不算：这时对方的话进不来（不在 `WONTON_MATRIX_ALLOWED_USERS` 里）。
- **恢复**：联系人删掉，或者不再是 Active，下一次列工具、调用就恢复。不另发工具列表变化的通知：Active 的名单一变，
  核心就重建这个 Bot，Agent 重新列工具。配对移除了、行还是 Active 时照样挡：重新配对后对方补发的消息还会进来。
- **还给的核心工具**，只放只读、没有副作用、回的是公开内容或 Bot 自己的资料：

  | 工具 | 理由 |
  | --- | --- |
  | `help` | Wonton 的帮助文档，公开内容 |
  | `search_catalog` | 官方索引里能装什么，公开内容；装不了 |
  | `plugin_guide` | 写插件的说明和示例，固定的文字 |
  | `get_profile` | 这个 Bot 自己的名字和头像设置，对方在聊天里本来就看得到 |

- **不给的**：
  - 有副作用：`install_plugin`、`uninstall_plugin`、`set_plugin_permission`、`save_file`、`share_file`（发给归属人，
    但内容可能来自远端的指使）、`set_profile`、`pin_page`、`unpin_page`。
  - 只读但会把家里的情况带出去：`list_plugins`（装了什么、网页地址）、`plugin_status`、`list_pinned_pages`、
    `list_shares`（共享文件夹的名字）、`view_file`（工具结果里的文件）、`user_locale`（家人用什么语言）。
  - 只读、只为装插件服务：`check_plugin`。装不了，给了没用。
  - 新加的核心工具默认不给，要在这里写明理由才加。
- **kind 是对方自报的**：跨机请求（`app.wonton.contact` 的请求）不带 kind，收到的一律记成 Bot；配对过的服务器的核心
  也可以把一个人当成 Bot 发请求过来，归属人同意后这个人就进了 Bot 的允许名单。所以门不看 kind，只看是不是远端。
  归属人同意之前，“等你确认”和 Bot 的联系人页都要让人看得出这是另一台服务器上的（带 `remote` 的行写出对方的服务器名），
  同意的提示写明同意后这个 Bot 只聊天。

按轮次挡（只挡远端联系人那一轮，归属人那一轮照旧）要等总线知道轮次的来源，见 #353。

## 理由

- 只换传输，不换 Matrix：私聊、群、加密、补发都是现成的，实测在名单制下全部可用。
- 复用 `wonton-tunnel` 和同一个 endpoint：不多开端口，不多一套身份，取消配对即断连接。
- 不终结 TLS：转发组件不碰联邦内容，按 CONNECT 里的服务器名选路就够，代码最少。
- 由核心判断离线、拒绝和没配对：Tuwunel 给不出，转发组件本来就知道。

## 没选的做法

- **Pinecone 或 P2P Matrix**：停了，接不进 Tuwunel，还要第二套覆盖网和身份。
- **终结 TLS、在转发组件里读 HTTP 头选路**：要给每个对方生成证书，还要解析 HTTP，多做的事都没有用处。
- **每个对方一个本机端口，用 `.well-known` 指过去**：抓取 `.well-known` 自己就要先解析名字，还多一套端口分配。
- **`/etc/hosts` 把服务器名指向核心的固定地址，转发组件读 TLS ClientHello 的 SNI 选路**（最初的做法）：要给联邦网络
  钉死子网和核心地址，同机装两套就撞；hosts 不能热加载，配对加了名字要重启 Tuwunel。
- **核心经 Docker API 查自己的地址再写 hosts**：免掉固定子网，但核心容器重建后地址会变，Tuwunel 的目的地缓存黏住
  旧地址，每次变都要重启 Tuwunel，hosts 不能热加载的问题也还在。
- **自建 DNS 回答所有 `.wonton.internal`**：能免掉写 `/etc/hosts`，但多一个组件，地址也要固定。
- **长效码和一次性密钥并存**（当面扫用一次性的，发出去的用长效的）：两种码的泄露后果都只是“能发请求”，把关都在同意，多一套只多一条路径要维护、要给主人解释。
- **请求用确认卡片批**：卡片是等着的一次调用，过期和核心重启都会丢；请求要能隔几天处理，所以落盘、在“其他服务器”页处理，私聊里只发提醒。
- **请求按时间过期**：过期了对方还得重发、主人又被提醒一次；有数量上限和重置，不过期也占不满。
- **A2A 桥插件**（ADR-0045 的第二种接法）：只能 Bot 对 Bot，拉不了远端的人进群。以后要接非 Wonton 的 Agent 时再做，和这个不冲突。

## 代价与风险

- 码长期有效、能转发，就会到不认识的人手里：他们能发请求，连上以后能知道本机的公网地址。打扰靠限频和重置挡；
  对方自报的显示名能冒充，靠主人看清是谁再点同意（见“码和请求的安全”）。

- `allow_invalid_tls_certificates` 是隐藏选项、全局生效，上游可能改名或删掉，升级 Tuwunel 时要看。
  向上游提“按服务器名信任指定证书”或“预置对方公钥”的能力，记进底座的问题。
- 预置不了对方公钥：首次连接时才取。安全性靠“名字只会被转发到配对时绑定的 endpoint ID”，转发组件的这条规则要写成测试。
- 出站靠 Tuwunel 的 `proxy.by_domain` 和“`.well-known` 拿不到就改拨 8448”这两个行为，升级 Tuwunel 时要跑
  联邦的 Docker 测试（`federation_config/proxy_tests.rs`）。
- 两台都在国内时多半走中继：n0 公共中继离得远，自建中继见 ADR-0048。
- 配对两台以后，对方主人能邀请这边的任何人：这边的人能拒绝，但会收到邀请。要限制时再加“只有主人能被对方邀请”的开关。

## 验证

实现时逐条验证，写进这一节：

- 出站经代理：Tuwunel 的联邦出站全部经 CONNECT 代理，不查 DNS。
- 两台真实主机（或者一台上起两套）各装一套：配对、两边的人互发消息、拉跨机群、Bot 在群里回复；
  对方离线、对方移除了配对、没配对三种情况在 App 上各显示对的原因；移除配对后再配对，缺的消息补齐。

核心层实测（进程内两个 endpoint / 两个核心，提交 `624d314`）：
- 服务器配对协议（`wonton/peer/0`，`crates/wonton-tunnel/tests/tunnel/peer_pair.rs`）：扫码、等同意、同意后两边绑定
  服务器名和 endpoint ID；拒绝、码过期、码被改、扫自己、已配对再扫、结果只认扫过的 endpoint ID、移除配对的通知到对方。
- 核心流程（`crates/wonton-core/src/peers/peers_tests.rs`、`crates/wonton-core/src/gateway/peers_api_tests.rs`）：
  出码、扫码、卡片同意后 `GET /_wonton/api/peers` 两边都是已配对；拒绝和卡片过期把两边的记录清掉；核心重启丢未回答的
  请求、保留已配对；一个服务器名只解析到配对时绑定的 endpoint ID；非主人设备的请求一律 401，错误类别和
  `X-Wonton-Error` 一致。
- 删除与同意的先后（`crates/wonton-core/src/peers/peers_tests.rs` 及 `peers_tests/`，2026-11-07，测试提交 `71daea6`）：
  - 对方删了配对：通知到达时记录留着、相位改成内部的 `Phase::RemovedByPeer`（就是落盘的状态，重启后还在），
    视图给 `RemovedByPeer`，联邦名单和查找撤掉；只有 `RemovePeer` 真删记录，对方已经没有记录时收到通知也不报错。
  - 本机离线、上线后联邦握手被对方拒绝：和收到通知同一个结果，不靠通知送到。
  - 对方删了以后两个方向重新配对：标过的记录被新配对替换，不报“已经配对过”，新配对照常成立。
  - 转发组件报连上时记下时刻（`last_connected_ms`）：对方删了、对方停掉以后还是那一刻，重启后还在。
  - 同意之后的第一次探活直接 `Connected`，中间不出 `RemovedByPeer` 或 `Offline`；出码方收下扫码方回送的配对结果。
- 回归：`wonton-tunnel` 既有测试 47 条全过。真实两机端到端（配对、互发、跨机群）待 Tuwunel 配置任务就绪后验证。
- 配对改成长效码加请求（`wonton/peer/1`，2026-11-07，进程内两个 endpoint / 两个核心）：长效码扫两次、
  重置后旧码作废并清掉旧请求、请求限频（20 条 / 一小时 10 条）、拒绝和撤销、互相发请求直接成立、
  重名标 `conflicts_with`、同名不同 endpoint、用户 ID 和服务器名对不上、取消请求、扫码方离线时的问结果、
  同意后的第一次探活直接 `Connected`、码里没有直连地址（`crates/wonton-tunnel/tests/tunnel/peer_pair.rs`、
  `crates/wonton-core/src/peers/peers_tests/`、`crates/wonton-core/src/gateway/peers_api_tests.rs`、
  `crates/wonton-client/tests/it/peers/`）。两台真实主机待实机任务。

实测（2026-11-07，Tuwunel 1.9.4 官方镜像，单机 Docker 上的对照实验）：

- **两份配置文件可行**：`-c` 可以给两次，后一份覆盖前一份的同键（拿 `server_name` 做探针实测；
  源码 `core/config/sources.rs` 也是这个语义）。第二份可以是无 `[global]` 段头的裸键文件（一份文件里
  段头和裸键不能混）。`SIGUSR1` 会重读全部启动配置文件：原地重写第二份里的名单后发 `SIGUSR1`，
  名单外邀请 403、名单内放行，删名单、恢复两个方向都实测，不用重启。
- **`/etc/hosts` 不能热加载**：以单文件绑定挂载进容器，宿主原地改写后，运行中的 Tuwunel 不重读；
  发 `SIGUSR1` 也不生效（配置热加载不重建解析器，hosts 是解析器构造时读的一次性快照）；重启容器
  才用上新映射。这是放弃 hosts、改走代理的原因之一。
- **出站一律拨 TLS**：联邦的出站请求固定用 https，对端监听没有 `[global.tls]` 时握手直接失败
  （socat 抓到出站首字节是 TLS ClientHello）。所以联邦拓扑里每台 Tuwunel 都要配自签证书终结 TLS，
  隧道转发进来的字节也要接在带 TLS 的监听上。
- **出站经代理可行**（Tuwunel 1.9.4，镜像 digest `sha256:0e86c616…`，两台容器加一个 CONNECT 代理，两台的
  `/etc/hosts` 和 DNS 里都没有对方的名字）：`[global.proxy]` 配上代理后，查对方用户资料、邀请、对方加入、对方收到
  消息都通。代理先收到 `CONNECT <名字>:443`（取 `.well-known`），回 502 后 Tuwunel 马上改发 `CONNECT <名字>:8448`。
  正式的配置（`by_domain`、核心的转发组件、Docker 分配的网络）由 `federation_config/proxy_tests.rs` 覆盖：
  两套各在自己的网络上、同时起，经两个核心的转发组件互通。
- 名单外请求被远端拒时，客户端 API 看不到 401/403 的原文：不可转发的错误被包成 502
  “Request to X failed.”（Tuwunel `core/error/response.rs` 的 withheld 逻辑）。核心做配对状态提示
  不能依赖客户端 API 的错误形态。
