# ADR-0071 聊天时间线的位置：回到底部、新消息数、重进停在哪，都由核心算

- 状态：已接受（2026-11-08）

## 背景

现状（Android 实测）：往上翻走以后新消息不拽列表（对），但右下角没有回到底部的入口，翻走期间来了几条也看不出来，只能一路滑回
底；每次进房间、换房间回来、杀掉 App 再进都直接跳到最新一条，上次看到哪不留痕（#745 第 3 项）。

时间线里已经有已读标记（`TimelineContent::ReadMarker`，Matrix 的已读位置，SDK 的 `__read_marker`），Android 在最新一条出现时
就发 `Action::MarkRoomRead`。缺的是“离开底部以后来了几条”和“进房间该停在哪”这两件判断。

它们是同一件事的两面，都要按条目种类、顺序和已读位置算。放在壳里要 Android 和 iOS 各写一遍，两边一漂移，数字和落点就不一样
（ADR-0005 的厚核心）。

## 决策

### 核心算，壳报告和渲染

- 壳报告列表在不在底部：`Action::SetTimelineScroll { room_id, scroll }`，`scroll` 是 `TimelineScroll::Bottom` 或
  `TimelineScroll::Away`。跨过底部时发，不每一帧发。
- 核心在每一批 `TimelineUpdate` 里给出 `viewport: TimelineViewport`：`Bottom`，或 `Away { new_messages }`。
  `new_messages` 是房间的未读数，和聊天列表那一行同一个数（SDK 的 `num_unread_messages`）。
- 壳画不画按钮只看 `viewport`：`Away` 时在右下角画“回到底部”，`new_messages` 大于 0 时把数字写在按钮上，是 0 时只画箭头。
  点按钮滚到最新一条，滚完报 `TimelineScroll::Bottom`，核心把 `new_messages` 归零。
- 新消息不拽列表。`Away` 期间到了新消息，只让 `viewport` 和数字变大。

### 进房间停在哪

第一批 `Reset` 带 `anchor: Option<String>`，是 `Reset` 里的 `TimelineItem::id`，壳先把它摆到视野顶部，之后每一批是 `None`。
壳在这个落点摆好之前不报 `Bottom`：报早了核心以为主人已经看到最新一条，会清掉落点。

落点是本账号的已读位置，主人一眼看到“以下是新消息”：

- 这一批里有 `TimelineContent::ReadMarker`（`__read_marker`）：锚它自己。那一行正好夹在已读和未读之间，摆在视野顶部就是
  “以下是新消息”的分界。
- 没有这一行，有未读，且已读位置在这一批里：锚位置后面第一条（后面没有了就是最新一条）。
- 没有这一行，有未读，已读位置不在这一批里（未读多到被加载窗口截断）：从末尾往回数未读条数，头一条就是落点；数不够一屏
  就锚最早一条，让主人接着往回翻，而不是把未读丢在身后。
- 没有未读：锚最新一条，和现在一样。
- 空房间：`None`。
- 给了落点、摆过去之前这一条没了（撤回、被裁掉）：壳停在最新一条。

已读位置取本账号的已读回执（`Timeline::latest_user_read_receipt_timeline_event_id`）。`ReadMarker` 那一行只用来当落点，
不用来判断有没有未读：这一行只在已读位置后面还有别人发的消息时才插，有它一定还有未读；但没有它不等于读完了，可能是读完时
被删掉、未读被加载窗口截断，或者标记还没插上。拿它当判据会把还有未读的房间当成读完。有没有未读看未读数：0 才是读到底了。

### 已读回执

只在真的贴着最新一条时发 `Action::MarkRoomRead`（新消息到了、点了按钮滚回底部）。翻在别处时新消息不标已读，
重进就停在已读位置。

已读位置直接取 SDK 跟踪的本账号已读回执，核心不另存一份；订阅重建（重进房间、重启核心）时也是同一份。

`MarkRoomRead` 派发成功只代表后台操作已排队；回执同步后未读数才清零。房间列表是可合并快照，时间线是按序消费的增量队列，
两者不同时到达：列表已清零不代表时间线的旧批次已经消费完；首批的 `Away` 也不代表后来报告的翻走已生效。

### 按钮的样子

- iOS：右下角的圆形材质按钮叠在列表上，上下留出输入栏和 Home 条的余量；带数字时数字在箭头上方的胶囊里。材质按 ADR-0029。
- Android：Material 3 的 `FloatingActionButton`，数字用 `BadgedBox`（99 以上写 `99+`），随 `Away` 进出做缩放淡入。
- 无障碍标签两端都带数字（“回到底部，还有 3 条新消息”），文字进各平台的本地化资源（ADR-0043）。不加副标题和说明文字。

## 理由

- **数字用房间的未读数，不用视野里数。** 和聊天列表那一行是同一个数：主人看到两处对不上会以为坏了。翻进历史里、下面都看过了时
  是 0，只画箭头；翻走以后到的消息都进这个数，翻走之前看过的不进。已读位置只在到底时移动，所以数字不会被翻动带跑。
- **落点用服务器的已读位置，不用壳的滚动位置。** 它在服务器上，换房间回来、杀掉 App 再进都还在；壳的滚动位置重进就没了，
  两端还要各存一份、各写一套失效规则。
- **判断有没有未读用未读数，不用 `ReadMarker` 那一行；但落点优先用这一行。** 已读位置后面没有别人的消息时 SDK 不插这一行，
  读完时还会删掉，未读数 0 才是“读到底了”；这一行在的时候它正好是已经渲染好的分界，锚它比锚后面第一条还准。
- **`anchor` 是条目 ID。** 时间线的条目 ID 在编辑、本地回显之后都不变，比下标稳：`Reset` 和壳的列表之间不会错位。
- **落定之前不报 `Bottom`。** 列表第一次量出来停在第 0 项（倒着排就是底部），不挡一下，核心先把落点当成看完了，按钮上的
  未读数字会闪一下再回来。

## 没选的方案

- **数字在壳里数。** 规则（0 时只显箭头、到底归零）要在 Kotlin 和 Swift 各写一遍，两端的落点规则也要各写一遍。
  壳已经按 `TimelineDiff` 维护着条目，数得出来，但核心的 ViewModel 就管不到这件事了。
- **用 `ReadMarker` 那一行当判据。** 省掉查已读回执，但 SDK 只在位置后面还有别人的消息时才插这一行、读完时删掉，
  “没有这一行”同时对应“读完了”和“从没读过”。
- **滚回底部用下标。** 本地回显发出、消息被编辑、翻页都在改下标，壳和核心的下标会错开。
- **新消息自动拽列表的开关。** 主人没要，先不加。
- **进房间一律回到底部。** 就是现在的样子，未读全被当成看过了。

## 代价

- 每一批 `TimelineUpdate` 都多一个 `viewport`，哪怕没动过。
- 壳要防抖着报滚动，报得太勤核心就跟着算得勤。
- 未读数是 SDK 按通知那套规则算的，和时间线里“没看过的条数”可能差一两条（不进时间线的状态事件、自家别的设备发的）。
- 回执送不到服务器时（离线），别的设备的已读位置不跟着走；本机照旧按底部的 0 画。
- 停在已读位置后面时，视野上面就是已看过的最新内容，往下才没读。
- 未读多到已读位置不在这一批里时，落点按未读数往回数，未读数和条目种类对不齐（比如中间夹着不进时间线的状态事件）时会差一两条。

## 待验证

- Android 自建 AVD（API 35）：翻走后来 3 条，按钮显示 3，点了回到底部、数字清零。
- 有未读时重进房间停在第一条未读，不跳到最新一条；未读几百条时停在最早一条。
- iOS 模拟器上同样两条。
- 已读回执只在到底时发出（服务器上同账号另一台设备的已读位置跟着走）。
