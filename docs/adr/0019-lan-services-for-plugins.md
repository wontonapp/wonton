# ADR-0019 插件在局域网上提供服务：只发布清单声明的端口

- 状态：已接受（2026-11-02）。“`webui` 的端口不能列进 `lan.ports`”已被 [ADR-0023](0023-egress-proxy.md) 取代；“Bot 装不了高权限插件”已被 [ADR-0033](0033-plugin-tabs.md) 取代；“`network.host` 仍不开放”已被 [ADR-0036](0036-plugin-privileges.md) 取代

## 背景

有些插件要让局域网里的电脑、手机、电视直接连上来，不经核心网关：
- Samba：SMB 用 445/tcp。
- Syncthing：同步用 22000/tcp 和 22000/udp，本地发现靠 21027/udp 广播。
- DLNA：SSDP 组播 239.255.255.250:1900，另加一个 HTTP 端口。

插件规范拒绝 compose 的 `ports` 和 `network_mode: host`。`network.host` 可以写进清单，但安装时报“尚未支持”。
ADR-0011 规定插件不直接向宿主或外网暴露端口。`sso: proxy` 信任网关加上的请求头，前提是只有核心连得到插件的端口：Docker
Engine 28 起，局域网不能经路由直接访问容器里没发布的端口。

有两条路可选：照 `network.host` 让插件直接用宿主的网络；或者新加一项权限，只把清单声明的端口发布到局域网。两条路在发现协议上
差别也大：
- macOS 和 iOS 靠 mDNS（`_smb._tcp`）找 SMB 服务器；
- Windows 靠 WS-Discovery（239.255.255.250:3702）；
- DLNA 靠 SSDP；
- Syncthing 靠 21027 端口的广播。

这些都是只在本网段里传的组播或广播。下面的取舍以开发机上的实测为准（见“验证结果”）。

## 决策

- **新权限 `network.lan`（高权限），只开放清单逐项列出的端口。** 写在 `lan.ports` 里，每项是服务、端口和协议：

  ```yaml
  x-wonton:
    permissions: [network.lan]
    lan:
      ports:
        - { service: samba, port: 445 }
        - { service: syncthing, port: 22000 }
        - { service: syncthing, port: 22000, protocol: udp }
  ```

  - 宿主端口和容器端口相同，不做映射。SMB 客户端只认 445，换了端口就等于不能用。
  - `protocol` 取 `tcp`（默认）或 `udp`。
  - `mcp` 的端口不能列进来，它只经网关访问。`webui` 的端口原来也不能，ADR-0023 放开了，由主人决定；`sso: none` 的网页，以及做不到只信任核心的代登录，要主人打开开关 `lan_webui`。
  - `lan` 和 `network.lan` 要一起写，只写一个，清单不合法。
  - 不能和 `matrix.bot` 一起申请：地址变了要按安装记录重新渲染、重建容器，核心不保存 Bot 的访问令牌。
  - compose 的 `ports` 和 `network_mode: host` 照旧拒绝。
  - Bot 装它要走确认卡片，见 ADR-0033 的“确认”。
- **端口开在核心自动选出的一个局域网地址上。** 核心发布端口时逐个填上 `HostIp`；由启动器声明了宣告地址时例外，见下面
  “绑定地址和宣告地址分开”。
  - **默认只选一个地址。** 先找宿主的默认路由：看 main 路由表，有几条时取 metric 最小的。选的是这条路由所在网卡的私有 IPv4
    主地址，不是宿主上所有的私有地址。
  - **虚拟网卡不进候选。** 这包括 Docker 的网桥（按 Docker 的网络列表认，不按名字猜）、veth、tun（Tailscale 等）和 WireGuard。默认
    路由正好走这些网卡时，不自动选，按下面“检测不到”处理。主人自己建的网桥（虚拟机主机上常见的 `br0`）不算虚拟网卡。
  - **只用私有地址。** 即 IPv4 的 10/8、172.16/12、192.168/16、100.64/10（运营商级 NAT，也是 Tailscale 用的网段），以及 IPv6 的
    fc00::/7。公网地址、环回地址和链路本地地址一律不用。
  - **主人可以改。** 在设置里可以改选网卡（端口跟着这块网卡的地址走），也可以直接选地址，可以多选。要开到 Tailscale、WireGuard
    这类网卡上，就在这里自己勾选。确认安装页和设置里都显示端口开在哪块网卡的哪个地址上。选网卡时只用它的 IPv4 地址，
    IPv6（fc00::/7）地址要逐个选。在这类地址上，插件看不到真实的客户端（见“代价与风险”），设置里在地址旁写明。
  - **`WONTON_LAN_ADDRESSES` 用来覆盖。** 核心容器设了这个变量（逗号分隔）时，只用里面的地址，不再自动选；设置里显示为由它
    指定，不能改。里面有不是私有地址的，核心启动时报错退出。
  - **检测不到就装不上。** 以下几种情况，`network.lan` 的插件都装不上：没有默认路由；默认路由走的是虚拟网卡；那块网卡上没有私有
    IPv4 地址；检测用的容器起不来；服务器跑在桌面虚拟机里而启动器没声明宣告地址（见下）。预览的 `blocked` 和安装错误都写明是
    哪一种，前几种并提示去设置里选网卡。错误类别是 `lan_unavailable`（HTTP 422）。
  - **插件知道自己开在哪里。** 核心把手机要连的地址经环境变量 `WONTON_LAN_ADDRESSES` 交给插件，插件可以在自己的网页上告诉用户怎么
    连，比如 `smb://192.0.2.10/`、`tcp://192.0.2.10:22000`。

### 绑定地址和宣告地址分开

“局域网地址”是两个不同的东西，桌面虚拟机（Docker Desktop、OrbStack、WSL2、Lima 这类）里它们不是一回事：

- **绑定地址**：容器端口经 `HostIp` 开在哪，必须在跑 Docker 的这台 Linux 的网卡上，否则容器起不来。
- **宣告地址**：告诉手机去哪连。它同时是隧道向 iroh 宣告的地址（ADR-0032）、配对信息里的直连地址、`lan.client` 的连接提示、
  插件拿到的 `WONTON_LAN_ADDRESSES`，以及出网直连网段（ADR-0023）的来源。

核心在桌面虚拟机里看到的是虚拟机 NAT 的网卡（OrbStack 198.19.x / 192.168.139.x，Docker Desktop 192.168.65.x，Lima usernet
192.168.5.x，WSL 随机的 172.x），手机在家里连不到。启动器知道电脑（宿主）的真实地址，用 `WONTON_ANNOUNCE_ADDRESSES` 交进来：

- 逗号分隔，每项是私有地址，可以带前缀（`192.168.1.20/24`）。宣告时只用地址；出网的直连网段用带前缀的网段，不带时 IPv4 按 /24、
  IPv6 按 /64。不是私有地址、前缀超长时核心启动报错退出。
- 设了就绑 `0.0.0.0`（有 IPv6 宣告地址时再绑 `::`），不绑选出的网卡地址；宣告的地方全用宣告地址。设置里两个都显示为不可改，
  `WONTON_LAN_ADDRESSES` 在设了宣告地址时不起作用。
- **为什么绑 `0.0.0.0`：** 宣告地址是宿主的地址，不一定在虚拟机的网卡上，绑到它上面容器起不来。OrbStack 的端口转发在 VM 外做，
  绑定到具体宿主接口长期不生效（[#291](https://github.com/orbstack/orbstack/issues/291) 到 v2.1.0 才实现，之后仍有人实测“代理在监听、
  连接不转发”）；Lima 的默认 `portForwards` 把虚拟机里的 `127.0.0.1` / `0.0.0.0` 都转到宿主 `localhost`，宿主侧监听哪个地址由
  启动器的规则决定。`0.0.0.0` 在这几种转发器里都能用。端口本来就要求全局唯一，通配绑定不需要按地址拆端口；预览的冲突检查按通配算，
  Docker 里任何地址上占着的同号端口都算撞上，宿主进程的试探仍走检测到的网卡地址。
- **怎么认出桌面虚拟机：只按内核串和 DMI 认，不按网卡类型或网段猜。** 检测容器读 `/proc/version` 和
  `/sys/class/dmi/id/{product_name,sys_vendor}`（容器里读到的是宿主虚拟机的内核和 DMI，不需要新挂载），里面含 `linuxkit`
  （Docker Desktop）、`orbstack`、`microsoft-standard-wsl2` 就是。Proxmox、ESXi、Unraid 里桥接的虚拟机是普通发行版内核，照常自动选；
  WSL 的随机 172.x 也可能撞上真实的家庭网段，所以不按网段猜。Lima 的内核也是普通发行版，认不出，由启动器声明（变量存在即说明
  有启动器）。
- **认出来又没设宣告地址就如实报错。** 新的错误类别 `desktop_vm`，照旧经 `lan_unavailable` 到用户面前，核心写的详情（按 App
  的语言）讲清“服务器跑在电脑的虚拟机里，手机连不到虚拟机的地址”和“启动器要设 `WONTON_ANNOUNCE_ADDRESSES` 为电脑的局域网地址”，
  并带检测到的内核串。设了 `WONTON_LAN_ADDRESSES` 也照报：它写的是绑定地址，解决不了这个问题。不静默降级。
- **怎么检测。** 核心在容器里看不到宿主的网卡，所以用自己的镜像起一个一次性的小容器来查。
  - 这个容器用宿主网络，去掉全部能力，根文件系统只读，不挂任何东西，以 nobody 身份运行。
  - 它读 `/proc/net/route`，经 netlink 列出地址，看 `/sys/class/net` 认出网卡的类型，再读 `/proc/version` 和 DMI 的型号、厂商，
    把结果打印出来就退出。
  - 核心直接跑在宿主上时（开发时），不起这个容器，直接读。
- **地址变了自动跟上。**
  - 核心启动时检测一次，运行中每 5 分钟再检测一次（隧道也要这些地址，见 ADR-0032，所以没有局域网插件时也检测）。预览、
    安装和打开局域网设置时也当场检测一次。
  - 绑定或宣告的地址变了，就按新地址重建声明了 `network.lan` 的插件里 `lan.ports` 指定的服务，以及 Compose 插值实际用到 `WONTON_LAN_ADDRESSES` 的服务（包括 `configs.content`），数据不动。一次性服务也按安装时的依赖顺序重新运行；无关服务和仅被它们依赖的服务不重建。
  - 检测不到地址时，把这些插件标为异常并写明原因。端口不改开到别的地址上，插件也不显示为正常。
- **端口发布在哪个网络上。** Docker 不在内部网络上发布端口，而且不报错（见“验证结果”）。
  - 声明了 `network.egress` 的插件，插件网络本来就是普通桥接，端口直接发布在它上面。
  - 没声明的，核心另建一个 `wonton-<slug>--lan`：关掉地址伪装（`com.docker.network.bridge.enable_ip_masquerade=false`）的
    桥接网络。只有 `lan.ports` 里的服务接进来，端口就发布在这个网络上。
  - 这些服务仍在原来的插件网络里，核心照常经那里访问它们。
  - 局域网的连接经 DNAT 进来，回包靠连接跟踪原路返回。网络关掉了伪装，这些服务主动连外网或局域网的其他主机都收不到回包，
    要出网仍得声明 `network.egress`。
- **不做发现。** 核心不替插件发 mDNS、WS-Discovery 或 SSDP，也不转发组播。用户按地址连：macOS 用 Finder 的“连接服务器”，
  Windows 输 `\\192.0.2.10\`，Syncthing 在对端填地址。DLNA 只能靠 SSDP 被找到，所以这样装上也用不了；以后真要做 DLNA 插件时
  另写 ADR。
- **端口冲突在预览里就说清。**
  - 预览拿已装插件的 `lan.ports` 查重。端口被占时 `blocked` 写明被哪个插件占着。
  - 被宿主自己的服务占着的端口，核心在容器里看不到。这种情况由 Docker 在启动时报错（`port is already allocated`、
    `address already in use`），安装把原文附上，然后回滚。
- **安装确认醒目展示。** 预览的 `notices` 里每个端口一行，醒目显示：哪个服务的哪个端口、开在哪块网卡的哪个地址上；局域网里的
  设备能直接连，不经核心登录，身份由插件自己验证。
- **`network.host` 另走一条路**：见 ADR-0036。这篇的端口发布方式不变，它实测到的问题写进了那边的提示。

## 接口：App 和核心

类型在 `crates/wonton-protocol` 的 `lan` 模块，字段的含义写在类型的文档注释里。鉴权和错误的格式同 ADR-0017 的“接口：App
和核心”。

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| GET | `lan` | — | `LanSettings` |
| PUT | `lan` | `LanChoice`（JSON） | `LanSettings` |

- GET 时核心当场检测一次，结果的处理同定期检测。
- PUT 时，核心核对选择后存下（重启后照旧），按上面的地址变化规则重建插件容器，做完再返回新的设置。请求断开了也照样
  做完。重建失败的插件标为异常，`plugins` 里写明原因。
- `LanSettings` 里 `addresses` 是绑定地址，`announce_addresses` 是手机要连的地址（没设宣告变量时两者相同）。
- 错误类别：
  - `invalid_input`（400）：一项都没选，网卡或地址不在 `interfaces` 里，或者 `mode` 不认识。
  - `conflict`（409）：地址由 `WONTON_LAN_ADDRESSES` 或 `WONTON_ANNOUNCE_ADDRESSES` 指定，不能改。
  - `lan_unavailable`（422）：选的网卡上没有私有 IPv4 地址，或者检测不了网卡。
- 客户端核心（`ClientCore`）有两个直接返回结果的调用：`lan_settings()` 和 `set_lan_choice(choice)`。
  - 出错时，`invalid_input` 和 `conflict` 返回 `InvalidInput`，`lan_unavailable` 返回 `NotReady`。
  - 安装或升级因 `lan_unavailable` 失败时，任务失败的原因是 `PluginFailure::LanUnavailable`，壳提示主人去局域网设置。

## 没选的做法

- **`lan.ports` 放开 `webui` 的端口，给第三方 App 用。** 没有 TLS，局域网设备还能绕过网关。第三方 App 走 ADR-0021。这条限制已被 ADR-0023 取消：要不要接受这个风险由主人决定（`sso: none` 的网页，以及做不到只信任核心的代登录，默认不开，要主人打开开关 `lan_webui`），第三方 App 的推荐做法不变。
- **宿主网络（`network.host`）。** 好处是发现协议、广播和 IPv6 都能直接工作；本地发现这一点，Syncthing 的 Docker 说明也建议用
  宿主网络。但插件进了宿主的网络命名空间，实测有这些问题：
  - **碰得到宿主上只给本机用的服务。** 实测连上了 caddy 的管理接口（能改整个反向代理）、MongoDB、Ollama 和代理，这几个都只监听
    `127.0.0.1`。
  - **能绕过网关直连别的插件。** 声明了 `network.egress` 的插件，网桥在宿主上有地址；核心跑在宿主上时，所有插件的网桥也有地址。
    这些插件容器的端口都连得上，`sso: proxy` 的前提就不成立了。
  - **能抓别的插件的包。** 带着 Docker 默认给的 `NET_RAW`，它在另一个插件容器的 veth 上抓到了 `GET /secret?token=demo`。去掉
    `NET_RAW` 能挡住抓包，前两条挡不住。
  - **端口开在哪里由插件自己说了算。** 宿主有 Wi-Fi、Tailscale 和 IPv6 全局地址，它的端口就跟着出现在这些地址上。宿主网络里的
    Syncthing 发到局域网的广播，还带着 Tailscale 的地址和每个 Docker 网桥的网关地址。
  - **网关不好接它的网页。** 在开发机这种有防火墙的宿主上，桥接网络连宿主的端口被 ufw 挡住，在容器里的核心连不上它。没有防火墙
    的宿主上核心连得上，可局域网里的设备也能绕过网关直接打开它的网页。
  - **有防火墙的宿主上，主人不改防火墙就用不了。** 实测在开发机上，局域网连不上宿主网络里的 445 和 22000，进来的 21027 广播被
    丢掉。宿主网络里的 Syncthing 一台局域网设备都没发现。
  - **出了问题核心看不出来。** 445 被占时，smbd 只在日志里记一行，容器照样运行。

  ADR-0036 放开了它，由主人决定：提示写明这些问题，默认去掉 `NET_RAW`，网页经中继接入。
- **发布到所有地址（Docker 的默认做法）。**
  - 实测 Wi-Fi 地址上也开放，docker-proxy 还在 `::` 上监听，IPv6 全局地址也连得上。
  - Docker 发布的端口走 FORWARD 链，普通 ufw 管不到（见 Docker 文档）。宿主有公网地址，或者路由器放行 IPv6 入站时，SMB 就直接
    暴露在互联网上了。开发机上挡住这些的是主人另装的 ufw-docker 规则，不能当作前提。
  - 核心自己的网关端口确实发布在所有地址上，但它每个请求都鉴权；插件的协议不是我们写的代码。
- **地址由主人手配（这份 ADR 的上一版草稿）。** 地址写死在配置里，DHCP 一换就失效：开发机重启后地址从 192.0.2.14 变成了
  192.0.2.10。这个做法保留下来，作为 `WONTON_LAN_ADDRESSES` 覆盖。
- **安装器在宿主上检测一次，写进 `.env`。** 安装器跑在宿主上，看得到网卡，但只检测这一次，跟不上 DHCP 换地址。
- **选宿主上所有的私有地址。** Wi-Fi、Tailscale、虚拟机网桥上的地址会一起开出去。在开发机上，就是有线和 Wi-Fi 两个地址，再加上
  Tailscale 的地址。
- **别的检测办法。**
  - Docker API 查不到宿主的地址：`info` 里没有，`host` 网络的 inspect 里也没有。
  - 把宿主的 `/proc` 挂进核心：`/proc/1/net/route` 是能看到宿主的路由表，但整个 `/proc` 暴露了宿主所有的进程。
  - 核心自己改用宿主网络：核心就和宿主网络里的插件一样，碰得到宿主上所有的服务；核心和插件网络之间的连接也得重做。
  - 常驻一个宿主网络的小容器监听 netlink：地址一变马上就能跟上，代价是多一个一直开着的特殊容器。地址很少变，定期检测就够了。
  - 用 `ip route get` 查某个外网地址：它会走策略路由，Tailscale 用出口节点时查到的是 tailscale0。所以只看 main 表里的默认路由。
- **对照成熟项目的做法。**
  - Home Assistant 的[网络集成](https://www.home-assistant.io/integrations/network/)默认自动检测：看系统路由表里发往 mDNS 组播地址 224.0.0.251 的下一跳落在哪块网卡，用它当默认网卡；
    检测不到时，用所有有可用地址的网卡。主人可以在“设置 > 系统 > 网络”里改选给 Zeroconf 这类集成用的网卡（[2021.6](https://www.home-assistant.io/blog/2021/06/02/release-20216/) 加入）。我们的做法和它
    最接近，区别是检测不到时不退回“所有网卡”，而是装不上。
  - TrueNAS：SMB 服务的 Bind IP Addresses 不选时，监听所有活动的网卡（[CORE 13.0 文档](https://www.truenas.com/docs/core/13.0/uireference/services/smbscreen/)）；
    应用端口的 Host IPs 留空时绑到 `0.0.0.0`（[TrueNAS 应用文档](https://apps.truenas.com/managing-apps/installing-apps/)）。这个默认我们不照搬，理由和“发布到所有地址”一样。
- **macvlan 和 ipvlan。** 插件拿到自己的局域网地址，发现协议能用，端口也不会冲突。代价是：
  - 主人要选网卡，还要在路由器上留出一段 DHCP 不发的地址；
  - Wi-Fi 网卡大多不认额外的 MAC；
  - 宿主和 macvlan 容器互相不通；
  - 容器的所有端口都在局域网上，`sso: proxy` 的前提不成立。
- **允许 compose 的 `ports`，再加限制。** 写法是标准的，但同一行在 `docker compose up` 下绑所有地址，在 Wonton 里只绑局域网地址，
  读的人会误会。地址由核心决定，所以和显卡一样写在 `x-wonton` 里。
- **核心自己做四层转发。** 核心跑在容器里，要转发也得先把端口发布给自己，还得自己写 UDP 转发，是造轮子。
- **核心代插件发 mDNS。** 要经宿主 avahi 的 D-Bus 发布 `_smb._tcp`，就得把系统 D-Bus 挂进核心，而系统 D-Bus 能做的远不止 avahi。
  很多服务器也没装 avahi。而且这只管 mDNS，管不了 WS-Discovery、SSDP 和 Syncthing 的广播。

## 代价与风险

- **没有发现。**
  - Finder 和 Windows 的“网络”里看不到 Samba，要手输地址。
  - Syncthing 的对端要手填 `tcp://<地址>:22000`。填 `dynamic` 时，全局发现给出的是公网地址和容器地址，实测连不上。
  - DLNA 用不了。
- **自动选可能选错。** 多网卡的宿主上，默认路由走的不一定是主人想开的那块网卡。比如默认路由走 Wi-Fi，而有线接的是另一个网段，
  这时要主人去设置里改。
- **地址变了要等一会儿才跟上。** 最多 5 分钟；重建容器还会断开正在用的连接。
- **检测要起一个宿主网络里的容器。** 它跑的是核心自己的代码，不带任何能力，根文件系统只读，什么都不挂，跑完就删。但它确实在宿主
  网络里，这段代码只能读，不能有别的动作。
- **绑定的地址是唯一的边界。** 普通 ufw 管不到发布的端口，核心也不改宿主的防火墙。主人在设置里勾上 Tailscale，tailnet 里的设备
  也就能连上。
- **关掉伪装的网络比 `isolated` 宽。**
  - 接进来的服务连得上宿主自己的地址（受宿主防火墙约束），宿主也能直接连它。
  - 它主动往外发的包不做伪装，带着 Docker 地址池里的源地址离开宿主。局域网主机就算有路由回到宿主，也直接连不进容器地址（见
    验证结果）。但对这些包的应答能不能回到容器没实测；如果能，局域网恰好把这个网段路由回宿主时，连接就真的建立起来了。
- **IPv6 看不到真实客户端。** 插件网络只有 IPv4，IPv6 地址上的端口由 docker-proxy 转发，插件看到的客户端地址是网桥网关。IPv4
  经 DNAT 进来，看得到真实地址。
- **局域网的连接不经核心登录。** 协议自己的鉴权就是全部防线。官方索引收录插件时，要审核它的局域网服务默认是否需要登录。

## 验证结果（2026-11-02）

**环境**

- 开发机：Linux，Docker Engine 29.7.2。有线 eno1 是千兆，地址 192.0.2.10；另有 Wi-Fi wlp2s0（192.0.2.11）、tailscale0，还有
  IPv6 全局地址。下面的地址换成了文档地址（RFC 5737 的 192.0.2.0/24），实际是私有网段。
- 开发机的防火墙：开着 ufw，加了 ufw-docker 的规则，只放行必要的端口和来自私有网段的连接。
- 局域网客户端：Mac（有线千兆，192.0.2.12），测试主机（100 Mb，192.0.2.13，没有防火墙）。
- 镜像：
  - `quay.io/samba.org/samba-server:latest`（Samba 4.24.7，2026-11-01 构建）
  - `syncthing/syncthing:2`（2.1.7）
  - `nginx:stable-alpine`
  - `python:3.13-alpine`

**端口发布和网络类型**

从 Mac 和测试主机用 IPv4 访问 192.0.2.10：

| 插件网络 | 发布的结果 | 局域网访问 |
| --- | --- | --- |
| 普通桥接 | `0.0.0.0` 和 `[::]` | 通 |
| 内部网络（`internal`），带不带 `isolated` 都一样 | 没有发布，`docker run -p` 也不报错 | 不通 |
| 内部网络（`isolated`），再接一个关掉伪装的桥接 | 发布在后者上，默认路由也走后者 | 通 |
| 关掉伪装的桥接 | `0.0.0.0` 和 `[::]` | 通 |
| 普通桥接，只发布在 192.0.2.10 | `192.0.2.10` | 只有 .10 通；.11、Tailscale、IPv6 都不通 |
| 宿主网络 | — | 不通（被 ufw INPUT 挡住）；经 Tailscale 能通 |

- 关掉伪装的网络里，容器连不上外网（223.5.5.5:53），也连不上局域网里的其他主机（192.0.2.13:22），但连得上宿主自己的地址
  （192.0.2.10:22）。对照组的普通桥接，三个都连得上。
- 发布到所有地址时，局域网经 Wi-Fi 地址 .11 也能访问。开发机自己经 IPv6 全局地址能访问到 docker-proxy；局域网的 IPv6 访问被 ufw
  挡住。Tailscale 的访问被 ufw-docker 挡住，因为 100.64/10 不在它放行的网段里。
- 容器看到的客户端地址：经 DNAT 进来的是真实地址（192.0.2.12、192.0.2.13）；经 docker-proxy 进来的是网桥网关 172.29.0.1。
- 发布到宿主上没有的地址时，报 `failed to bind host port 192.0.2.14:18090/tcp: cannot assign requested address`，容器停在
  Created。
- 两个插件都发布 445 时，后一个报 `Bind for :::445 failed: port is already allocated`，容器停在 Created。
- 宿主网络的 smbd 遇到 445 已被占用时，日志里记 `Address already in use`，容器仍显示 Up。

**检测宿主的地址**

在开发机上，用 `nginx:stable-alpine` 里的 busybox 起了一个和检测容器一样受限的容器：`--network host --cap-drop ALL --read-only
--security-opt no-new-privileges --user 65534:65534`。结果：
- `/proc/net/route` 里有两条默认路由：eno1（metric 100）和 wlp2s0（metric 600）。按规则选出的是 eno1 上的 192.0.2.10。
- netlink 列出了所有地址，包括 tailscale0 的 100.101.102.103 和 Docker 网桥的地址。
- `/sys/class/net` 里认得出网卡类型：
  - Docker 网桥的 `uevent` 是 `DEVTYPE=bridge`，wlp2s0 是 `DEVTYPE=wlan`；
  - eno1 和 wlp2s0 有 `device`（物理网卡）；
  - tailscale0 有 `tun_flags`。

**局域网主机经路由直接访问容器**

经主人同意，在测试主机上临时加了一条路由 `10.250.0.0/23 via 192.0.2.10`，测完马上删掉。开发机上每种网络起一个 nginx，80 端口发布到
宿主，8081 不发布。从测试主机直接访问容器地址：

| 网络（网关模式） | 容器地址:80（已发布） | 容器地址:8081（没发布） |
| --- | --- | --- |
| 关掉伪装的桥接（`nat`），同时接在带 `isolated` 的内部网络里 | 不通 | 不通 |
| 普通桥接（`nat`） | 不通 | 不通 |
| `nat-unprotected`（对照） | 通 | 通 |
| `routed`（对照） | 通 | 不通 |

- 经宿主地址访问发布的端口，照常是通的。
- 两个对照组都有通的，说明路由本身没问题。nat 网关模式下，Docker 挡掉所有直接发到容器地址的连接，关不关伪装都一样；即使是已经
  发布的端口，也只能经宿主地址访问。

**宿主网络的容器**

使用 Docker 默认的能力：
- 连得上宿主只监听 127.0.0.1 的 2019（caddy 管理接口）、27017（MongoDB）、11434（Ollama）和 7899（代理）。
- 连得上普通桥接和不带 `isolated` 的内部网络里容器的端口；带 `isolated` 的连不上。
- 用 AF_PACKET 在另一个插件容器的 veth 上抓到了它收到的 HTTP 请求。加上 `--cap-drop NET_RAW` 后，创建 AF_PACKET 套接字时报
  `Operation not permitted`。
- 反过来，桥接网络里的容器（核心所在的位置）经网关地址、`host-gateway` 或宿主的局域网地址去连宿主网络里的服务，全部超时。

**Samba**

- 普通桥接，发布 445：Mac 的 `smbutil view` 列出了共享，协商到 SMB 3.1.1；测试主机上 445 端口连得上。
- 吞吐：Mac 挂载后读写 1.5 GiB 随机数据，写 114 MB/s，读 115.5 MB/s，达到千兆线速。
- 宿主网络下 445 被 ufw 挡住，只好让 smbd 改听 ufw 放行的 8090 来比较：写 114 MB/s，读 113–115 MB/s。同一个 8090 端口换成发布方式，
  写 115 MB/s。宿主网络第一次测写入只有 22–26 MB/s，原因没查到；单独重测是 114 MB/s。
- 发现：这个镜像里没有 avahi 和 wsdd。Mac 的 `dns-sd -B _smb._tcp` 能列出局域网里约 30 台 SMB 主机，其中没有 开发机。

**Syncthing**

- 本地发现，桥接网络（发布了 21027/udp）：在测试主机上收了 45 秒的 21027 广播。局域网里另外 6 台 Syncthing 每 30 秒广播一次，开发机上的
  实例一次也没有。它自己的发现缓存是空的，状态却显示 `IPv4 local` 没有错误。
- 本地发现，宿主网络：测试主机收到了它的广播。IPv4 的来源是 .11；IPv6 的来源是两块网卡的链路本地地址。广播里带了 38 个地址。它自己的
  发现缓存仍然是空的，因为进来的广播被 ufw 丢掉了。
- 连接和吞吐：对端是 Mac 上 OrbStack 里的 Syncthing，只往外连。
  - 地址填 `tcp://192.0.2.10:22000`：立刻直连，1.5 GiB 随机文件同步用了 17.5 秒，约 92 MB/s。
  - 宿主网络、改听 8090：用了 17.7 秒。
  - 地址填 `dynamic`：全局发现给出的是办公室的公网地址和容器地址 172.29.0.5，6 分半钟没连上。

**组播**

Python 往三个组各发三个带标记的包：

| | SSDP 1900 | WS-Discovery 3702 | mDNS 5353 |
| --- | --- | --- | --- |
| 桥接网络的容器发，测试主机收 | 收不到 | 收不到 | 收不到 |
| 宿主网络的容器发，测试主机收 | 收到 | 收到 | 收到 |
| 测试主机发，桥接网络的容器收（发布了 1900/udp 和 3702/udp） | 收不到 | 收不到 | — |
| 测试主机发，宿主网络的容器收 | 收到 | 收不到（被 ufw 挡住） | 收到 |

ufw 默认的 `before.rules` 放行 mDNS 和 SSDP 的入站组播。
