# 开 PR 与合并的队列规矩

开着同时太多 PR，最大的代价不是审查，是 CI 名额和冲突：一次 ios 构建四十多分钟、Android 二十多分钟，
同一批文件被几条分支改来改去，rebase 一次就白跑一轮。所以数量、顺序、寿命三件事都定死，
剩下的（落后 main、等构建）不算拦路。

## 1. 非 draft 的 PR 同时最多 6 张

满了要先合掉一张（或者把它合回卡里）才能开新的第 7 张。草稿不算数，但草稿别留着白占分支——
成型就置 ready，进队列；不成型就别开。

数的时候算「开着且非 draft」的张数：`gh pr list --state open --json isDraft`。

## 2. 基础层单独一条队，先合

这几处是全仓的地基，别的分支一碰就要重新 rebase，所以它们独占一条队，合并顺序在其它之上：

- `crates/wonton-protocol`（协议、动作、能力位）
- 核心订阅（gateway 的订阅与分发、`wonton-client` 的订阅侧）
- Composer（`composer/`、`chat/composer` 两端）
- 菜单与侧栏（两端菜单、房间侧栏、`menu` 相关文件）

做法：基础层的 PR 开着时，其它 PR 不许先合进 `main`——等它落地，其它分支再 rebase 上去、再往下走。
同一张 PR 同时碰了基础层和非基础层，按基础层算，单独走。

两条 PR 改到同一批文件（菜单、Composer 这类）时互相排队，先开的先走；不撞文件的并行推，不用等。

## 3. 分支寿命 48 小时

超过 48 小时没有新提交，关掉、内容退回卡里（卡上写清已到哪一步、还剩什么），别让死分支占着队列名额。
要接着做就重开分支，从当时的 `main` 起。

例外只有一种：PR 正在等一个明确的、有主的决定（等人审、等对方产线），卡上「等主人」或「等待」写着是谁等什么。
这种情况在满 48 小时时贴一条说明继续留着，没写清的照常关。

## 什么样不算拦路

- **落后 `main`**：不算。落后不挡合并，也不用为了它挂起。
- **`BLOCKED`**：先看是什么——`BLOCKED` 只分两种，别人正在跑、或者真有冲突。正在跑就等它跑完，不是问题。
- **冲突**：只有这个要排。冲突由 `.github/workflows/pr-rebase.yml` 在 `main` 动了之后自动试解一次，
  解不开就贴冲突文件清单打 `needs-rebase` 标，作者接手。挂着 `needs-rebase` 的 PR 不进合并队列。

## 复审和合并

复审只在**最新的、已提交的 head** 上判，旧 head 的结论一律作废；复审不改码、不推 head，有问题发 review
结论退回作者。作者照结论改完推上去即算答复，不需要额外回话。

不需要 approve 状态，也没有 approval 门槛：CI 绿、没有冲突、没有 `needs-rebase`，就直接合
（`gh pr merge --squash` 或 auto-merge）。合并用 squash。

## 收尾

PR 合了就把对应的卡当场收掉，并清掉本地分支；`needs-rebase` 的 PR 解完冲突后自己摘标。
